# 変更を設計する

実装する人が、範囲、リスク、検証について新しく判断しなくても進められる計画を作る。\
出力は計画であり、対象のファイルは変更しない。

## 作業手順

1. **目標を言い直す**

   期待する挙動、範囲、対象外、制約を示す。\
   成功の条件と対象外が、推測なしに明確であれば完了とする。\
   明確でない場合は止まり、ユーザーが明確にすべきことを報告する。

2. **影響を受ける構造を洗い出す**

   変更が影響し得る入口、主な分岐、責務の境界、現在の確認を見つける。\
   変更が影響し得る部分をそれぞれ挙げられれば完了とする。

3. **変更の境界を定める**

   確認された原因を完全に修正し、現在の要件を満たす、最も小さな境界を見つける。\
   境界は、影響を受ける責務、不変条件、取り決め、既知の実行経路から導く。\
   そのうえで、変わらない部分と、影響を受けるインターフェース、モジュール、データ、設定、依存関係、コードの利用者を挙げる。\
   影響を受ける各部分が、理由とともに境界の内か外に分けられれば完了とする。

   境界には、次の規則を当てはめる。

   - 現在の公開された入力、シグネチャ、呼び出し方は、現在の証拠が変更を求めない限り保つ。\
     「missing」のような語は、既存の値を指すことも、新しい呼び出し方を指すこともある。\
     その意味は、現在の取り決めと呼び出し元から判断する。
   - コードを共通化するのは、同じ知識、責務、不変条件、取り決めを証拠が示している場合だけにする。\
     見た目が似ているだけのコードは、重複したままでよい。

4. **局所的な修正か、構造的な修正かを選ぶ**

   局所的な修正で確認された原因を修正できる場合は、局所的な修正を選ぶ。\
   局所的な修正が次のいずれかに当たる場合は、構造的な修正を選ぶ。

   - 確認された原因を残す
   - 既存の規則を写す
   - 確立した責務の境界を迂回する
   - 既知の経路の間で挙動を食い違わせる
   - 既知の追加修正を必要とする

   構造的な修正では、次の項目を示す。

   - 局所的な修正では足りない理由
   - 構造的な修正によって取り戻すもの
   - 変わる取り決めと、変わらないもの

   不確かさ、結合の強さ、やり直しの費用によって比較が役立つ場合は、構造の異なる代案と比べる。\
   選択に、証拠が支える理由があれば完了とする。

5. **新しい構造の理由を示す**

   新しい抽象化、依存関係、設定項目、互換のための経路、プロセス、サービス、デプロイの単位ごとに、次の項目を記録する。

   - それが解決する現在の問題と、その問題か、合意した近い将来の要件を示す証拠
   - 検討したより単純な代案と、それでは足りない理由
   - 保守と運用にかかる費用

   既存の書き方と設計は、既知の失敗が構造的な変更を必要としない限り保つ。\
   設計原則は、責務、取り決め、インターフェース、依存関係についての現在の問題を解くためだけに使う。\
   任意の将来の改善は、別の一覧にする。\
   新しい項目のそれぞれに、現在の理由があれば完了とする。

6. **リスクへの対処を計画する**

   重要なリスクごとに、防ぐ、減らす、検知する、復旧する、埋め合わせる、封じ込めるのいずれかの方法を示す。\
   リスクの中には、通常の実装計画を超えて、実行の前に管理策を必要とするものがある。\
   たとえば、破壊的な操作、データの移行、セキュリティの変更、外部の状態の変更、元に戻せない変更である。\
   これらのリスクでは、別の実行準備の評価が必要であることを示し、その評価で決めるべきことを挙げる。\
   重要なリスクのそれぞれに、対処の方法か実行準備の必要性があれば完了とする。

7. **検証を計画する**

   変更する責務、挙動、回帰のリスク、失敗の境界ごとに、確認と、期待する証拠を示す。\
   各確認の深さは、その影響と不確かさから選ぶ。\
   たとえば、静的な確認、焦点を絞った回帰テスト、繰り返しの計測である。\
   一つの確認で複数の主張をそれぞれ明確に示せる場合は、その確認を共有する。\
   各項目に確認があれば完了とする。

8. **作業を分ける**

   作業を、人がレビューできる小さな単位に、挙動と責務に沿って分ける。\
   読みやすさのための変更では、処理の段階と、読み手が一緒に理解する単位で分ける。\
   開始の条件、実装の範囲、停止の条件を示す。\
   依存関係の追加、破壊的な操作、未解決の権限は、実装を始める前に挙げる。\
   各単位に範囲と期待する結果があれば完了とする。

9. **レビュワー向けの情報を用意する**

   実装する人とレビュワーのために、次の項目のうち当てはまるものを用意する。

   - 目的と、期待する結果
   - 製品や運用の状況と、その重要度
   - 範囲と対象外
   - 影響を受ける利用者、データ、取り決めと、変更が誰から見えるか
   - 制約と、受け入れたトレードオフ
   - 計画した検証と、不明な点
   - 検知と復旧の手段
   - レビュワーが注意して見るべき箇所

   重要度や影響の及ぶ範囲が分からない場合は `Unknown` とし、低リスクとはみなさない。\
   当てはまる各項目に、値か `Unknown` があれば完了とする。

## 報告

変更に合った構成で、次の項目を含める。

- 推奨する進め方と、その証拠、前提、未解決の問い
- 変わるものと、変わらないもの
- 選択が重要な場合は、局所的な修正か構造的な修正かの理由
- 必要な現在の作業と、任意の将来の改善
- 依存関係、影響を受ける境界と利用者、互換性への影響
- 重要なリスクと、それぞれへの対処の方法
- 検証: 各責務やリスク、起こり得る失敗、確認とその期待する証拠
- レビュワー向けの情報
- 開始と停止の条件、実装の範囲、作業の単位

代わりの設計、モジュールの構成図、移行の詳細、切り戻し、ユーザーへの説明点は、重要な場合だけ加える。\
計画した確認には、それぞれ未実行と記す。\
影響の大きい未決定の選択は、ユーザーに委ねる。
