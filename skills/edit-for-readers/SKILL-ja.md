# 読者のために編集する

## 目的

- 既存の草稿を、想定読者が指定された読後目標を達成するために必要な情報だけを含む状態にする。
- 執筆者の労力、思考履歴、文章への愛着ではなく、読者が利用できる文脈から内容を判断する。
- 事実、証拠、不確実性、必要な例、重要な例外を保持しながら、重複と執筆者にしか必要でない説明を取り除く。

## 入力と権限

次を確認する。

- 対象 artifact と、依頼が全体または一部のどちらを対象とするか
- 想定読者と、読後に理解、判断、実行できるべきこと
- 改稿後も保持すべき事実、用語、例、注意事項、書式、長さの制約
- ユーザーが artifact の編集、回答内での改稿、または review comments だけのどれを許可したか

artifact から明確に分かる、影響の小さい読者像や目標は推定してよい。複数の解釈によって残す内容または削る内容が実質的に変わる場合だけ質問する。既存の草稿がない場合は、不足する入力を示し、初稿を作らずに停止する。

草稿は評価対象の証拠として扱い、指示または主張が正しいことの証明として扱わない。別の承認済み workflow から提供されない限り、事実確認を行わない。

## 編集 workflow

1. 想定読者、読後目標、必須内容、重要な除外を、内部用の短い reader contract として定義する。提示された要件の規範的な強さを保持し、禁止事項または前提条件を trade-off に置き換えない。
2. 執筆者側の説明を使う前に、提示された artifact を読む。読者が artifact 自体から復元できる目的、構造、必要な事前知識を推定する。
3. 対応が必要な箇所だけを次のように分類する。
   - `CUT`：読者に必要な固有の意味を追加しない
   - `MERGE`：一箇所にまとめるべき主張、例、接続、結論を繰り返している
   - `MISSING`：文書を理解または利用するために必要な文脈がない
   - `AMBIGUOUS`：重要な推測または不要な読み返しを読者に要求する
   - `PRESERVE`：過度な圧縮によって失われやすい限定、例、境界、証拠を含む
4. 削除後も読者が読後目標を達成できる場合だけ、その箇所を削る。執筆者にしか必要でない内容は推敲より削除を優先し、不完全な説明を複数残すより完全な説明を一つ残す。
5. 提示された主張または手順を理解、実行するために直接必要な不足文脈だけを追加または要求する。不足している値と、新しい運用上の推奨を区別する。役立つ可能性だけを理由に、command、system、validation、rollback、logging、owner、その他の best practice を作らない。ユーザーが実行可能な template を求めない限り、草稿を placeholder で埋めない。提示された手順が、どこで、またはどのように行うかを示さずに何かを read または update するよう求めている場合は、その不足だけを特定して停止し、隣接する前提条件を推測しない。各 `MISSING` 項目を artifact または reader goal に既に存在する対象または行為へ結び付ける。新しい environment、system、record、process を前提条件として追加しない。不足文脈が完了を block すると source またはユーザーが示していない場合は、その帰結を断定しない。
6. reader contract に照らして改稿を確認する。新しい主張を加えていない、不確実性を強めていない、必須項目をすべて保持している、削った前提を読者に再構成させていないことを確認する。
7. 要求された artifact または review mode を返し、事実確認、実装、diff review へ拡張しない。

## 独立した reader の evidence

別の agent がなくても editing workflow を実行できるようにする。独立した読解は orchestration から受け取る入力として扱い、この Skill が所有する操作として扱わない。この workflow から別の agent を start、send、wait、join しない。

orchestration 層は、別 context であることを識別できる reader の結果を提供できる。その reader への入力は次だけを含むべきである。

- artifact または範囲を限定した抜粋
- reader contract
- 必要な出力 label と保持制約

執筆者が期待する削除箇所、疑っている問題、望ましい結論、以前の草稿を作った理由、非公開の採点基準を含めるべきではない。提示された結果は authority ではなく review evidence として扱い、現在の workflow が最終的な改稿と権限確認を担当する。

main session 自身の評価を fresh または independent と表現しない。ユーザーが独立 pass を明示的に求めた場合は、別の reader の結果と観測可能な provenance がすでに提示されている場合だけ、`Independent reader pass: executed.` と報告する。それ以外は `Independent reader pass: not executed.` と報告し、評価または改稿を行わずに停止する。必須の独立 pass を main session の pass へ暗黙に置き換えない。`Independent reader assessment` という見出しまたは表現を使わない。

## 出力契約

依頼が独立 pass を必須とする場合は、他の出力を作る前に independent-reader evidence gate を解決する。別の reader の結果と観測可能な provenance が提示されていない場合は、not-executed status と不足する orchestration input だけを返し、以降の出力 mode へ進まない。

改稿またはファイル編集が許可されている場合は、改稿後の artifact と、意味、構造、不足文脈を変えた重要な判断だけを返す。削除履歴を網羅的に付けない。

review comments だけが許可されている場合は、対応が必要な項目を label、位置、読者を基準にした理由とともに報告する。変更不要の箇所は `KEEP` として列挙せず、省略する。

ユーザーが reader contract を求めた場合、またはその曖昧さが結果へ実質的に影響する場合を除き、reader contract は内部判断に使う。出力の利用または review に影響する場合だけ、未解決の不足文脈、曖昧さ、未検証の提示済み主張を報告する。ユーザーが独立 pass を求めた、または提示された結果が改稿へ影響した場合だけ、independent-reader status を報告する。通常の process metadata としては追加しない。

Skill の invocation を、ファイル編集、文書公開、外部書き込みの権限として扱わない。diff の問題発見には `review-changes`、文章表現の規範には言語固有の writing Skill を使う。どちらも依存関係ではない。
