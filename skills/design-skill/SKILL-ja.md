# Design Skill

## 目的

- 草案を書く前に、再利用可能な Skill が適切な対応か判断する。
- 実装を担当する工程が、責務、選択条件、補助資料、評価に関する判断をやり直さずに適用できる、証拠に基づいた設計を作る。
- 診断、設計、実装を分ける。\
  既存の監査結果は証拠として利用できるが、この Skill は監査結果がなくても使えるものとする。

## 証拠

`references/authoring-guide.md` は、設計に必要な詳細を確認するために使う。

- **Design discovery metadata:** `name` と `description` を作成・修正する場合
- **Separate portable and client-specific layers:** クライアント固有のメタデータや制御が必要な場合
- **Review third-party and executable capabilities:** 第三者由来の資料を改変する場合や、実行可能な補助ファイルを設計する場合
- **Design evaluation before extensive instructions:** 評価の入力、採点、比較、追加検証へ進む条件を定める場合

毎回ガイド全体を読むことを要求せず、該当する節を読む。

利用できる範囲で以下を集める。

- 期待する結果、利用者、クライアント、モデル、失敗の兆候
- 再利用可能な知識や手順の不足を示す、実際の作業例、修正、実行記録、出力
- Skill を使わない場合、または旧版を使った場合の比較基準
- 適用されるローカル指示と配布上の制約
- 隣接する Skill、その `description`、併用時の挙動
- 第三者由来の内容や実行可能な資料を改変する場合の、出所、ライセンス、全ファイル一覧、利用できる機能を通じて処理が行われる経路

適用されるローカル指示は、その範囲で優先すべき指示として扱う。\
同梱のガイドは、ローカル指示が規定していない部分で、他の環境でも使える基準として参照する。\
観測した証拠、推論、前提、未確認事項を区別する。\
文章上の妥当性しか確認できない場合は、実証済みの改善ではなく、静的な仮説として設計を示す。

## 手順

1. 新しい Skill が必要だと仮定せず、期待する能力と、繰り返し発生する失敗または知識の不足を定義する。
2. 代表的な作業と比較基準となる挙動を確認する。\
   エージェントに不足するもの、すでに処理できるもの、繰り返し利用する価値のある修正を特定する。
3. 継続的に参照する指示を設けない、ローカル指示やツールを使う、既存 Skill を更新・統合する、分割する、新設する、といった関連する対応を比較する。
4. 隣接する Skill と配布先の構成を確認する。\
   成果物を選ぶ前に、責務の重複、選択時の競合、コンテキストの消費量、併用時のリスク、第三者への信頼や利用できる機能の境界に関する問題を解消する。
5. 一貫した責務の単位を一つ選ぶ。\
   対象利用者、対象とする作業、除外、入力、出力、失敗時の扱いを定義する。
6. `name` と `description` の案を作る。\
   自動選択に必要な情報をすべて `description` に入れ、選択の競合を防ぐ場合は除外条件も含める。
7. エージェントがすでに知っている一般論を除き、再利用できる内容だけを `SKILL.md`、`references/`、`scripts/`、`assets/`、評価用ファイルへ配置する。\
   他の環境でも使えるメタデータ案は共通の要件に限定し、クライアント固有の追加事項は引き継ぎで別に列挙する。\
   呼び出しの制御、UI、必要なツール、権限の挙動が求める場合だけ拡張を加え、形式上同じファイルへ置く場合は対象クライアントを示して、他のクライアントでも受け付けられることを検証する。\
   すべてを同じ詳細度に固定せず、手順を誤りやすい作業かどうかに応じて指示の自由度を調整する。
8. 作業手順に必要な場合だけ、安全性や権限の境界を定義する。\
   外部の指示、スクリプト、ツール、ファイルシステムへのアクセス、ネットワークへのアクセスが関係する場合は、それらを組み合わせた処理とデータの経路を追跡し、利用可能なら、確実に保証すべき条件をクライアント側で強制できる制御へ移す。\
   特定の見出し構成を強制せず、必要な安全上の性質を保つ。
9. 本文を大量に書く前に評価を設計する。\
   重要な責務、選択条件、安全上の性質、変更した挙動を、起こり得る失敗、シナリオまたは確認、採点方法へ対応付ける。\
   静的検証、対象を絞った回帰確認、実測と反復による調整のどれが妥当かと、次の段階へ進む根拠を示す。\
   選択、比較基準、単独使用、併用、指示への準拠、出力の品質、クライアント、モデルの評価は、関連するリスクを扱う場合だけ含め、すべてに共通するケース数や実行回数を目標にしない。
10. 設計が実際に影響する対象だけを特定し、実装に必要な引き継ぎを作る。\
    この手順では Skill を編集・実装しない。

## 判断基準

- モデルがすでに安定して作業を実行でき、再利用可能な専門知識や手順が不足していない場合は、Skill を作らない。
- 選択条件、出力の要件、リスクの範囲に一貫性を保てる場合は、既存 Skill の更新・統合を優先する。
- 責務をまとめると、選択、読み込み、実行が曖昧になる場合は、新設または分割を優先する。
- 参考資料やスクリプトは、繰り返す再調査を減らす、分野固有の証拠を提供する、誤りやすい操作を検証可能にする場合だけ同梱する。
- 主となる指示は簡潔に保ち、読み込む各節の情報がコンテキストの消費量に見合うようにする。

## 報告に含める情報

固定の提案テンプレートではなく、判断に合う構成を使う。\
以下の情報を含める。

- 推奨する対応と、代替案より適切な理由
- 証拠、前提、未解決の問い
- 責務と選択条件の案
- Skill を推奨する場合のメタデータ案
- 本文と補助資料の配置
- 他の環境でも使えるメタデータと内容、別に列挙したクライアント固有の追加事項、必要な場合は第三者由来の内容の出所に関する要件
- 実装後も保つべき安全性、データの経路、権限に関する性質
- 評価する責務、採点方法、選んだ検証の深さと追加検証へ進む条件、段階的に導入する方針
- 影響する対象と、実装に着手できる引き継ぎ

証拠が、継続的に参照する指示は不要、または別の対応が適切と示す場合は、Skill 案を強制しない。\
ファイル編集、依存追加、リポジトリの方針変更は行わず、実行が許可された実装工程へ引き渡す。
