# Skill を設計する

誰かが Skill を書き始める前に、再利用する Skill が正しい対処かを判断する。\
実装する人が、責務、選ばれる条件、資料について新しく判断しなくても適用できる、証拠に基づく設計を作る。\
出力は設計であり、Skill のファイルは変更しない。\
既存の監査があれば証拠として使えるが、この Skill は監査がなくても使える。

設計に当てはまる [references/authoring-guide.md](references/authoring-guide.md) の節を読む。

- **Design the discovery metadata**: `name` と `description` を作成または修正する場合
- **Write the body**: `SKILL.md` の内容を計画する場合
- **Separate portable and client-specific layers**: 設計にクライアントのメタデータや制御が必要な場合
- **Review third-party and executable capabilities**: 設計が第三者の資料を取り入れる場合や、実行できる資料を含む場合

適用されるローカルの指示は、その範囲で権限を持つ。\
同梱のガイドは、ローカルの指示が何も定めていない部分で使う。

## 作業手順

1. **不足を定める**

   意図する能力と、繰り返し起こる失敗や知識の不足を定める。\
   意図する結果、利用者、クライアント、モデル、失敗のしるしを集める。\
   新しい Skill は、出発点ではなく、考えられる答えの一つとして扱う。

2. **基準となる挙動を調べる**

   代表的な作業、訂正、トレース、出力と、Skill がない場合や以前の版での挙動を調べる。\
   エージェントに欠けているもの、すでにうまくできること、再利用できる訂正を特定する。\
   観測した証拠、推論、前提、不明点を分ける。\
   文章としてのもっともらしさしかない場合は、設計を静的な仮説と記す。\
   不足を証拠とともに示せるか、証拠がないことを示せれば完了とする。

3. **対処を比べる**

   次の対処を比べる。

   - 継続して適用される指示を設けない
   - ローカルの指示やツール
   - 既存の Skill の更新や統合
   - 既存の Skill の分割
   - 新しい Skill

   次の基準を当てはめる。

   - モデルがすでに確実に作業でき、再利用する文脈や手順が欠けていない場合は、Skill を設けない。
   - 選ばれる条件、出力、リスクの範囲がまとまったままの場合は、更新か統合を選ぶ。
   - 両方の責務を持つ一つの Skill では、選ばれ方、読み込み、実行が曖昧になる場合は、新しい Skill か分割を選ぶ。

4. **隣接する Skill を調べる**

   隣接する Skill、その description、一緒に使ったときの振る舞いを調べる。\
   配布の経路と、ローカルの指示を調べる。\
   責務の重なり、競合する選ばれ方、コンテキストの消費、共存のリスクを解消する。\
   第三者の資料や実行できる資料では、出所、ライセンス、ファイルの完全な一覧、機能の経路も解消する。\
   選んだ対処に、未解決の重なりや信頼の境界がなければ完了とする。

5. **責務を定める**

   一つのまとまった責務を選ぶ。\
   その利用者、範囲に入る作業、入力、出力、失敗時の扱いを定める。

6. **メタデータを下書きする**

   ガイドに従って、`name` と `description` を下書きする。\
   選ばれる条件の文脈は、すべて `description` に入れる。\
   選ばれる条件は、隣接する Skill の条件と競合しない程度に具体的にする。

7. **内容を割り当てる**

   エージェントがまだ持っていない、再利用する内容だけを、`SKILL.md`、`references/`、`scripts/`、`assets/` に置く。\
   参照資料やスクリプトを同梱するのは、繰り返しの調べ直しを省く場合、分野の証拠を与える場合、壊れやすい操作を確かめられるようにする場合だけにする。\
   `SKILL.md` は、読み込まれる各節がコンテキストの消費に見合う程度に短く保つ。\
   各手順に完了条件を計画し、各規則はそれを当てはめる手順に置く。\
   指示の自由度は、作業の壊れやすさに合わせる。\
   共通のメタデータは共通の取り決めにとどめ、クライアント固有の追加は分けて挙げる。

8. **安全の範囲を定める**

   安全や許可設定の範囲は、作業手順が必要とする場合だけ定める。\
   外部の指示、スクリプト、ツール、ファイルシステムやネットワークへのアクセスが関わる場合は、組み合わさった経路をたどる。\
   強い保証は、クライアントがそれを強制できる制御を提供している場合、その制御に移す。

9. **引き継ぎを用意する**

   設計が実際に影響する置き場所を特定する。\
   残すコード、構成、安全性の確認を含めて、実装への引き継ぎを用意する。

## 報告

判断に合った構成で、次の項目を含める。

- 推奨する対処と、それが代案より良い理由
- 証拠、前提、未解決の問い
- 責務と、選ばれる条件
- Skill を推奨する場合は、メタデータの下書き
- 内容と資料の割り当て
- 共通のメタデータと内容、それとは分けたクライアント固有の追加
- 第三者の資料についての、出所の要件
- 実装が保たなければならない、安全、データの流れ、許可設定の性質
- 結果の確認と、展開の方針
- 影響を受ける置き場所と、実装への引き継ぎ

継続して適用される指示を設けないことや、別の対処を証拠が支える場合は、Skill の代わりにそれを推奨する。\
ファイルの変更、新しい依存関係、リポジトリの方針の変更は、許可された実装の作業手順が行う。
