# 変更をレビューする

差分が引き起こす問題や、差分によって表に出る問題を見つける。\
各問題を、ほかの人が評価するのに必要な証拠とともに報告する。

## レビューする前に

1. **差分を特定する**

   次のうち、最初に当てはまるものを使う。

   - ユーザーが示した差分、コミット範囲、PR の範囲
   - PR では、その PR のベースとヘッド
   - ローカルの変更では、ステージ済み、未ステージ、関連する未追跡のファイル

   レビューする変更を正確に示せれば完了とする。\
   考えられる二つの範囲でレビューの結果が変わる場合は、ユーザーに尋ねる。\
   差分を取得できない場合は、レビューを実行しなかったことを報告し、足りない入力を示す。

2. **レビュワー向けの情報を集める**

   依頼、PR、リポジトリから、次の項目を集める。

   - 目的と、期待する結果
   - 製品や運用の状況と、その重要度
   - 範囲と対象外
   - 影響を受ける利用者、データ、取り決めと、変更が誰から見えるか
   - 制約と、受け入れたトレードオフ
   - 検証と、不明な点
   - 検知と復旧の手段
   - ユーザーが注意して見てほしい箇所

   各項目に値があるか、`Unknown` と記録されていれば完了とする。\
   重要度や影響の及ぶ範囲が分からない場合は `Unknown` とし、低リスクとはみなさない。

## レビューする

3. **設計をレビューする**

   目的、設計、取り決め、責務の境界、変更されたコードを使うコードから始める。\
   そのうえで、[レビューの観点](#レビューの観点) から、この変更に当てはまる観点を選ぶ。\
   変更のリスクと、レビューする観点を示せれば完了とする。

4. **差分を調べる**

   差分と、その前提を確かめるのに必要な周辺の証拠を読む。\
   この証拠には、仕様、テスト、呼び出し元、スキーマ、似た実装が含まれる。\
   依頼、コメント、仕様にある主張は、コードと確認の結果に照らして確かめる。\
   変更が引き起こす問題や、変更に関係する問題を報告する。

5. **確認を実行する**

   結果によって指摘を裏付けたり退けたりできる場合は、安全で読み取りだけの確認を実行する。\
   作業ツリー、依存関係、外部のシステムは変更しない。\
   実行した確認は、そのコマンドと結果とともに、提案する確認とは分けて記録する。

6. **指摘を書く**

   証拠が裏付け、この変更にとって重要な指摘を、それぞれ [指摘の項目](#指摘の項目) の項目で書く。\
   影響は、証拠が裏付ける範囲だけを書く。\
   起こり得る結果が役に立つが確かめていない場合は、条件付きで書き、`Unconfirmed premises` に加える。\
   各指摘に、ラベル、確信度、当てはまるすべての項目があれば完了とする。

7. **差分全体の再レビューでは、前回の指摘と照らし合わせる**

   この手順は、ユーザーが差分全体の再レビューを求めた場合だけ行う。\
   前回の各指摘を `Resolved` か `Remaining` とし、それ以外の指摘を `New` とする。\
   `New` の指摘には、次のいずれかの発生経緯を付ける。

   - `Fix-induced`: 修正によって生じた。
   - `Newly observable`: 修正によって見えるようになった。
   - `Late-discovered`: 以前から見えていたが、前回のレビューで報告されなかった。

   変更を妨げない `Late-discovered` の指摘は、`note` として報告するか、報告から外す。\
   そうすることで、その指摘が次の修正の繰り返しを始めないようにする。

8. **レビューの結果を報告する**

   次の項目を報告する。

   - 結論と、レビューした差分
   - レビューした範囲と、重要な対象外
   - ラベルと影響の順に並べた指摘
   - 実行した確認と、そのコマンドと結果
   - 提案する確認、確認しなかった部分、残るリスク

   重要な指摘がない場合は、そのことを明記し、同じように範囲、確認、リスクを報告する。\
   仕様についての問いが未解決の場合は、差分の残りをレビューし、その問いを `question` の指摘として報告する。\
   レビューの観点が完了していない場合は、レビューが完了していないことを示す。\
   修正と、指摘への対応の判断は、ユーザーに委ねる。

## レビューの観点

変更にとって重要な観点だけを使う。

**コードと挙動**

- 正確さ、境界値、順序、時刻、丸め、並行処理、エラー処理、データの完全性
- API やスキーマのような外部との取り決め
- 認可、認証、入力の検証、インジェクション、秘密情報や個人情報の露出、安全でない副作用
- 後方互換性、移行、段階的な展開、呼び出し元や似た実装との一貫性
- 代替の経路、再試行、エラーを捕まえて処理を続ける経路: それぞれが現在の失敗を扱い、その結果を観測できる
- 互換のための経路: 現在の利用者、公開済みの挙動、保存されたデータ、移行、切り戻しがそれを必要としているか
- テストの網羅性と質（実装に依存するテストや、モックを使いすぎたテストを含む）
- 影響が具体的な場合の、保守性と性能

**構造**

証拠が具体的な結果を示す場合に、構造の問題を報告する。\
たとえば、規則の重複、一貫しない挙動、到達できない分岐、運用の手間の増加である。\
これは両方の向きに当てはまる。

- 構造が多すぎる: 現在のどの要件も必要としない抽象化、拡張点、設定項目、依存関係、層
- 構造が少なすぎる: 確認された原因を残す、共通の規則を写す、ほかの既知の経路と食い違う局所的な修正

共通の責務や規則があることを証拠が示している場合は、局所的なコードを重複させたほうが短くても、共通化した抽象化を受け入れる。

**文書**

- 実装や基準となる資料と一致する事実
- コマンド、例、リンク、識別子、用語、欠けている情報
- 利用できる場合は、描画、lint、内容の確認

**設定**

- スキーマとパーサーに対する妥当性、優先順位、既定値、環境との相互作用、互換性
- 挙動を変える値と、それに必要な挙動の確認
- 段階的な展開、復旧、秘密情報の扱い、運用への影響

## 指摘の項目

各指摘に、ラベルを一つ付ける。

| ラベル | 意味 |
| --- | --- |
| `must` | マージの前に修正する。証拠が重大なリスクを示し、より小さな対応では足りない。 |
| `should` | 修正を勧める。代わりの案や制約によって判断が変わり得る。 |
| `suggestion` | 変更を妨げない改善 |
| `question` | 次の行動が、明確化や前提の確認である。 |
| `nit` | 小さな、任意の修正 |
| `note` | 対応を必要としない情報 |

`must` と `should` は、好みではなく、証拠のある問題にだけ使う。\
`question` は、前提が確かめられていなくても、起こり得る影響を保つ。

各指摘に、次の項目を書く。

- `Confidence`: `high`、`medium`、`low` のいずれか
- `Finding`: 問題、提案、問い、情報
- `Evidence`: それを裏付ける位置、取り決め、挙動、確認の出力、リポジトリ内の例
- `Impact`: 証拠が裏付ける結果、または確かめていない前提が正しい場合の結果
- `Verification`: 指摘を確かめる、再現する、または退ける方法
- `Unconfirmed premises`: 指摘、その影響、そのラベルが依存する仮定や不明点。\
  ない場合は `none identified`

ラベルを変え得る場合は、次の項目を加える。

- `Exposure and preconditions`: 条件、経路、頻度、影響を受ける人。\
  分からない場合は `Unknown`
- `Criticality and blast radius`: 影響を受ける部分の重要度と、害の広がり
- `Detectability, recovery, and workaround`: 問題を検知し、封じ込め、復旧する方法
- `Remediation cost and trade-offs`: 作業、検証、複雑さ、回帰のリスク、遅れの点での修正の費用

差分全体の再レビューでは、`Re-review state` を加え、`New` の指摘には `New finding origin` も加える。\
`Generalizable check` は、その確認がこの差分の外でも役立つ場合だけ加える。

リスクは、高いか低いかのような順序で、証拠とともに比べる。\
証拠が裏付けるリスクに対して、十分な最小の対応を選ぶ。
