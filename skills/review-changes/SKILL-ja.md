# Review Changes（差分レビュー）

## 目的

- 実効差分が導入または顕在化させる重要な問題を発見し、別の人や Skill がレビューの前提を調べ直さずに評価できる根拠を返す。
- 求める対応、潜在影響、確信度、再レビュー状態を別の軸として扱う。
- 変更目的、対象の重要度と露出、修正のコストとリスクに応じて求める対応を調整し、数値スコアへ還元しない。
- コード、文書、設定を、全差分に同じチェックリストを強制せず、変更内容とリスクに応じた確認方法でレビューする。

## 対象範囲と根拠

レビュー前に実効差分を確定する。

1. 差分、コミット範囲、PR 範囲が明示されていれば、それを使う。
2. PR では、指定された base と head、または PR の実効差分を使う。
3. 対象未指定のローカルな「現在の変更」レビューでは、ステージ済み・未ステージの変更と関連する未追跡ファイルを確認し、含めた範囲を明示する。
4. 複数の解釈でレビュー結果が実質的に変わる場合だけ確認する。差分を取得できない場合は、レビューを実行できなかったと報告する。

適用されるリポジトリ指示と、変更意図を理解するのに必要な周辺根拠を読む。
差分に応じて、仕様、テスト、呼び出し元、スキーマ、外部仕様、同種の実装、リポジトリ内の先例を確認する。根拠が差分外にあってもよいが、指摘はレビュー対象の変更が引き起こす、または変更に関係する問題でなければならない。無関係なリポジトリ全体監査へ広げない。

ユーザーが示した主張、コメント、外部仕様は結論ではなく検証対象の根拠として扱う。観測済み挙動、静的推論、前提、未知を区別する。

利用可能な場合は、レビューの前提情報を使う。目的と期待結果、対象や運用上の重要度、対象範囲と対象外、影響する利用者・データ・仕様と変更の露出、制約と採用済みの得失、検証結果と不明点、検知・復旧の仕組み、指定された確認の重点が対象になる。重要な根拠の状態は `Observed`、`Reported`、`Inferred`、`Unknown`、`Conflicting` のまま保持する。重要度や露出が不明なら `Unknown` とし、低リスクの根拠にしない。

## 手順

1. 実効差分、意図する挙動、レビューの前提情報、レビュー範囲、重要な除外範囲を示す。目的、重要度、露出が判断に重要でも利用できない場合は、値を作らず不明として扱う。
2. 行単位の詳細より先に、変更目的、設計、守るべき仕様、責務の境界、影響する利用側を確認する。変更に伴うリスクを特定し、全観点を機械的に適用せず、必要なレビュー観点を選ぶ。
3. 差分と、変更の前提・仕様・統合点・提示されたレビューの前提情報を確認するために必要な最小限の周辺根拠を調べる。
4. 結果が指摘を実質的に強める、弱める、または反証できる場合、安全で関連する非変更型の確認を実行する。レビュー中に依存を導入したり、tracked file を変更したり、外部へ書き込んだりしない。
5. 実行した確認と結果を、提案だけの確認から分ける。利用不能または意図的に除外した確認は未実行として記録する。
6. 根拠で裏付けられた重要な指摘をすべて報告する。記載する影響は、提示済みまたは確認済みの仕様、挙動、実行経路が裏付ける結果に限定し、指摘を深刻に見せるためだけに未確認の後続処理を想定しない。後続処理で重要な結果が生じ得ても未確認なら、条件付きで記述し、その前提を `Unconfirmed premises` に記録する。空の指摘一覧を避けるためだけに好み、`nit`、`note` を追加しない。
7. 求める対応を変え得る場合は、指摘の露出と前提、対象の重要度と影響範囲、検知と復旧、修正に伴う費用や得失を整理する。根拠のない数値スコアではなく、根拠に基づいて比較し、確認できたリスクを十分に扱える最も低コストな対応を優先する。
8. 各指摘に所定のラベルと確信度を一つずつ付ける。指摘、記載した影響、リスクの判断材料、求める対応が依存する前提や不明点はすべて `Unconfirmed premises` に記録し、依存する点がない場合だけ `none identified` とする。未確認前提によって求める対応が `question` でも、大きな潜在影響は保持する。
9. 明示的な全面再レビューでは、前回指摘を `Resolved` / `Remaining` / `New` に整理する。すべての `New` を `Fix-induced`、`Newly observable`、`Late-discovered` のいずれかへ分類する。どの由来でも重要な問題は報告する。以前から観測可能だった `Late-discovered` が単独では修正を要しない場合、新たな修正の繰り返しを始めず、対応を求める指摘から除外するか、有用な場合だけ対応不要の `note` として要約する。
10. レビュー範囲、実行した確認、未確認範囲、残るリスクをまとめる。重要なレビュー観点が未完了なら、承認や安全性を暗示せずレビュー未完了と示す。

## レビュー観点

変更に関係する観点だけを使う。

### コードと挙動

- 正しさ、境界値、順序、時刻、丸め、並行性、エラー処理、データ整合性
- API やスキーマなどが保証する挙動と内部実装上の制約
- 認可、認証、入力検証、インジェクション、秘密情報や個人情報の露出、危険な副作用
- 後方互換性、移行、段階的な反映、呼び出し元や同種の実装との整合
- フォールバック、再試行、例外捕捉後の処理継続が、現在の失敗条件に対応し、確認できた原因を隠さず、必要な復旧後の状態を観測・検証できるか
- 互換経路が、既知の利用側、公開済みの挙動、永続データ、移行、異なるバージョンが混在する反映、ロールバックによって現在必要とされるか。未公開というだけで互換性が不要とみなさない
- テスト範囲と、実装への過度な依存や過剰なモックを含むテスト品質
- 個人の好みや推測的な最適化ではなく、具体的な影響がある保守性と性能
- 現在の要件や観測済みのリスクでは保守・運用上の費用を正当化できない抽象化、拡張点、設定項目、依存、互換経路、設計上の層
- 差分量を減らす一方で、確認済みの原因を残す、共有規則を重複させる、確立済みの責務の境界を迂回する、既知の経路間で挙動を不整合にする、既知の追随修正を必要とする局所的な修正

過剰な複雑性と狭すぎる修正は、規則の重複、挙動の不整合、到達不能な分岐、追加の運用負担、既知の追随変更など、具体的な結果を根拠が示す場合だけ指摘する。設計上の好みだけで報告しない。
一方、現在の根拠が共有責務、守るべき共通条件、仕様を示し、変更が不要な拡張点や具体的な費用を追加していない場合、局所的に重複したコードの方が短いという理由だけで抽象化や統合を問題視しない。

### 文書

- 事実の正しさと、実装または正本との整合
- コマンド、例、リンク、識別子、用語、読者に見える欠落
- 利用可能な表示確認、lint、同じ入力から同じ結果が得られる内容検査

### 設定

- スキーマとパーサーの妥当性、設定の優先順位、既定値、環境との相互作用、互換性
- 静的な値が観測可能な挙動を変え、挙動確認が必要か
- 段階的な反映、復旧、秘密情報の扱い、運用上の影響

## 指摘契約

- `Label`
  - `must`: 重要なリスクが十分に支持され、それを十分に扱える低コストな対応がなく、マージ前の修正が必要
  - `should`: 原則修正推奨。代替案や制約を相談できる
  - `suggestion`: マージを止めない改善
  - `question`: 次の行動が前提や意図の確認
  - `nit`: 軽微で任意の修正
  - `note`: 対応不要の情報
- `Confidence`: `high` / `medium` / `low`
- `Finding`: 具体的な問題、提案、質問、補足
- `Evidence`: 根拠となる位置、契約、挙動、確認結果、リポジトリ内の先例
- `Impact`: 利用可能な根拠が裏付ける影響。明示した未確認の前提がある場合は、その前提が確認されたときに生じること。未確認の後続処理を想定しない
- `Exposure and preconditions`: 求める対応に重要な場合、根拠が裏付ける条件、到達可能な経路、頻度、影響する利用者の範囲。重要でも利用できない場合は `Unknown`
- `Criticality and blast radius`: 求める対応に重要な場合、影響する製品、ツール、データ、仕様、運用の重要度と、裏付けられた影響範囲
- `Detectability, recovery, and workaround`: 求める対応に重要な場合、適用可能な検知、封じ込め、復旧、ロールバック、実用的な回避策の根拠
- `Remediation cost and trade-offs`: 求める対応に重要な場合、現在の根拠が裏付ける実装、検証、複雑性、回帰、遅延、保守に伴う重要な費用
- `Verification`: 確認、再現、反証の方法
- `Unconfirmed premises`: 指摘、記載した影響、リスクの判断材料、求める対応が依存する前提や不明点。該当しない場合は `none identified` とし、未確認範囲や残るリスクと照合する。根拠、影響、確認方法でこの項目を代用しない
- `Re-review state`: 明示的な全面再レビューだけで `Resolved`、`Remaining`、`New`
- `New finding origin`: `New` の指摘だけで `Fix-induced`、`Newly observable`、`Late-discovered`
- `Generalizable check`: 今回の差分を超えて再利用できる学びがある場合だけ

`Must-fix`、`Should-fix`、`Nice-to-have` は互換入力として受け取り、`must`、`should`、`suggestion` または `nit` へ正規化する。好みだけの指摘に `must` や `should` を使わない。`question` でも潜在影響は大きくなり得るため、前提が未確認であることだけを理由に影響を消さない。

## 出力契約

レビュー状態に応じて構成を調整し、空の節は出力しない。

完了したレビューには次を含める。

- 結論と実効差分
- レビュー範囲と重要な除外範囲
- 求める対応と影響順に並べた指摘
- 実行したコマンドまたは確認方法と実際の結果
- 提案する確認、未確認範囲、残るリスク

簡潔に報告する場合も、各指摘の `Unconfirmed premises` を独立した項目として示す。確信度、リスクの判断材料、残るリスクの記述から読者に推測させない。

重要な指摘がない場合は、そのことを明記し、レビュー範囲、実行した確認、未確認範囲、残るリスクも報告する。裸の `LGTM` を返したり、軽微なコメントを捏造したりしない。

差分を取得できない、または結果が実質的に異なる解釈を解消できない場合は、レビューを実行できなかったと示し、不足する入力を特定する。「問題なし」として扱わない。

## 関連ワークフローとの境界

- 既存指摘を評価し、対応するかどうかと対応方針を決める場合は `triage-review-feedback` を使う。
- 一つ以上の特定済み指摘に対する通常の修正後再レビューには、既定で `validate-fix` を使う。
- 指摘ごとのコメント案には、指摘の評価、状態、対応の決定が明示済みの場合だけ `draft-review-comments` を使う。\
  通常は `triage-review-feedback` がそれらを提供し、このレビュー結果だけでは対応を求めるコメント案の作成を認めない。
- 重要な指摘がなく、PR 全体へのコメント案またはレビュー要約が求められた場合は、レビュー全体の結論、確認範囲、実施した確認、重要な制約を `draft-review-comments` に渡す。\
  指摘ごとの評価や対応の決定を捏造せず、レビュー操作を選んだりコメントを投稿したりしない。
- 問題発見を伴わない説明的な差分要約には `summarize-changes` を使う。

修正を実装したり、指摘への最終的な対応を決めたりしない。未解決の仕様質問が差分の残りをレビューする妨げにならない場合、全体を止めず `question` として報告する。別エージェントやサブエージェントは既定で使わない。
