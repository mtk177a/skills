# 変更を実装する

変更を小さな単位で行い、各単位を検証してから次の単位に進む。

## 編集する前に

1. **範囲を書き出す**

   期待する挙動、変更してよい部分、変えてはいけない部分を書き出す。\
   各項目が、依頼か合意した計画から来ているか、ユーザーが確認したものであれば完了とする。\
   足りない項目によって実装が変わり得る場合は、状態を `Blocked` として止まり、その項目を尋ねる。

2. **高リスクの変更では、許可と回復の手段を確かめる**

   データの削除や移行、依存関係の追加、認証、認証情報、権限、暗号処理の変更を含む場合は、次の 2 つを確かめる。

   - ユーザーが、この操作とこの範囲を許可している。
   - 失敗したときに回復する手段がある。

   両方を確かめられたら完了とする。\
   どちらかが足りない場合は、編集する前に状態を `Blocked` として止まり、足りないものを報告する。

3. **テストリストを作る**

   変更によって追加または変更される挙動ごとに、短い 1 行を書く。\
   挙動を変えない変更では、結果を示す確認を書く。\
   期待する挙動や結果のそれぞれに行があれば完了とする。

## 1 単位ずつ進める

テストリストから項目を一つ選び、次の 2 つのサイクルのどちらかを使う。

### TDD のサイクル

公開されたインターフェースで行う速いテストが、変更の前に期待した理由で失敗し得る場合に使う。

1. **Red**

   項目のテストを一つ書いて実行する。\
   テストが失敗し、その失敗が期待する挙動の欠如を示していれば完了とする。

2. **Green**

   テストを通す最小の変更を行う。\
   一時的な単純な実装でもよい。\
   新しいテストと、ほかの焦点を絞ったテストが通れば完了とする。

3. **Refactor**

   このサイクルで書いたか変更したコードとテストを、名前や重複などの点で改善する。\
   小さな改善ごとにテストを実行する。\
   テストが通り、このサイクルのコードが明確になれば完了とする。

4. **テストリストを更新する**

   項目を完了にし、見つかった新しい項目を追加する。

テストは次のように書く。

- 公開されたインターフェースを通して挙動を確かめる。\
  そうすれば、内部の構造が変わってもテストは通る。
- 期待値は、仕様や既知の例から得る。\
  コードと同じ計算で求めない。
- テストダブルに置き換えるのは、ネットワークや時計のような外部の依存だけにする。

実装と有効なテストが食い違う場合は、実装を変える。\
テストを変えるのは、期待する挙動が変わった場合だけにする。

TDD のリズムと、よくある誤りについては、`references/tdd_twada.md` を読む。

### 確認のサイクル

文書、メタデータ、生成された出力、挙動を保つリファクタリングには、このサイクルを使う。\
役に立つテストに、大がかりな準備、多くのモック、遅い E2E の基盤、本番にしかない状態が必要な場合にも使う。\
主にモックや今の実装を確かめているだけのテストは、最も近い役に立つ確認より劣る。

1. 比べるのに役立つ場合は、現在の結果を記録する。

2. 変更を行う。

3. 結果を示す確認を実行する。\
   たとえば次のいずれかを使う。

   - 変更の前後での既存のテスト
   - パーサーやスキーマによる検証、lint、フォーマットの確認
   - dry run、ビルド、描画
   - 自動の確認がない場合は、注意深い目視の確認

確認が期待する結果を示せば完了とする。

## 計画が合わなくなったとき

- 必要な変更が、変更してよい部分より大きい場合は、止まる。\
  その証拠と、必要な範囲を報告する。
- モジュールの分割のような、より大きな構造の変更が必要な場合は、別の変更として報告する。
- 確認された原因を修正する。\
  代替の経路や緩和策を加えた場合は、それを始動させる条件とともに、緩和策として報告する。
- 同じ仮説での 2 回の試行が失敗し、新しい証拠が得られなかった場合は、試行を止める。\
  次の編集の前に、仮説を変えるか、足りない入力を報告する。

## 終える

1. **回帰の確認を実行する**

   影響を受ける範囲全体について、回帰の確認を実行する。\
   確認が通るか、失敗をそれぞれ記録したら完了とする。

2. **結果を報告する**

   次の項目を報告する。

   - 状態: `Done`、`In progress`、`Blocked` のいずれか
   - 変更したファイル
   - テストリストの各項目について、テストまたは確認、変更前の結果、変更後の結果
   - 実行しなかった確認と、その理由
   - 残るリスク
   - `Blocked` の場合は、足りない入力と、変更しなかった部分

3. **`Done` の場合は、レビュワー向けの情報を加える**

   レビュワーが必要とする情報を、次の表の形で加える。\
   当てはまる行だけを含める。

   | 項目 | 内容 |
   | --- | --- |
   | Objective（目的） | 目的と結果 |
   | Usage context（利用状況） | 製品や運用の状況と、その重要度 |
   | Scope（範囲） | 実際の範囲と対象外 |
   | Impact（影響） | 影響を受ける利用者、データ、取り決め |
   | Decision constraints（判断の制約） | 制約と、受け入れたトレードオフ |
   | Verification（検証） | 検証と、不明な点 |
   | Controls（対策） | 検知と復旧の手段 |
   | Review（レビューの重点） | レビュワーが注意して見るべき箇所 |
