# Implement Changes（実装）

## 目的

- 承認済みで十分に明確な変更を、小さくレビューしやすい作業単位で適用する。
- すべての変更に一つの開発手法を強制せず、期待結果と利用可能な根拠から検証方法を選ぶ。
- 実行済みの確認、未確認範囲、残存リスクを区別できる根拠を残して完了する。

## 入力と着手条件

利用できるものを集める:

- 承認済みの目的、期待動作、対象範囲、対象外、停止条件
- `design-changes` または別の承認済み実装引き継ぎ
- 利用可能な場合は、レビュー担当者に渡す予定の情報。製品や運用上の重要度、影響を受ける利用者・データ・API の入出力仕様やデータ形式、互換性などの要件、影響の及ぶ範囲、採用済みのトレードオフ、検知・復旧手段、根拠の状態（`Observed` / `Reported` / `Inferred` / `Unknown` / `Conflicting`）、レビューで重点的に確認する点を含む
- 該当する場合、必要な変更範囲を裏付ける合意済みの診断または別の根拠
- 対象ファイル、リポジトリ指示、既存挙動、影響を受ける利用者
- 局所確認、広い回帰確認コマンド、環境上の制約
- 依存追加、破壊的変更、移行、認証、認可、認証情報、権限、暗号処理に関する承認と管理策

`design-changes` の出力は必須ではない。依頼と既存実装から低影響で局所的な詳細は補ってよいが、要件、権限、リスク許容を作り出してはならない。不足が実装を実質的に変え得る場合は `Blocked` として止まる。

上流のレビュー結果が現在の応答形式を使う場合は、承認済みの `Act now` 作業だけを実装する。旧形式の後続判断では、技術的な評価を推測せず、`accept` を `Act now`、`defer` を `Defer`、`reject` を `No action` に読み替える。引き継ぎに含まれるだけの `Defer` や `No action` の作業は実装しない。

## 手順

1. 編集前に、目的、承認、着手条件、対象範囲、対象外、停止条件を確認する。
2. 高リスク変更では、具体的な操作と対象範囲、必要な管理策、残るリスク、実行権限が実装に進める状態かを確認する。不十分なら編集前に止まり、不足する対象、根拠、管理策、復旧方法、リスク受容、承認判断を特定する。利用可能なら `assess-risky-change-readiness` に準備状況の判断を任意で引き継げるが、停止報告はこの Skill 単体で成立させる。
3. 関連実装と指示を確認する。計画した作業単位の全体が、合意済みの一貫した変更範囲を扱うことを確認し、差分を減らすことだけを理由に承認済みの構造的修正を局所修正へ縮小しない。変更を小さな作業単位へ分け、それぞれに期待結果と検証方法を割り当てる。
4. 作業単位を一つ選ぶ。後述の基準から検証方式を決め、選択理由を記録する。
5. TDD を使う作業単位では:
   - 局所テストを一つ作成または更新する
   - 実行し、意図した理由で失敗することを確認する（Red）
   - 承認済みの一貫した変更範囲内で、通過させる最も単純な実装変更を行う（Green）
   - テストが通った状態でのみリファクタリングする
6. TDD を使わない作業単位では:
   - 有用な場合は比較基準または変更前の観測を残す
   - 承認済みの一貫した変更範囲内で最も単純な変更を行う
   - 選択した再現可能な確認または目視確認を実行する
   - Red を作るためだけに無関係な失敗を作らない
7. 新しい根拠と、実際にレビュー担当者へ渡す情報を記録する。\
   計画した目的・範囲・影響する変更範囲・トレードオフ・検証・復旧手段・レビューで重点的に確認する点との差異も記録し、残る作業単位を更新する。\
   局所修正では確認済みの原因、共有規則、確立済みの責務範囲、既知の影響経路が未解決になると判明した場合、回避策を追加しない。\
   必要な一貫した変更範囲が承認済みの範囲を超える場合は停止し、その根拠と必要な範囲の判断を報告する。\
   依存関係、テスト方針、リスクの実質的な変更も、作業を広げる前に止める。\
   復旧処理や緩和策を実装する際は、その効果と原因修正を区別する。\
   代替経路や復旧経路を追加する場合は、現在の失敗条件、発動条件、復旧後に必要な状態、不正な結果を検知できる確認方法を示す。\
   症状が消えただけで原因を解消したと扱わない。\
   現在の利用者、データ、配備、ロールバックに必要な復旧処理・エラー処理・互換性は維持し、過去に存在したことや将来役立つかもしれないことだけを理由に経路を残さない。
8. 実装試行とテスト実行を分けて記録する。同じ仮説のまま実質的に同じ試行が新しい根拠なしに2回失敗した場合は、同等の3回目の編集前に止まる。失敗した仮説と、構造的に異なる分岐または不足する入力を一つ記録する。
9. 各作業単位の後に局所確認を実行する。完了報告前に、影響範囲で利用可能な、より広い関連回帰確認を実行する。存在しない、実行できない、意図的に除外した確認は記録し、通過したものとして扱わない。
10. 後述の報告要件に従って最終状態を報告する。

## 検証方式の選び方

次のすべてを満たす場合は、TDD を既定とする:

- 観測可能な挙動を変更する
- 期待結果を局所的な自動確認で表現できる
- 実装前に意味のある失敗を確認できる
- その確認の作成と実行が作業単位に対して現実的である

ファイル拡張子だけで判断しない。\
観測可能な挙動に影響する設定変更には TDD が適する場合がある。\
一方、文書、静的なメタデータ、スキーマだけの設定、生成物、挙動を保つリファクタリングには、次のような方法が適する場合がある:

- 変更前後の既存テスト
- 構文解析またはスキーマの検証
- lint または書式の確認
- ドライラン、描画、ビルド、利用側での確認
- 再現可能な差分または不変条件の確認
- 自動化された判定方法がない場合の局所的な目視確認

TDD を適用しない場合は、理由と代替根拠を明示する。TDD を選んだ場合は、具体的なサイクルを `references/tdd_twada.md` で確認する。

## 報告契約

依頼に合わせて表現を変え、空の見出しは出さない。常に次を含める:

- 状態: `Blocked`、`In progress`、`Done`
- 承認済み範囲、作業単位、期待結果、実際の変更ファイル
- 完了した作業単位ごとの検証方法と、それが適する理由
- 変更理由と、レビューまたは検証に必要な引き継ぎ

`Blocked` では次を含める:

- 停止理由と根拠
- 不足する情報、権限、制御
- 変更しなかった範囲
- 次に必要な判断または構造的に異なる確認

`Done` では次を含める:

- 実際に実行した局所確認と広い確認、そのコマンドと結果
- 未実行の確認と未確認事項
- 正確性、安全性、保守性に関して残るリスク
- 関連する、レビュー担当者に渡す実際の情報。目的と結果、製品や運用の状況と重要度、実際の範囲と対象外、影響を受ける利用者・データ・API の入出力仕様やデータ形式、互換性などの要件と影響の及ぶ範囲、制約と採用済みのトレードオフ、検証と未確認事項、検知・復旧手段、レビューで重点的に確認する点、計画との重要な差異を含む。無関係な項目は省き、重要な未確認事項は残す
- 結果を判断するために必要なユーザー向け説明ポイント

## 境界

- 対象範囲と権限が十分であることを確認する前に編集しない。
- 変更を通すためだけに、有効なテストを削除または弱体化しない。
- 意味のある失敗テストが存在しない場合に Red → Green を強制しない。
- テストの再観測を実装失敗の反復として扱わない。
- 新しい根拠または異なる仮説なしに、同じ3回目の試行を続けない。
- 未実行の確認を通過したと主張せず、根拠より広い安全性を示唆しない。
- 合意済みの原因または既知の影響経路を未解決にする場合、承認済みの構造的修正をより小さな局所修正へ置き換えない。
- 承認済みの成果または合意済みの設計に必要でない抽象化、汎用化、互換経路、無関係なリファクタリングを追加しない。
- 対象範囲の実質的拡大、依存追加、合意済みテスト方針の変更、未承認の破壊的・高リスク操作の前に確認する。
- 別エージェントやサブエージェントを既定で使わない。関連 Skill がなくても、この Skill 単体で使えるようにする。
