# 日本語表現の判断基準と例

この reference は禁止語表ではない。
注意する表現が文章の意味を正確に伝えているかを確認し、必要な場合だけ文脈に合う形へ整える。

## 判断の順序

1. その分野や媒体で定着した用法か確認する。
2. その語が実際の動作、状態、条件、結果を正確に表しているか確認する。
3. 引用、正式名称、UI、コード、設定、識別子、検索に必要な原語ではないか確認する。
4. 読者が別の意味を補わなければ理解できない場合は、具体化または言い換えを検討する。
5. 言い換えによって正確さ、簡潔さ、既存文体が損なわれる場合は元の表現を維持する。

## 保護対象と Markdown

URL、パス、コード、コマンド、設定キー、識別子、正式名称、引用、検索に必要な原語は、説明語と分けて扱う。

コードスパン、コードブロック、リンク先、見出し、リスト、表、引用などの Markdown 構文は、文章を自然にする目的だけでは変更しない。

リンクの表示文字列を整える場合も、リンク先、アンカー、パス、識別子との対応を保つ。

保護対象を変更する依頼が明示されている場合は、その対象と範囲を確認し、指定されていない部分へ変更を広げない。

## 最終成果物の再点検

書き換えを完了したら、修正前の文章を部分的に確認するのではなく、完成した文章全体を新しい入力として読み直す。

最終成果物では、修正前に確認した主体、動作、条件、結果、確度、範囲と照合し、条件の消失、断定への変化、対象範囲の拡大や縮小がないか確認する。

候補となる英語や混在表現をもう一度拾い、新たに導入した表現、用語の揺れ、保護対象、Markdown 構文の変化がないか確認する。

長い文章では同じ語や抽象表現の集中による意味の偏りを確認する。

複数の関連文書が同じ依頼に含まれる場合だけ、文書間で共有すると決めた用語と意味を照合する。

## 見直す傾向

### 原語に固定した訳語を割り当てている

- **兆候**：`break`、`fail`、`ignore`、`support` などに、文脈を問わず同じ日本語を割り当てている。
- **確認すること**：停止、例外、互換性の喪失、不整合、未処理、対象環境への対応など、実際に起きることを特定する。
- **維持できる場合**：「ビルドが失敗する」「後方互換性が壊れる」のように、分野で意味が共有され、対象も明確な場合。
- **例**：処理を完了できない、例外を送出する、互換性が失われる、設定を処理に使用しない、Windows に対応する。

### 他言語の名詞化や主語構造を残している

- **兆候**：「この方法は性能の改善を提供する」のように、他言語の名詞化や主語構造を保っている。
- **確認すること**：誰かが何かを提供するのか、処理の結果として状態が変わるのかを確認する。
- **維持できる場合**：サービス、API、組織などが実際に機能や情報を提供する場合。
- **例**：この方法により性能が改善する、この変更で処理時間を短縮できる、この API は監査ログを提供する。

### 一般的な説明語を英語のまま使っている

- **兆候**：日本語で意味を保てる形容詞、抽象名詞、説明用ラベルを英語のまま助詞や動詞へ接続している。
- **確認すること**：原語が正確さ、参照、検索に必要なのか、単に説明のために使われているのかを確認する。
- **維持できる場合**：製品名、正式な機能名、コード、設定キー、識別子、規格名、定着した専門用語、原語そのものを論じる場合。
- **例**：`deterministic` のように日本語化すると技術的な性質を失い得る語は、表現別の判断例に従う。

必要な原語でも読者に未知と考えられる場合は、初出時に短く説明し、その後は日本語または定着した表記で通す。

### 抽象語や比喩が具体的な対象を隠している

- **兆候**：「核心」「土台」「主役」「入口」「線引き」などが、説明対象を示さずに重要さや関係だけを表している。
- **確認すること**：原因、前提、主要な処理、開始地点、判断基準など、実際に指す対象を確認する。
- **維持できる場合**：対象が明確で、比喩が文章の理解や調子に必要な場合。
- **例**：主要因、前提条件、中心となる処理、最初の手順、責任範囲、判断基準。

### 口語的・比喩的な動詞が操作を曖昧にしている

- **兆候**：「素通りする」「潰す」「踏み込む」「塞ぐ」「溶かす」「逃がす」「倒す」など、複数の操作や結果を表し得る動詞を使っている。
- **確認すること**：検査を受けない、候補を除外する、詳しく検討する、通信を遮断する、資源を消費するなど、対象の操作を確認する。
- **維持できる場合**：会話、ブログ、分野内の慣用表現として意味が明確な場合。
- **例**：検証を受けない、原因候補から除外する、検討範囲に含める、脆弱性を修正する、時間を費やす、安全になる設定を選ぶ。

### 同種の抽象表現が短い範囲に集中している

- **兆候**：個々には適切な抽象語、比喩、一般的な説明句が短い範囲に重なり、対象の具体的な情報が薄くなっている。
- **確認すること**：各文が新しい対象、動作、条件、結果を伝えているか確認する。
- **維持できる場合**：具体化しても情報が増えない場合や、変更後の方が冗長になる場合。
- **例**：同じ種類の表現が重なっていても、禁止語として一律に削らず、文章全体の分布を見直す。

## 表現別の判断例

### `deterministic`

- **曖昧になる点**：決定性を表す技術用語なのか、人手によらず定型的に処理することを表しているのかが分からない。
- **確認すること**：同じ入力から同じ結果を得られる性質を指しているか確認する。
- **維持できる場合**：日本語化すると決定性という技術的な性質を失う場合。
- **意味に応じた表現例**：原語を維持するか、「同じ入力から同じ結果を得られる方法で検出する」のように決定性を具体化する。

「機械的に検出する」は、決定性ではなく、人手によらず定型的に処理する意味を表す非技術的な文脈に限る。

### 契約

- **曖昧になる点**：法的な合意や当事者間の約束を指すのか、要件、仕様、保証する挙動、入出力条件、互換性、責任分担などをまとめて指すのかが分からない。
- **確認すること**：法的な契約を指すのか、名前の付いた技術概念や定義済みの用語を指すのか、単に複数の要件や挙動をまとめているのかを確認する。
- **維持できる場合**：法的な契約を指す場合や、Design by Contract、Code Contracts、contract testing など、分野や製品で定着した用語そのものを指す場合。
- **意味に応じた表現例**：API が保証する挙動、入出力の要件、受け入れ条件、互換性の要件、公開仕様、責任分担。

API に関する文章であることだけを理由に、「この API の契約」や「API の契約」を維持しない。
単に複数の条件をまとめている場合は、成功時に返す値、受け付ける入力、互換性を保つ条件など、その箇所で必要な意味を直接示す。
`API contract` や `data contract` などの原語は、その語自体が定義または引用され、参照や検索に必要な場合に維持できるが、日本語の「API の契約」へ機械的に訳さない。
「契約」を残すために、当事者、違反、強制力など、元の内容にない法的な比喩を補わない。

### ゲート、門

- **曖昧になる点**：開始地点や入口を指すのか、前提条件、自動検査、人による承認、続行可否の判断、実行やアクセスの制御を指すのかが分からない。
- **確認すること**：何を、誰またはどの処理が確認し、結果によって何の開始、続行、実行、アクセスを認めるかを確認する。
- **維持できる場合**：Quality Gate、論理ゲート、量子ゲート、製品やパイプラインで正式に定義されたゲートなど、固有または定着した用語として使う場合。
- **意味に応じた表現例**：入口、前提条件、自動検査、承認、判断段階、通過条件、実行条件、アクセス制御。

「契約」が満たすべき要件や保証する挙動を表すのに対し、「ゲート」はその条件を確認し、先へ進めるかを決める箇所や仕組みを表すことがある。
単なる開始地点や利用経路には「入口」を使えるが、通過条件や続行可否の判定がある場合は、その条件、確認、承認、制御のいずれを指すのか示す。
物理的な門や、比喩を意図した文章まで一律に言い換えない。

### 静かに壊れる、静かに失敗する

- **曖昧になる点**：「静か」が、通知、記録、例外、処理継続のどれを表すのか分からない。
- **確認すること**：何が起きず、利用者や呼び出し元から何を観測できないのかを確認する。
- **維持できる場合**：比喩として意図され、直後に具体的な挙動が説明される場合。
- **意味に応じた表現例**：例外を送出せずに失敗する、エラーを返さない、ログに記録されない、不整合を検知しないまま処理を続ける。

### 黙って無視される

- **曖昧になる点**：入力がどの段階まで処理され、何が通知されないのか分からない。
- **確認すること**：構文解析、検証、保存、実行のどこで入力が使われなくなるのかを確認する。
- **維持できる場合**：会話的な説明で、対象と結果が直前の文脈から明確な場合。
- **意味に応じた表現例**：警告なく無視する、設定値は読み込むが処理には使用しない、未対応の項目を保存せず処理を続ける。

### 地味に効く、効いてくる

- **曖昧になる点**：影響を受ける対象、方向、条件が示されていない。
- **確認すること**：性能、遅延、エラー率、保守費用、作業時間の何が、どの条件でどう変わるかを確認する。
- **維持できる場合**：会話や随筆で評価の細部をあえて省く場合。
- **意味に応じた表現例**：入力が増えるほど遅延への影響が大きくなる、保守に必要な作業を減らす、測定では処理時間が約一割短くなった。

### 正本

- **曖昧になる点**：`source of truth` に対応させただけなのか、正式な文書管理上の正本、定義済みの用語、同期や更新の基準を指しているのかが分からない。
- **確認すること**：正式な効力を持つ文書なのか、法的・文書管理上の責任を持つ記録なのか、公式版や更新の基準なのか、単なる翻訳元・参照元なのかを確認する。
- **維持できる場合**：文書管理、契約、記録管理上の正式な用語として使われている場合、本文で「正本」と定義されている場合、または「正本」という語自体を引用・検討している場合。
- **維持しない場合**：英語文書を翻訳するときの元資料、比較する参照資料、仕様を読むための参照先を表すだけの場合。
- **意味に応じた表現例**：翻訳元、参照元、英語版、基準となる仕様、公式版、正式な管理元、更新内容を反映する基準。
- **注意点**：原文に唯一性や排他性がない場合、「唯一の参照元」などの意味を追加しない。

「英語正本を参照して翻訳する」のように翻訳関係だけを表す場合は、「英語の原文を参照して翻訳する」や「英語版を基準に翻訳する」など、確認できる関係を直接示す。

「このリポジトリを正本とする」のように管理責任や更新基準を表す場合も、必要に応じて「公開スキーマの基準とする」「このリポジトリの内容を基準に反映する」など、実際の管理関係を具体化する。

## 文脈に適合するなら維持する表現

次の表現には、日本語の技術文書で定着した用法がある。
AI の出力に多いという理由だけで変更しない。

- 実測
- 照合
- 見落とす
- 断定
- 取り違える
- 原因を切り分ける
- 要点
- 素朴な実装
- **既定値**：`初期値` とは異なる概念を指すことがあるため、表面的な読みやすさを理由に置き換えない。
