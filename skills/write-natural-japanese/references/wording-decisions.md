# 日本語表現の判断基準と例

この資料は、表現が文脈の意味を正確に伝えているかを判断し、必要な場合に整えるための基準と例を示す。\
語ごとに禁止する表としてではなく、判断の基準として使う。

## 判断の順序

1. その分野や媒体で定着した用法かを確かめる。
2. その表現が、実際の動作、状態、条件、結果を正確に表しているかを確かめる。
3. 引用、正式名称、UI、コード、設定、識別子、検索に必要な原語ではないかを確かめる。
4. 読者が別の意味を補わなければ理解できない場合は、具体化するか言い換えることを検討する。
5. 言い換えによって、正確さ、簡潔さ、既存の文体が損なわれる場合は、元の表現を保つ。

## 説明文と正確な文字列を区別する

同じ概念でも、説明に使う表現と、正確に保つ文字列では、扱いが異なる。

- **一般的な説明の表現**: 意味を保てるなら、文脈に合う日本語にしてよい。\
  定義文では、説明する対象を主語として残す。
- **識別子**: API のメソッド名だけでなく、関数名、変数名、設定キー、コマンドなども、正確な文字列として保つ。
- **画面の表示と正式名称**: 読者が実際に参照する文字列を保つ。\
  検索や参照に原語が必要な場合は、説明の表現と併記してよい。

### 対照例: storage state

| 役割 | 元の文 | 完成文の例 |
| --- | --- | --- |
| 一般的な説明 | 一般的な説明として storage state は保存された認証情報の状態を指します。 | ここでいう保存状態は、保存された認証情報の状態を指します。 |
| API メソッド | API メソッド `storageState` でその状態を取得します。 | API メソッド `storageState` で、その状態を取得します。 |
| 画面表示 | 画面では “Storage State” と表示されます。 | 画面には “Storage State” と表示されます。 |

この例では、一般的な説明で storage state を繰り返さず、意味を伝える日本語を使える。

## 表現の問題と判断例

問題の種類ごとに、次の 4 つの項目で判断する。

- **兆候**: 文章のどこに問題が現れるか
- **確認すること**: 言い換える前に確かめる、実際の意味
- **残せる場合**: 元の表現で正確に伝わる場合
- **言い換えの候補**: 確かめた意味に合う場合だけ使う表現。\
  固定の訳ではない。

まず何が曖昧かを確かめ、入力が支える場合だけ、言い換えの候補を選ぶ。\
元の表現で正確に伝わる場合は、元の表現を残す。\
具体的な語の例は、その語が属する問題の種類の下に置く。

### 原語に固定した訳語を割り当てている

- **兆候**: `break`、`fail`、`ignore`、`support` などに、文脈にかかわらず同じ日本語を割り当てている。
- **確認すること**: 停止、例外、互換性の喪失、不整合、未処理、対象の環境への対応など、実際に起きることを特定する。
- **残せる場合**: 「ビルドが失敗する」「後方互換性が壊れる」のように、分野で意味が共有され、対象も明確な場合。
- **言い換えの候補**: 処理を完了できない、例外を送出する、互換性が失われる、設定を処理に使用しない、Windows に対応する。

#### distribute

`distribute` を常に「配布」と訳すと、手元で作るだけで誰にも渡さないパッケージまで「配布」と呼ぶことになる。\
実際に他人へ渡すのでなければ、「パッケージを作る」「公開する」など、起きることを表す語を選ぶ。

#### 契約

- **兆候**: 法的な合意や当事者間の約束を指すのか、要件、仕様、保証する挙動、入出力の条件、互換性、責任の分担などをまとめて指すのかが分からない。
- **確認すること**: 法的な契約を指すのか、名前の付いた技術の概念や定義済みの用語を指すのか、単に複数の要件や挙動をまとめているのかを確かめる。
- **残せる場合**: 法的な契約を指す場合や、Design by Contract、Code Contracts、contract testing など、分野や製品で定着した用語そのものを指す場合。
- **言い換えの候補**: API が保証する挙動、入出力の要件、受け入れ条件、互換性の要件、公開仕様、責任の分担。

API についての文章であることは、「この API の契約」や「API の契約」を残す理由にならない。\
単に複数の条件をまとめている場合は、成功時に返す値、受け付ける入力、互換性を保つ条件など、その箇所で必要な意味を直接示す。\
`API contract` や `data contract` などの原語は、その語自体が定義または引用され、参照や検索に必要な場合に保つ。\
日本語にするときは、「API の契約」ではなく、その箇所で必要な意味を書く。\
当事者、違反、強制力のような法的な比喩を書くのは、元の内容にそれがある場合だけにする。

#### 正本

- **兆候**: `source of truth` に対応させただけなのか、正式な文書管理上の正本、定義済みの用語、同期や更新の基準を指しているのかが分からない。
- **確認すること**: 正式な効力を持つ文書なのか、法的または文書管理上の責任を持つ記録なのか、公式版や更新の基準なのか、単なる翻訳元や参照元なのかを確かめる。
- **残せる場合**: 文書管理、契約、記録管理での正式な用語として使われている場合、本文で「正本」と定義されている場合、「正本」という語自体を引用または検討している場合。
- **言い換えの候補**: 翻訳元、参照元、英語版、基準となる仕様、公式版、正式な管理元、更新内容を反映する基準。

英語の文書を翻訳するときの元の資料、比較する参照資料、仕様を読むための参照先を表すだけの場合は、言い換える。\
唯一性や排他性（「唯一の参照元」など）は、原文にある場合だけ書く。\
「英語正本を参照して翻訳する」のように翻訳の関係だけを表す場合は、「英語の原文を参照して翻訳する」や「英語版を基準に翻訳する」など、確かめられる関係を直接示す。\
「このリポジトリを正本とする」のように管理の責任や更新の基準を表す場合も、必要に応じて実際の管理の関係を具体化する。\
たとえば、「公開スキーマの基準とする」「このリポジトリの内容を基準に反映する」である。

### 他言語の名詞化や主語の構造を残している

- **兆候**: 「この方法は性能の改善を提供する」のように、他言語の名詞化や主語の構造を保っている。
- **確認すること**: 誰かが何かを提供するのか、処理の結果として状態が変わるのかを確かめる。
- **残せる場合**: サービス、API、組織などが、実際に機能や情報を提供する場合。
- **言い換えの候補**: この方法により性能が改善する、この変更で処理時間を短縮できる、この API は監査ログを提供する。

#### 英語の複合名詞

`personal plugin archive upload` を「個人用 Plugin のアーカイブアップロード」のように名詞の連続で訳すと、誰が何をするのかが読み取りにくい。\
「個人用の Plugin としてアップロードする」のように、動詞を使って操作として書く。

### 中黒で種類の違う項目を並べている

- **兆候**: 「単体・APM 導入」「復旧・運用・セキュリティ・外部状態への影響」のように、中黒が「と」「または」「/」の役割をまとめて担っている。\
  そのため、並列の範囲や修飾のかかり方が読み取れない。
- **確認すること**: 並んでいる項目が同じ種類で同じ階層か、and と or のどちらの関係か、修飾語がどこまでかかるかを確かめる。
- **残せる場合**: 「日付・時刻」のように、同じ種類の短い語を並べ、範囲が明らかな場合。
- **言い換えの候補**: 「単体導入または APM 導入」と書く。\
  項目が多い場合や修飾がかかる場合は、文を分けるかリストにする。

### 立場によって指す相手が変わる語を使っている

- **兆候**: 「ユーザーがアップロードする」のように、エージェントから見た依頼者、製品の利用者、文書の読者のどれを指すかが、文脈から決まらない。
- **確認すること**: その動作を実際に行うのが誰かを確かめる。
- **残せる場合**: 文書の冒頭で語の指す相手が定義され、文書全体で一貫している場合。
- **言い換えの候補**: 保守者、利用者、依頼者など、実際の立場を表す語を使う。\
  読者自身が行う手順なら、主語を省いた指示の形にできる。

### 一般的な説明の表現を英語のまま使っている

- **兆候**: 日本語で意味を保てる形容詞、抽象名詞、説明用のラベルを、英語のまま助詞や動詞へつないでいる。
- **確認すること**: 原語が正確さ、参照、検索に必要なのか、単に説明のために使われているのかを確かめる。
- **残せる場合**: 製品名、正式な機能名、コード、設定キー、識別子、規格名、定着した専門用語、原語そのものを論じる場合。
- **言い換えの候補**: 英語を残す理由がなければ、意味が通る日本語を選ぶ。\
  原語を使う場合は、読者に未知と考えられるなら初出で短く説明し、その後は日本語か定着した表記で通す。\
  読者の検索や参照に必要なら、説明の表現と原語を併記してよい。

#### `deterministic`

- **兆候**: 決定性を表す技術用語なのか、人手によらず定型的に処理することを表しているのかが分からない。
- **確認すること**: 同じ入力から同じ結果を得られる性質を指しているかを確かめる。
- **残せる場合**: 日本語にすると、決定性という技術的な性質が失われる場合。
- **言い換えの候補**: 原語を保つか、「同じ入力から同じ結果を得られる方法で検出する」のように決定性を具体化する。

「機械的に検出する」を使うのは、決定性ではなく、人手によらず定型的に処理する意味を表す、技術的でない文脈だけにする。

### 抽象語や比喩が具体的な対象を隠している

- **兆候**: 「核心」「土台」「主役」「入口」「線引き」などが、説明の対象を示さずに、重要さや関係だけを表している。
- **確認すること**: 原因、前提、主要な処理、開始地点、判断基準など、実際に指す対象を確かめる。
- **残せる場合**: 対象が明確で、比喩が文章の理解や調子に必要な場合。
- **言い換えの候補**: 主要因、前提条件、中心となる処理、最初の手順、責任範囲、判断基準。

#### ゲート、門

- **兆候**: 開始地点、参照先、利用方法を比喩で表しているのか、前提条件、自動の検査、人による承認、続行するかの判断、実行やアクセスの制御を指しているのかが分からない。
- **確認すること**: 何を、誰またはどの処理が確かめ、その結果によって何の開始、続行、実行、アクセスを認めるかを確かめる。
- **残せる場合**: Quality Gate、論理ゲート、量子ゲート、製品やパイプラインで正式に定義されたゲートなど、固有の用語や定着した用語として使う場合。\
  物理的な門や、比喩を意図した文章の場合。
- **言い換えの候補**: 入口、参照先、利用方法、前提条件、自動の検査、承認、判断の段階、通過の条件、実行の条件、アクセスの制御。

「契約」が満たすべき要件や保証する挙動を表すのに対し、「ゲート」は、その条件を確かめ、先へ進めるかを決める箇所や仕組みを表すことがある。\
開始地点や利用の経路を比喩的に示すなら、「入口」を使える。\
文書の参照先や使い方を指すなら、その関係を直接書くこともできる。\
通過の条件や続行するかの判定がある場合は、その条件、確認、承認、制御のどれを指すかを示す。\
原文が便宜上 quality gate と呼んでいても、正式名称でなければ、「ゲート」を残す必要はない。\
人による承認は「承認」、結果の確認は「確認」として区別する。\
「最終」「最後」などの時点は、原文に示されている場合だけ表す。

### 口語的または比喩的な表現が動作を曖昧にしている

- **兆候**: 「素通りする」「潰す」「踏み込む」「塞ぐ」「溶かす」「逃がす」「倒す」など、複数の操作や結果を表し得る動詞を使っている。
- **確認すること**: 検査を受けない、候補を除外する、詳しく検討する、通信を遮断する、資源を消費するなど、対象の操作を確かめる。
- **残せる場合**: 会話、ブログ、分野内の慣用表現として、意味が明確な場合。
- **言い換えの候補**: 検証を受けない、原因の候補から除外する、検討の範囲に含める、脆弱性を修正する、時間を費やす、安全になる設定を選ぶ。

#### 静かに壊れる、静かに失敗する

- **兆候**: 「静か」が、通知、記録、例外、処理の継続のどれを表すのかが分からない。
- **確認すること**: 何が起きず、利用者や呼び出し元から何を観測できないのかを確かめる。
- **残せる場合**: 比喩として意図され、直後に具体的な挙動が説明される場合。
- **言い換えの候補**: 例外を送出せずに失敗する、エラーを返さない、ログに記録されない、不整合を検知しないまま処理を続ける。

「例外を送出しない」と確かめられても、内部で例外が「発生しない」とは限らない。\
ログや画面の通知の有無も、別の事実として扱う。\
分かっている挙動だけで文を完成できる場合は、その挙動だけで書き、執筆を続ける。

#### 黙って無視される

- **兆候**: 入力がどの段階まで処理され、何が通知されないのかが分からない。
- **確認すること**: 構文解析、検証、保存、実行のどこで入力が使われなくなるのかを確かめる。
- **残せる場合**: 会話的な説明で、対象と結果が直前の文脈から明確な場合。
- **言い換えの候補**: 警告なく無視する、設定値は読み込むが処理には使用しない、未対応の項目を保存せずに処理を続ける。

#### 地味に効く、効いてくる

- **兆候**: 影響を受ける対象、方向、条件が示されていない。
- **確認すること**: 性能、遅延、エラー率、保守の費用、作業時間のうち何が、どの条件で、どう変わるかを確かめる。
- **残せる場合**: 会話や随筆で、評価の細部をあえて省く場合。
- **言い換えの候補**: 入力が増えるほど遅延への影響が大きくなる、保守に必要な作業を減らす、測定では処理時間が約 10% 短くなった。

### 同じ種類の抽象的な表現が短い範囲に集中している

- **兆候**: 個々には適切な抽象語、比喩、一般的な説明の句が、短い範囲に重なり、対象の具体的な情報が薄くなっている。
- **確認すること**: 各文が、新しい対象、動作、条件、結果を伝えているかを確かめる。
- **残せる場合**: 具体化しても情報が増えない場合や、変更後のほうが冗長になる場合。
- **言い換えの候補**: 語ごとに置き換えるのではなく、文章全体で、具体的な情報との釣り合いを見て書き直す。

## 文脈に合えば残す表現

次の表現には、日本語の技術文書で定着した用法がある。\
AI の出力に多いことは、これらを変える理由にならない。

- 実測
- 照合
- 見落とす
- 断定
- 取り違える
- 原因を切り分ける
- 要点
- 素朴な実装
- キャッシュ
- **既定値**: `初期値` とは異なる概念を指すことがある。\
  `初期値` に置き換えるのは、両者が同じ概念を指す場合だけにする。
