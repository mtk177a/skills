# 依頼を明確にする

## 目的

- ユーザーが意図する意味と期待する結果をすり合わせ、依頼の曖昧さや情報不足を解消し、合意した依頼内容を返す。\
  要件、権限、受け入れるリスクを捏造しない。
- 後続作業への引き渡しを求められた場合は、予定している次の作業を開始するために必要な内容だけを明確にする。
- 依頼の明確化は、一度にまとめて質問して済ませるのではなく、複数回のやり取りを通じて進める。
- 次の行動を実質的に変え得る情報や判断についてだけ、ユーザーの作業を中断する。

## 確認根拠と進行状況

利用可能な情報を集める。

- 依頼と、過去の質問・回答を含む関連する会話履歴
- 意図のすり合わせだけを求めているのか、整理した依頼内容の引き渡しを求めているのか、承認済みの作業の途中で明確化しているのかという依頼の位置づけ。\
  必要に応じて、予定している次の作業と、その開始条件
- 適用される指示、既知の環境情報、関連 Issue、エラー、制約
- 対象を書き換えず、安全かつ依頼に関係する調査から得られる事実

明確化を進める間、次の情報を区別して記録する。

- ユーザーまたは正式な情報源から得た確認済みの事実
- 合理的な推論とその根拠
- 明示した作業上の前提
- 未解決の質問と矛盾
- 不足している承認や、リスクを受け入れるという判断

推論、前提、不完全な回答、無回答を、確認済みの要件として扱わない。\
値は存在するが提示・確認されていない状態と、判断自体がまだ行われていない状態を区別する。\
`未提示` や `不明` を `未決定` と読み替えない。

## 明確化の手順

1. 明確化によって求められている結果を特定する。\
   追加の質問をする前に、意図、期待する結果、重要な未確定点をどう理解しているか短く返す。\
   特に、依頼の意味を理解できているか確認された場合は、この順序を守る。\
   後続作業を勝手に想定せず、ユーザーがその理解を訂正できるようにする。\
   引き渡しを求められた場合は、予定している次の作業と、開始に最低限必要な条件を特定する。\
   後続作業へ渡せる状態とは、その作業を開始できる状態であり、すべての後工程を完全に仕様化した状態ではない。\
   次の作業の担当が権限と責務の範囲内で調査する事実や設計で決める技術的な選択を、ユーザーが事前に決めるよう要求しない。
2. ユーザーの最新回答を、それまでに整理した内容へ反映する。\
   回答済みの事項を保持し、重要な未解決事項は、回答を得る、明示的に置き換えられる、予定する次の作業に影響しなくなる、または次の作業で解消すべき事項として引き渡すまで保持する。\
   以前の情報との矛盾は、説明せずに一方を採用するのではなく、明示する。\
   最新回答が以前の条件を明示的かつ曖昧さなく置き換えた場合は、同じ置き換えを再確認せず、訂正として記録する。
3. 期待する結果、完了条件、合意した対象範囲、対象外、制約、環境、権限、外部への作用、リスク、検証の実行可能性を変え得る情報や判断の不足を特定する。\
   対象と調査範囲が明確な場合は、対象を書き換えない安全な調査で事実を確認する。\
   予定している次の作業の担当が、ユーザーの意図、権限、受け入れるリスクを捏造せず、自らの責務と権限の範囲内で解消できない不足だけを、この段階で解消すべき重要な不足として扱う。
4. 残る不足を分類する。
   - **進行を妨げる不足（Blocking）:** 作業を実質的に変え得るか、エージェントが補えない情報・承認・リスクの受け入れ判断を必要とする。
   - **前提で補える不足（Assumable）:** 影響が小さく、局所的で元に戻せるうえ、既存の規約または利用可能な根拠に支えられている。
   - **現段階では影響しない不足（Irrelevant for now）:** 予定している次の作業へ影響しない。
5. 進行を妨げる可能性がある不足について質問する前に、予定している次の作業で、利用を許可された根拠とユーザーが示した判断基準から解消できるか確認する。\
   解消できる場合は、その作業で解消すべき事項として保持し、明確化の完了を妨げる条件にはしない。\
   解消できない場合だけ、不足を解消するために必要な質問を行い、各回答が必要な理由を短く説明する。\
   回答を必要とする後続作業は停止するが、その回答に依存しない安全な調査まで停止しない。
6. 前提で補える不足については、前提、根拠、影響範囲、見直し条件を明示してから進む。\
   前提は、承認や重要なリスクを受け入れる判断の代用にはならない。
7. ユーザーが回答するたびに手順 2 へ戻る。\
   一度の質疑応答を、明確化の完了とみなさない。\
   回答が部分的なら、回答済みの質問をそのまま繰り返さず、残る重要な不足へ絞って追加質問する。
8. 次のいずれかの状態でだけ終了する。
   - **準備完了（Ready）:** 求められた意図のすり合わせが完了し、引き渡しも求められている場合は、予定している次の作業の開始条件を満たした。\
     その作業の担当が権限の範囲内で調査する技術的な事実や、設計で決める事項が残っていてもよい。
   - **前提を明示して進行（Proceed with assumptions）:** 明示した、影響の小さい前提だけが残っている。
   - **進行不可（Blocked）:** ユーザーが回答できない、判断を保留した、または必要な権限を取得できないため、重要な不足を安全に解消できない。

## 判断基準

- 質問数、やり取りの回数、選択肢、前提の数を固定しない。\
  追加のやり取りによって、次の作業を開始できるかどうかや安全性が変わり得る間だけ継続する。
- `design-changes` へ渡す場合は、期待する結果、成功とみなす範囲、合意した対象範囲と対象外、重要な制約、設計する権限が十分に確認できていることを求める。\
  実装構造、対象ファイル、製品・サービスの提供元や依存先の選択、詳細なデータの対応づけ、検証の設計は、それらの決定が設計の責務に明示的に含まれ、必要な判断基準がユーザーから得られている場合は、未決のまま渡す。
- `implement-changes` へ直接渡す場合は、実装方針、承認済みの対象範囲、除外範囲、重要なリスクについての判断、利用可能な検証根拠が十分に確定していることを求める。\
  未解決の設計判断は `design-changes` へ回す。
- 重要な選択を正確に表せる場合だけ選択肢を提示する。\
  推奨は、根拠、既存の既定の方針、または明示した利点と不利益に支えられている場合だけ示す。
- 依頼に複数の目標がある場合、それらが一つの一貫した結果を構成するか判断する。\
  一緒に扱うことで対象範囲、順序、承認、レビューのしやすさが変わる場合だけ、分割を提案するか優先順位を確認する。
- 一見矛盾する要件を、段階、順序、例外などの関係を捏造して両立させない。\
  後の明示的な回答が以前の条件を明確に置き換えた場合を除き、ユーザーに矛盾の解消を求める。
- ユーザーが意図のすり合わせ、または整理した依頼内容の引き渡しを明示的に求めない限り、すでに明確な依頼を再質問・再構成しない。\
  理解確認のために実装の詳細を求めたり、曖昧さのない合意をもう一度確認したりしない。
- 未解決事項があっても進むよう求められた場合、前提で補える不足にだけ前提を使う。\
  進行を妨げる不足が残る場合は、進行不可（`Blocked`）として報告する。

## 応答に含める内容

固定のテンプレートを出すのではなく、現在の状態に応じて応答を調整する。

理解確認では、単に肯定したり質問を並べたりせず、理解した内容を短く言い換えることから始める。\
理解できた意図と重要な未確定点を分け、求められた明確化に必要な内容だけを質問する。\
すり合わせが完了したら、合意した依頼内容を単体で理解できる形で返し、明確化が完了したことを伝える。

質問する場合は、未解決事項、次の行動へ与える影響、質問、判断に必要な選択肢やその利点と不利益を含める。\
回答待ちとなる後続作業が明らかでない場合は、その作業も示す。

前提で進む場合は、各前提、根拠、影響範囲、見直し条件を含める。

整理した依頼内容の引き渡しを求められた場合や、次の作業にそれが必要な場合は、確認済みの期待する結果、依頼の理解や後続作業で選択肢の利点と不利益を評価するために必要な重要な背景・理由、成功条件または完了条件、合意した対象範囲、対象外、制約、前提、未解決事項または不足する権限、次の行動を含める。\
複数回のやり取りを経て準備完了（`Ready`）となった場合は、最新回答で変化した部分だけでなく、引き渡した内容を単体で理解するために必要な確認済み情報を再掲する。\
ユーザーまたは正式な情報源から得た情報だけを、確認済みの要件や背景として扱う。\
実装に伴って生じそうな結果、一般的に推奨される方法、設計で取り得る案を、要件、背景、完了条件、前提、選択済みの方式として扱わない。\
重要な場合は、次の作業で検討すべき未解決事項として保持する。\
確認済み情報と推論を区別し、空の項目は省く。

進行不可（`Blocked`）の場合は、未解決の重要な不足、欠けている根拠または判断、変更しなかった範囲、依頼を再開できる条件を示す。\
新しい情報なしに同じ質問を繰り返さない。

## 境界

- 依頼が理解できた後、実装方針、影響範囲、リスク、検証を設計する必要がある場合は、次の作業の候補として `design-changes` を示す。
- 変更が十分に明確かつ承認済みで、不確実性が低く、設計を独立した作業として引き渡す必要がない場合だけ、`implement-changes` への直接の引き渡しが適切となる。
- 明確化だけを求められた場合は、合意した依頼内容を返して終了し、ユーザーの次の指示を待つ。\
  意味についての合意は、設計や実行を開始する承認ではない。\
  承認済みの作業の途中で明確化している場合は、一般的な承認を重ねて求めず、既存の範囲と権限で元の担当作業へ戻す。\
  その作業自体を、この Skill の責務として行わない。
- ユーザーまたは判断の基準となる指示が示した対象と検証上の制約は保持するが、後続の実装で扱うファイルの範囲、実装方針、検証方針を捏造したり選んだりしない。\
  実装や差分レビューを行わず、明確化を破壊的操作や外部への作用の承認として扱わない。
- 別の Skill を必須の依存先とせず、単独で機能させる。\
  後続の Skill の名前は、引き渡し先を明確にするために役立つ場合だけ挙げる。
