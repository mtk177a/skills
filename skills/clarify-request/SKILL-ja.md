# Clarify Request（依頼の明確化）

## 目的

- 曖昧または情報不足の依頼を、要件、権限、リスク許容を捏造せず、予定している次の workflow が開始できる状態にする。
- clarification を一度の質問ではなく、複数ターンにまたがる反復 workflow として扱う。
- 次の行動を実質的に変え得る情報や判断についてだけ、ユーザーの作業を中断する。

## Evidence と clarification state

利用可能な情報を集める:

- 依頼と、過去の質問・回答を含む関連する会話履歴
- 予定している次の workflow と、それに必要な情報や承認
- 適用される指示、既知の環境情報、関連 Issue、エラー、制約
- 安全で関連性のある read-only inspection から得られる事実

clarification の進行中は、次を分けて保持する:

- ユーザーまたは権威ある情報源が示した確認済み事実
- 合理的な推論とその根拠
- 明示した作業用の前提
- 未解決の質問と矛盾
- 未取得の承認またはリスク許容

推論、前提、不完全な回答、無回答を、確認済み要件へ変換しない。
値が存在するものの未提示・未確認である状態と、判断自体が未決定である状態を区別する。`未提示` や `不明` を `未決定` へ置き換えない。

## Clarification cycle

1. 予定している次の workflow と、開始に最低限必要な情報・権限を特定する。decision-ready とは、その workflow を開始できる状態であり、すべての後工程を完全に仕様化した状態ではない。次の workflow が調査・設計する権限と責務を持つ事実や技術的選択を、ユーザーが事前に決めるよう要求しない。
2. ユーザーの最新回答を clarification state へ反映する。回答済み事項を保持し、未解決の重要な gap は、回答済み、明示的に置換済み、予定する次の workflow に不要、またはその workflow の open input に割り当て済みとなるまで保持する。以前の情報との矛盾は黙って一方を選ばず明示する。最新回答が以前の条件を明示的かつ曖昧さなく置き換えた場合は、同じ置換を再確認せず訂正として記録する。
3. 期待結果、完了条件、合意済み scope、non-goals、制約、環境、権限、外部作用、リスク、検証可能性を変え得る不足を特定する。対象と inspection scope が明確な場合は、安全な read-only inspection で事実を確認する。予定している次の workflow がユーザーの意図、権限、リスク許容を捏造せず、その責務と権限の中で解決できない不足だけを、この段階の重要な不足として扱う。
4. 残る不足を分類する:
   - **Blocking:** 作業を実質的に変え得るか、エージェントが補えない情報・承認・リスク許容を必要とする。
   - **Assumable:** 低影響、局所的、可逆的で、既存規約または利用可能な evidence に支えられている。
   - **Irrelevant for now:** 予定している次の workflow へ影響しない。
5. blocking の可能性がある gap を質問する前に、予定している次の workflow が、承認された evidence とユーザーが示した判断基準から解決できるか確認する。解決できる場合は、その workflow の open input として保持し、clarification を停止しない。解決できない場合だけ、gap の解消に必要な質問を行い、各回答が必要な理由を短く説明する。回答を必要とする後続作業は停止するが、無関係で安全な discovery まで停止しない。
6. assumable gap には、前提、根拠、影響範囲、見直し条件を明示してから進む。前提は承認や重要なリスク許容の代用にはならない。
7. ユーザーが回答するたびに手順2へ戻る。一度の質疑応答を clarification の完了とみなさない。回答が部分的なら、回答済みの質問をそのまま繰り返さず、残る重要な不足へ絞って追加質問する。
8. 次のいずれかの状態でだけ終了する:
   - **Ready:** 予定している次の workflow の開始条件を満たした。その workflow が権限内で調査する技術的事実や決定する設計事項が残っていてもよい。
   - **Proceed with assumptions:** 明示した低影響な前提だけが残っている。
   - **Blocked:** ユーザーが回答できない、判断を保留した、または必要な権限を取得できないため、重要な不足を安全に解消できない。

## 判断基準

- 質問数、clarification のターン数、選択肢、前提に固定数を設けない。追加のやり取りが readiness または安全性を変え得る間だけ継続する。
- `design-changes` へ渡す場合は、期待結果、success boundary、合意済み scope と non-goals、重要な制約、設計する権限が十分に確認できていることを求める。実装構造、対象ファイル、vendor または dependency の選択、詳細な data mapping、verification design は、それらの決定に必要な基準がユーザーから得られ、設計責務に明示的に含まれる場合は未決のまま渡す。
- `implement-changes` へ直接渡す場合は、実装方針、承認済み scope、除外範囲、重要なリスク判断、利用可能な検証根拠が十分に確定していることを求める。未解決の設計判断は `design-changes` へ回す。
- 重要な選択肢を正確に表せる場合だけ選択肢を提示する。recommendation は evidence、既存の default、または明確な trade-off が支える場合だけ示す。
- 依頼に複数の目標がある場合、それらが一つの一貫した結果を構成するか判断する。一緒に扱うことで scope、順序、承認、reviewability が変わる場合だけ、分割を提案するか優先順位を確認する。
- 一見矛盾する要件を、段階、順序、例外などの接続関係を捏造して両立させない。後の明示的な回答が以前の条件を明確に置き換えた場合を除き、ユーザーへ整合を確認する。
- ユーザーが structured handoff を明示的に求めない限り、すでに明確な依頼を再質問・再構成しない。
- 未解決事項があっても進むよう求められた場合、assumable class にだけ前提を使う。blocking gap は `Blocked` として報告する。

## Reporting contract

固定テンプレートを出すのではなく、現在の状態に応じて応答を調整する。

質問する場合は、未解決事項、次の行動へ与える影響、質問、判断に必要な選択肢・trade-off を含める。明らかでない場合は、回答待ちとなる後続作業を示す。

前提で進む場合は、各前提、根拠、影響範囲、見直し条件を含める。

次の workflow が必要とする場合、または structured handoff を求められた場合は、確認済みの intended outcome、依頼の理解または下流の trade-off 評価に必要な重要な背景・理由、success / completion criteria、accepted scope、non-goals、constraints、assumptions、未解決事項または不足する権限、next action を含める。複数ターンの clarification が `Ready` になった場合は、最新回答で変化した部分だけでなく、handoff を単体で理解するために必要な確認済み情報を再掲する。ユーザーまたは authoritative source が示した情報だけを確認済み要件または背景へ昇格させる。実装上ありそうな帰結、一般的な best practice、設計上の可能性を、要件、背景、完了条件、前提、選択済みの方式へ変換しない。重要な場合は次の workflow の open input として保持する。確認済み情報と推論を区別し、空の項目は省く。

`Blocked` の場合は、未解決の重要な不足、欠けている evidence または判断、変更しなかった範囲、依頼を再開できる条件を示す。新しい情報なしに同じ質問を繰り返さない。

## 境界

- 依頼が理解できた後、実装方針、影響境界、リスク、検証を設計する必要がある場合は `design-changes` を使う。
- 変更が十分に明確かつ承認済みで、不確実性が低く、独立した設計 handoff が不要な場合だけ、`implement-changes` へ直接進む。
- ユーザーまたは authoritative guidance が示した対象と検証制約は保持するが、後続の実装ファイル境界、実装方針、verification strategy を捏造・選択しない。実装、差分レビューを行わず、clarification を破壊的操作や外部作用の承認として扱わない。
- 別の Skill を必須依存とせず単独で機能させる。後続 Skill の明示が handoff に役立つ場合だけ名前を挙げる。
