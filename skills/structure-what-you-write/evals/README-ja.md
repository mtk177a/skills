# structure-what-you-write の評価

## 目的

このガイドは、この Skill を単独で使うことで、同じモデルが Skill なしで書く場合よりも有用な挙動が得られるかを評価するためのものである。
意味と権限を保ちながら、読者が根拠のある情報を見つけ、理解し、比較し、利用しやすくなるかを評価する。
採点基準への合格は作業としての十分さを示すが、それだけでは Skill による効果を示さない。
好みの Markdown の形ではなく、読者の作業に照らして両方の出力を判断する。

## 評価定義

- [evals.json](evals.json): 定義内の入力ファイルとケース別の採点基準を持つ、15 件の動作ケース。
- [triggers.json](triggers.json): 明示的・暗黙的な執筆依頼と、執筆以外の対照ケースを含む、8 件の起動判定ケース。
- [report.json](report.json): 最新の動作評価の実行結果。\
  評価候補のハッシュと各採点項目の判定を含み、比較による判断は後述する。

実行用データとファイルは架空の内容で、それ自体で必要な情報が揃っている。
外部サービスの操作、公開、インストール、稼働中のシステムへの操作を必要とするケースはない。

## 評価方法を選ぶ

「この Skill が意図した効果を出すか」を確認するときは、`baseline-comparison` を使い、`candidate` と `without-skill` を明示的に指定する。
候補条件には対象 Skill だけを与え、対照条件には Skill を与えない。
モデル、推論強度、依頼、実行用ファイル、利用できるツール、サンドボックスを揃える。
個人用の同名コピーがないことだけでなく、モデルに見える Skill 一覧全体を確認する。
無関係な個人用 Skill は評価の呼び出し内だけで無効にし、必要な分離を確認できなければ停止する。
別の Skill の選択、導入、協力を、個別 Skill の合格条件にしない。

有効性を評価した後の局所的な回帰確認には `targeted-candidate` を使う。
意味を変えない文書変更には `static-only` を使う。
`targeted-routing` は任意の独立した起動判定であり、文章への効果を測るものでも、単独利用の挙動を受け入れるための前提でもない。
他 Skill との併用を評価する場合は、具体的な利用環境に関する問いと範囲を別に定める。
共通規則は、[評価方法の選択](../../../docs/evaluation.md#select-an-evaluation-path) を参照する。

動作ケースでは、編集しないことを期待する場合も `workspace-write` を使い、許可されていない編集を観測できるようにする。
プロンプトには、分割・統合・表・見出しの形ではなく、読者の目的と許可された編集範囲を書く。
対になるフィールドのケースでは、Skill 内の事例とは異なる分野の名称と選択可能数を使う。
これらは別の入力への適用を確かめる架空のタスクであり、実際の文章作成全般での性能を示すものではない。

## 評価ケース

### 動作評価ケース — evals.json

各行は、[evals.json](evals.json) の一つのケースと、そのケースで確認する責務、採点に必要な根拠を示す。
変更した責務に応じてケースを選ぶ。
受け入れ条件の全体は、定義内の採点基準に記載されている。

| ケース ID | 責務 | 検出する失敗 | 採点に使う根拠 |
| --- | --- | --- | --- |
| `views-and-checks` | 意味のある情報単位と包含関係 | 恣意的なまとめ方を残す、または確認の指示をビューの情報と同列に扱う | 編集後のタスクと、保持された名前・フィルターの対応 |
| `state-and-completion` | 関連はあるが異なる情報の役割 | 状態の定義、進捗の根拠、条件付きの完了規則を分かりにくくする | 編集後の判定文書と、すべての条件が保持されていること |
| `field-lookup` | 独立したフィールドの参照 | 一つのフィールドの定義全体を見つけにくくする、または未設定と明示的な None を混同する | 定義がまとまって配置されていることと、各フィールドの意味の正確さ |
| `field-comparison` | 読者に応じた表現 | 事例で別々の表を使っているという理由で、有用な並列表現を機械的に分割する | 独立したスキーマを保ちながら、共通の観点で比較できること |
| `ordered-procedure` | 実行順序と例外 | 前提条件の確認より先に書き込む、または再試行の禁止や結果確認を該当する操作から切り離す | 編集後の手順と、すべての停止・検証条件 |
| `split-reader-tasks` | 独立した読者の作業 | 利用開始や設定参照を難しくする、または矛盾する複製を作る | 両方の読者の参照経路、内容の完全性、情報の管理元、リンク。ファイル数は指定しない |
| `merge-fragmented-guide` | 一つのまとまった読者の作業 | ファイルを次々に移動させる、または指示やリンクを失う | 完全な手順と README から必要な移動。ファイル名は指定しない |
| `standalone-task` | 単独実行、情報の配置、挙動の保持 | 必須の規則を別資料へ移す、保守者の作業を実行手順に残す、または再構成中に実行時の規則を作り足す | 提供された運用要件とタスク本文の比較、保守者向け文書、作成されたファイルの一覧 |
| `short-message` | 短い文章の作成 | 短いメッセージに報告書の枠組みを付ける、または約束を作り出す | 完成したメッセージと、送信・ファイル書き込みを行っていないこと |
| `no-documentation-impact` | 変更不要の判断 | 読者への影響がない内部リファクタリングに対して、無理に編集する | 元の実行用ファイルとの比較と説明 |
| `review-only-scope` | 構造のレビューと編集権限 | 局所的な表現の校正だけで済ませる、またはレビューのみの依頼で関連資料を編集する | 指摘、配置の提案、実行用ファイルが変更されていないこと |
| `focused-readme-update` | 範囲を絞った更新と検証 | 無関係な節を書き直す、または実行していないコマンドを検証済みとする | README の差分、コマンドの実行記録と出力、他のファイルが保持されていること |
| `pr-description` | 根拠に基づく PR 本文の作成 | 執筆経緯、却下された挙動、未検証のリリースに関する主張を掲載する | 変更内容、差分、報告者を明示した検証記録と、完成した説明文との比較 |
| `unknown-design-rationale` | 現在の挙動と判断理由の区別 | 実装の根拠から承認済みの設計理由を作り出す、または独立して裏付けられる作業まで拒む | 現在の挙動を説明した文書と、判断理由が不明である旨の明示 |
| `faithful-restructure` | 忠実な編集と内容の選定の区別 | 提供された主張を削除する、主張の確度を変える、または提案を承認済みに変える | 提供された原文と、すべての主張・条件との比較 |

対になる `field-lookup` と `field-comparison` は、異なる読者の作業に対して同じ入力を使う。
フィールド定義の表現方法を変更する場合は、両方を選ぶ。
成功条件は、固定された表のパターンを写すことではなく、依頼された参照や比較に適した構造を選ぶことである。
独立した読者、一つのまとまった手順、単独実行のケースは、それぞれ異なる配置の判断を検証するものであり、分割や統合自体を良いとはみなさない。

### 起動判定ケース — triggers.json

各行は、[triggers.json](triggers.json) の一つのケースを示す。
期待する選択は `expected_handlers` に対応し、執筆依頼では対象 Skill、執筆以外の対照ケースでは空の配列となる。
これらのケースは、完成した文章の品質ではなく、Skill の選択を検証する。
任意の起動判定のために残すものであり、単独利用の効果を比べる評価には含めない。

| ケース ID | 依頼の種類 | 期待する選択 | 検出する失敗 |
| --- | --- | --- | --- |
| `explicit-structure` | 対象 Skill の明示的な使用指定 | `structure-what-you-write` | 明示的な使用指定を見逃す |
| `implicit-readme` | README の新規作成 | `structure-what-you-write` | 暗黙的な文書作成の依頼を見逃す |
| `implicit-email` | 短いメールの作成 | `structure-what-you-write` | 短いメッセージを執筆支援の対象から外す |
| `implicit-structural-review` | 編集を伴わない構造のレビュー | `structure-what-you-write` | 情報構造のレビューを見逃す |
| `implicit-no-change-assessment` | 文書変更の要否の判断 | `structure-what-you-write` | 変更不要になり得る文書作業を見逃す |
| `arithmetic` | 計算 | 選択なし (`[]`) | 数値計算で執筆支援を起動する |
| `literal-copy` | 文字列の正確なコピー | 選択なし (`[]`) | 書き換えが禁止された依頼で執筆支援を起動する |
| `lookup-only` | 数値の直接参照 | 選択なし (`[]`) | 単純な値の取得で執筆支援を起動する |

## 選択した評価を実行する

コマンドはリポジトリのルートから実行する。

1. **定義と入力を確認する。**
   - プロンプトや実行用データを、採点基準や期待する回答と分ける。
   - 実行用ファイルのパスが安全か確認する。
   - 依頼された作業に必要な事実が入力に揃っているか確認する。
   - 採点基準を、現在の Skill の要件と照合する。
   - リポジトリの checker を実行する。\
     パッケージのメタデータ、評価定義、参照するファイルを検証できる。

   ```bash
   python3 scripts/check_repository.py
   ```

2. **選択したケースの計画を作る。**
   前の節で選んだ評価方法、条件、サンドボックスを使う。\
   単独利用の効果を初めて比べる評価では、後述する 9 ケースを選ぶ。

   ```bash
   evaluation_tmp="$(mktemp -d)"
   python3 scripts/run_skill_evaluation.py plan \
     --skill structure-what-you-write \
     --path baseline-comparison \
     --purpose "Assess the incremental effect of the standalone Skill." \
     --affected "reader access, placement, creation, review and preserved meaning" \
     --condition candidate \
     --condition without-skill \
     --case views-and-checks \
     --case field-lookup \
     --case field-comparison \
     --case split-reader-tasks \
     --case merge-fragmented-guide \
     --case standalone-task \
     --case short-message \
     --case review-only-scope \
     --case pr-description \
     --base-ref HEAD \
     --sandbox workspace-write \
     --output "$evaluation_tmp/plan.json"
   ```

3. **計画を確認し、実行する。**
   実行前に、選択したケース、条件、サンドボックス、推定モデル呼び出し数を確認する。\
   [共通の実行手順](../../../docs/evaluation.md#execute-the-approved-plan) に従う。\
   9 ケースを両条件で実行するため、モデル呼び出しは 18 回となり、採点用モデルの追加呼び出しはない。\
   計画を作っただけでは、ケースは実行されない。

4. **観測した結果を採点する。**
   後述する根拠の要件と、[共通の採点手順](../../../docs/evaluation.md#grade-planned-results) に従う。\
   動作の採点基準は呼び出し元のエージェントまたは人間が採点し、起動判定は Runner が実行記録から採点する。\
   両条件に同じ採点基準を適用し、後述する確認課題で読者の作業のしやすさを比較する。\
   採点用に追加のモデルを用意する必要はない。

5. **結果を記録し、追加の根拠が必要か判断する。**
   実際に実行した後で、[共通の報告手順](../../../docs/evaluation.md#preview-and-write-the-report) に従う。\
   生の計画、実行記録、実行用ファイルのスナップショット、採点結果は、リポジトリの外に置く。\
   選択したケースで採否の判断に必要な問いが解消したら停止する。\
   評価を追加するのは、変更した責務、未検証の失敗、不安定な結果、または判断に影響する根拠の矛盾がある場合に限る。

## 結果を採点する

### 動作評価: 文章品質と許可範囲内の変更

動作ケースは、`evals.json` の各採点基準に照らして評価する。
すべての基準が必須条件として設定されている。
構造を判断するときは、依頼された読者の作業に役立ち、必要な関係と条件・留保がすべて保たれているかを確認する。
ビューの一覧は、対応関係、確認の指示、対象範囲が明確なら、リストでも表でも合格できる。
フィールドのケースが求めるのは、指定された列配置ではなく、依頼された情報の参照方法を実現することである。

選択したケースについて、次の観点のうち該当するものをすべて確認する。
これは採点の観点であり、ケースを重複なく分類するものではない。

| 採点の観点 | 確認する根拠 | 確かめること |
| --- | --- | --- |
| 文章品質と内容の完全性 | 完成した成果物または回答と、依頼・提供された資料との比較 | 必要な情報と関係が正確で、欠けずに含まれ、読者に役立つこと |
| 編集権限と既存内容の保持 | 変更・追加・削除された実行用ファイルと、元の内容との比較 | 変更が権限の範囲に収まり、変更不要・レビューのみのケースでは内容が変わっていないこと |
| 参照の整合性 | 編集の影響を受ける相対リンクと、その参照先 | 移動や削除の後も、必要な情報にたどり着けること |
| 検証についての報告 | 実行記録と実際のコマンド出力を、最終報告と比較 | 観測した検証結果が、提供された報告や未実施の確認と区別されていること |

最終回答だけから、編集が完了したと判断しない。
編集しないケースでも、サンドボックスでは書き込みが可能なため、実際の内容変更の有無を確認する。
`standalone-task` では、欠落だけでなく追加も確認する。
処理順、入力検証、停止・継続の挙動、アクセス制限、必須の出力制約を新たに定めるには、提供された根拠が必要である。
見出しや箇条書きなどの表現形式は、必要な実行時の挙動を変えない限り選択できる。
根拠が不足する場合は `inconclusive` と記録する。

### 起動判定: 期待する選択と観測した選択の比較

期待する選択には `triggers.json` の `expected_handlers` を使い、観測には完了したイベント記録を使う。
Skill の読み取り成功イベントから、インストールされた Skill のうち、どれが読み取られたかを確認する。
完了した記録に対象の読み取りも曖昧な読み取りの試行もなければ、選択されなかった根拠になる。
記録がない場合、未完了の場合、失敗したシェルコマンド内の読み取りの成否が未確定の場合は `inconclusive` とし、選択されなかった証拠にはしない。
Runner が、[共通の評価規則](../../../docs/evaluation.md#grade-planned-results) に従い、実行記録からこの起動判定の要件を採点する。

## 読者の作業に対する効果を比較する

選択したケースは、異なる意図した効果と、過剰な構造化を防ぐ対照を含む。
他のケースは個別の回帰確認のために残し、一律の必須ケース数は定めない。
次の確認課題は採点者向けであり、実行担当の入力には加えない。

| ケース | 読者の確認課題と比較に使う根拠 |
| --- | --- |
| `views-and-checks` | Unowned のフィルターと共通の使用前確認を探す。恣意的なまとまりを読み解き直さずに、名前・フィルター・確認事項の関係が分かるかを見る |
| `field-lookup` | Request checks の全値、選択・解除の規則、空欄・None の意味を一まとまりで調べる。見出しの数ではなく、必要な移動や無関係な情報の走査を見る |
| `field-comparison` | 両フィールドの選択可能数と特殊な状態を直接比較する。参照用と比較用の出力が、それぞれ異なる読者の作業に適応しているかを見る |
| `split-reader-tasks` | README から、既定値での初回起動と、保守者の WIDTH 参照をたどる。直接参照できるか、定義の管理元が一つか、不要な移動がないかを見る |
| `merge-fragmented-guide` | README から、前提条件から失敗時の報告までをたどる。全指示を保ちながら、必須のファイル間移動を比べる |
| `standalone-task` | 実行する読者に task.md だけを渡す。必要な規則がその中に残り、新しい実行時の判断を課していないかを見る |
| `short-message` | 同僚としてメッセージを読む。報告書の枠組みや架空の約束を加えず、4 点の事実・依頼が伝わるかを見る |
| `review-only-scope` | 設定と問題報告の案内をどこに置くべきか、その理由を判断する。実行可能な診断、情報の管理元に関する説明、根拠のない指摘を、編集していないことと合わせて比べる |
| `pr-description` | 実際の挙動変更と検証の限界を判断する。根拠に基づいて情報をまとめているか、実装済みの挙動と執筆メモを区別する負担がないかを見る |

1. 完成した成果物・回答と実際の実行記録から、各条件の全採点項目を判定する。\
   実行担当の自己申告だけで判定しない。
2. 条件名を隠して出力を確認課題で比較し、参照箇所と、情報の参照や理解に関わる具体的な差を記録してから、条件名を開示する。
3. 各組での候補の効果を、`better`（改善）、`equivalent`（同等）、`worse`（悪化）、`mixed`（重要な得失が混在）、`inconclusive`（判定不能）のいずれかで記録する。\
   改善は、読者が作業を進める助けになる差で判断する。\
   表の書式、見出しの増加、短文化、ファイルの増加だけでは改善としない。\
   重要な得失が混在するときは `mixed`、根拠が不足するときは `inconclusive` とする。\
   意味の欠落、無許可の編集、要件の捏造を、他の良さとの平均で相殺しない。
4. 根拠がある効果と、その限界を示す。\
   候補が必須条件に違反した場合は、対照の成否にかかわらず、無条件に採用を勧めない。\
   両条件が要件を満たし、確認課題で重要な差がなければ、Skill による追加の効果は実証できなかったと記録する。\
   候補が合格したことから有効性を推測しない。\
   得失が混在する場合や改善が限られる場合は、観測した特定の作業だけを裏付けるものであり、公称の対象範囲全体を裏付けるものではない。

採点は呼び出し元のエージェントが行う。
条件名を隠すことで期待による偏りを減らすが、独立した評価者による試験や統計的な盲検試験になるわけではない。
有利な比較結果を得るために簡単なケースを追加したり調整したりせず、同等や悪化もそのまま記録する。
判断に関わる不安定さや曖昧さがある場合だけ繰り返し、却下した候補の結果は分けて残す。

## 追加評価の判断

単独利用の挙動を受け入れる前に、不足入力の報告要件が失われる具体的な問題に対応する。
設計の見直しで今回の結果を超える具体的な効果を提案する場合は、有利なケースを増やすのではなく、関係する同じタスクを両条件で比べる。
別クライアント、繰り返し実行時の安定性、実際の読者、複数ターンの作業、参照できない外部の根拠、大規模な文書、表示後のアクセシビリティは、具体的な問いがある場合に別途評価するものであり、一律の前提条件ではない。
起動判定と複数 Skill の連携は、個別 Skill の単独利用の効果を判断する条件には含めない。
