# 指示対象を定義する

## 目的

- 候補語を提案する前に、重要な語を具体的な指示対象、その役割、関係へ結び付ける。
- 流暢な一語が、別々の条件、状態、事象、値、記録、目的、手段、実体、その他の文脈固有の役割を隠すことを防ぐ。
- 元の workflow が持つ設計、調査、執筆、実装の責務を引き受けず、指示対象と命名の契約を返す。

## 必須 reference

この Skill が発火したら、[references/referents-before-labels.md](references/referents-before-labels.md) を最後まで読む。reference を意味判断の基準、このファイルを実行上の契約として使う。

## 証拠と入力

利用できるものを集める。

- 元となる要件、観測、証拠、推論順序
- 作成対象の文書、設計要素、説明、識別子
- 確立したドメイン用語と、その根拠となる情報源
- semantic preflight の後に再開する元の workflow
- 別ファイルを求められた場合は、その作成に対する明示的な許可

確認済み情報、推論、前提、未知を区別する。対象と調査範囲が明確なら、安全で関連する read-only の確認によって発見可能な事実を解決する。表を完成させるために、目的、指示対象、役割、関係、命名権限を捏造しない。

## 手順

1. 新しく導入する語、または意味を広げて再利用する語のうち、後続の推論を実質的に変え得るものだけを特定する。
2. 関係する指示対象と関係を区別できるだけの情報が、元の情報に含まれているか確認する。重要な事実が不足している場合は、焦点を絞って質問するか `Blocked` と報告し、不完全な grounding から命名表を作らない。
3. 最初に Grounding table を作る。この段階には候補語、初出定義、候補語を前提にした表現を含めない。
4. Grounding table だけで検証する。各行は、ラベルへ依存せず、具体的な指示対象、現在の意味上の役割、推論内の位置、不確実性を特定できなければならない。
5. 関係するすべての Grounding row が検証を通過した後にだけ Naming table を作る。確立した語またはユーザーが示した語を優先する。具体的な記述を境界を変えずに短縮できる正確な語がなければ、新語を導入せず `concrete wording` とする。
6. 状態を選ぶ。
   - `Ready`：対応関係と命名上の制約が確定し、元の workflow が再開できる。
   - `Decision required`：複数の対応または候補語が、公開契約やドメイン境界に異なる意味を与える。根拠のある選択肢を示し、黙って選ばず、判断に必要な質問をする。
   - `Blocked`：指示対象を確定するために必要な重要な証拠、情報、権限を得られない。
7. 命名だけの依頼では、表と状態を最終成果物として返す。より広い作業の一部なら handoff として返し、この Skill を終了して元の workflow を再開させる。
8. Grounding row が訂正された場合は、依存する Naming row をすべて無効化し、grounding を修正して、影響する命名案だけを再生成する。ユーザーが作成した内容や後続成果物を上書きしない。

## Grounding table の契約

列順は次のとおりとする。

| ID | 出典 | 目的 | 具体対象 | 意味上の役割 | 前後関係 | 不確実性 |
| --- | --- | --- | --- | --- | --- | --- |

- `R1` のような安定した機械的 ID を使う。ID は表を対応付けるためだけの参照であり、ドメイン用語ではない。
- 候補語を言い換えるのではなく、指示対象が何であるかを書く。
- 現在の説明または設計で果たす意味上の役割を書く。必須 reference にある役割は例であり、閉じた分類ではない。必要なら正確な文脈固有の役割を使う。
- 一つのラベルが異なる指示対象または意味の異なる役割を隠す場合は行を分ける。同じ指示対象が複数の関係へ参加するという理由だけでは分けない。
- ユーザーが示した推論順序と不確実性を保つ。
- 不確実性は `confirmed`、`inferred`、`assumed`、`unknown` で示し、明らかでなければ短い根拠を添える。
- 目的や推論段階が意味上異なる場合、または対応を一貫して確認できない場合だけ表を分ける。固定行数で分割しない。

## Naming table の契約

Grounding table が完成した後にだけ、次の表を作る。

| ID | 候補語 | 状態 | 初出定義 |
| --- | --- | --- | --- |

- Grounding ID を使い、明示的な一対一対応を保つ。
- `状態` には `established`、`proposed`、`concrete wording`、`decision required` を使う。
- 新しく提案する語は「X とは〜を指す」と正確に定義する。確立した語はその旨を示し、Grounding table に記録された根拠との対応を保つ。
- 同じ ID に複数候補を対応させてよいのは `Decision required` の場合だけとし、黙って選ばず意味上の違いを示す。
- 各候補語を単独で読み、区別が重要な別の行を同じように指せないことを確認する。
- Naming table 全体を隠しても、Grounding table だけで意味が通らなければならない。

## 出力とファイルの扱い

- `State: Ready`、`State: Decision required`、`State: Blocked` のいずれかから始める。
- grounding を示せるだけの情報があれば Grounding table を含める。Naming table は grounding が検証を通過した場合だけ含める。
- `Decision required` では、未解決の意味上の選択、その選択が公開契約またはドメイン境界へ与える影響、ユーザーが決める質問を示す。
- `Blocked` では、不足する証拠または情報、未確定の対応、解除条件を示す。
- 既定では会話内に表を返す。ユーザーが追加成果物を明示的に許可した場合だけ別の referent-table ファイルを作る。対象文書の作成許可を sidecar ファイルの作成許可として扱わない。
- hash、ファイル時刻、ユーザー確認を、観測可能な Grounding → Naming の順序の代用にしない。

## 境界

- 対応関係が完成し、低影響で局所的かつ可逆な命名だけが残る場合は、ユーザー確認を必須にしない。
- この Skill を、対象文書、設計、報告、コードを書く権限として扱わない。
- 曖昧さが指示対象や用語に関するものでない場合は、依頼全体を明確化しない。その責務を `clarify-request` または元の workflow へ返す。
- すべての指示対象を閉じた役割一覧へ押し込まず、固定行数で表を分割しない。
- 訂正済み用語のブラックリストを主な対策にしない。
- 正確な対応と初出定義なしで新語を導入しない。
- 実行時に外部の出典記事を取得しない。bundled reference だけで完結させる。
