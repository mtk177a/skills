# コミット案を作成する

## 目的

- 明示された Git の変更範囲から、目的ごとに分けたコミット計画と、必要な情報を含む Conventional Commits メッセージを作る。
- 既存の Git index を変更せず、ステージ済み、未ステージ、未追跡、提供された差分だけの変更を区別する。
- Skill の呼び出しを変更権限として扱わず、別途許可されたコミット作業に引き継げるよう、読み取りだけで案を作る。

## 対象と根拠

案を作る前に、対象とする変更範囲を確定する。

1. 差分、パスの一覧、コミット範囲、またはステージ済みの変更だけという指定があれば、それに従う。
2. 元の作業で変更範囲が明示されている場合は、それを引き継ぐ。
3. ローカルの「現在の変更」という指定だけの場合は、ステージ済み、未ステージ、関連する未追跡の変更を確認し、含めた範囲を明示する。
4. 複数の妥当な解釈によってコミット内容が実質的に変わる場合だけ質問する。\
   変更範囲を確認できない場合は、案を作成できなかったと報告する。

対象リポジトリに明示されたコミットの種類、scope、メッセージ、要約行の言語に関する規約を先に読む。\
変更目的と、その理由を示す Issue、設計資料、実装からの引き継ぎ情報、テストなど、利用できる証拠を確認する。\
差分から分かるのは「何が変わったか」であり、それだけで「なぜ変わったか」は証明できない。

関連する各変更を `Staged`、`Unstaged`、`Untracked`、`Partially staged`、`Provided diff only` のいずれかに分類する。\
リポジトリの状態を確認できない場合も、提供された差分からメッセージ案は作れる。\
ただし、現在の index を確認済みとしたり、実行できるステージング用コマンドを示したりしない。

## 手順

1. 対象とする変更範囲、リポジトリ規約、変更意図を示す証拠、重要な除外範囲を明示する。
2. リポジトリの状態を確認できる場合は、status と diff stat から始め、各コミット案を判断できるまでステージ済み、未ステージ、未追跡の変更内容を確認する。\
   段階的に確認してもよいが、目的や分け方が不明なパスや変更箇所（hunk）を、内容を確認せずに含めない。
3. 変更の一覧を作る。\
   対象内の各パスや変更箇所を一度だけ、特定のコミットに `Included` として割り当てるか、`Excluded` として明示的に外すか、`Unresolved` とする。\
   変更を黙って省略・重複させない。
4. 差分に秘密値や認証情報の疑いがある場合は、その値を再掲せず、その内容について通常のコミット計画を続けない。\
   必要最小限のパスと分類だけを示して対象から外し、必要な対処や不確実性を報告する。\
   根拠なしに無害な仮の値とみなさない。
5. 一つの目的、必要な依存関係、レビューできる挙動ごとに変更をまとめる。\
   同じファイルに異なる目的の変更があれば、変更箇所ごとに分ける。\
   名前の変更と削除の対応を保ち、必要なコミット順を明示する。\
   必要な数だけコミットを使い、件数を抑えるために異なる目的の変更をまとめたり省いたりしない。
6. リポジトリ規約、確認済みの変更意図、外部から分かる挙動の変化、互換性への影響からコミットの種類を選ぶ。\
   意図が不明なために種類が実質的に変わり得る場合は、構文だけから推測せず、質問するか `Unresolved` とする。
7. 必要な情報を含むメッセージ案を作る。\
   要約行には対象リポジトリが指定する言語を使い、指定がなければユーザーの言語を使う。\
   どちらからも判断できない場合は質問するか、言語を未確定とする。\
   scope はリポジトリ規約が対応しているか、その規約の下で明らかに役立つ場合だけ付ける。\
   経緯、参照、リリース処理に必要なら body または footer を追加する。\
   後方互換性を失う変更には必ず `!` または `BREAKING CHANGE:` footer を付ける。\
   コミットの種類、後方互換性を失う変更、body、footer の判断が自明でない場合は `references/commit-types.md` を読む。
8. 既存のステージ済みの内容と、除外した作業ツリーの変更を保つステージング計画を作る。\
   一部だけステージ済みのファイルは、ファイル全体で index を置き換えず、変更箇所ごとの操作として扱う。
9. リポジトリの状態を確認済みで、計画を曖昧さなく表現できる場合だけ、実行候補のコマンドを示す。\
   安全で環境に依存しない表現ができない場合は、コマンドを省略して理由を説明する。
10. 対象内の変更が一度ずつ割り当てられ、各コミットに主目的が一つあり、メッセージが確認済みの意図とローカル規約に合い、除外した内容が含まれず、Skill によってリポジトリの状態が変わっていないことを確認する。

## 安全なコマンドの規則

- 意図した内容がすでにステージ済みなら、不要な `git add` を付けない。
- 現在のファイル全体がそのコミットに属し、除外対象や未ステージの別の変更を含まない場合だけ、ファイル単位の `git add` を使う。
- 変更箇所ごとのステージングには `git add -p -- <path>` または同等の対話手順を使う。\
  対話コマンドを、選択内容まで確定したそのまま実行できるコマンドとして示さない。
- パスを指定する前に `--` を置き、確認したシェルに合わせてパスを引用符で囲む。\
  パスやメッセージを安全で環境に依存しない形で表現できない場合は、シェルコマンドを付けず、操作計画だけを示す。
- 複数行のメッセージ、body、footer は、安全なコマンド表現を確認できない限り、メッセージ用のブロックに記す。\
  不安定な一行の `git commit -m` に押し込まない。
- 現在のリポジトリ状態を確認できない `Provided diff only` には、ステージングやコミットのコマンドを示さない。

## 報告内容

タスクに合わせて表現を調整し、空の節は省略する。次の意味情報を維持する。

- 対象とする変更範囲、関連するリポジトリ規約、変更意図の根拠
- 各コミット案の主目的、必要な情報を含むメッセージ、現在の状態を付けた対象パスや変更箇所、必要な実行順、ステージング計画
- 安全なコマンドの規則を満たす場合だけ、実行候補のコマンド
- 除外した変更と未解決の変更
- 秘密値の疑いに対する扱い、その他の停止理由、未確認事項
- 実行していないリポジトリの変更と、次の作業への引き継ぎ

案を完成できない場合は、不足している変更範囲、重要な変更意図、リポジトリ規約、または安全なステージングの判断を明示し、影響する範囲を未解決のまま残す。\
結果を完全な計画として示さない。

## 権限と作業の境界

- この Skill の読み込みや明示的な呼び出しは、`git add`、`git commit`、`git push`、index の変更、実装、その他のリポジトリへの書き込みを許可しない。
- 元の依頼ですでにコミットが明示的に許可されている場合は、その作業へ案とステージング計画を引き継ぐ。\
  一律の追加承認を求めたり、許可を受けた担当者の作業を妨げたりしない。
- `summarize-changes`、`review-changes`、実装作業を置き換えない。\
  この Skill はコミットの分け方とメッセージを提案し、PR の説明を書いたり、レビュー指摘を探したり、ファイルを変更したりしない。
- メッセージ、コマンド、説明に秘密値や認証情報を出力しない。
- ユーザーの無関係な変更を変更・破棄したり、黙ってコミット対象へ取り込んだりしない。
