# コミットを下書きする

範囲を定めた Git の変更を、まとまりのあるコミットの計画と、完全な Conventional Commits のメッセージにする。\
現在のインデックスを保ち、ステージ済み、未ステージ、未追跡、示されただけの変更を区別する。\
出力は計画とメッセージである。\
ステージ、コミット、プッシュは、別に許可されたコミットの作業手順が行う。\
依頼がすでにコミットを許可している場合は、その作業手順が続けられるように、計画をその作業手順に返す。

## 作業手順

1. **変更の範囲を特定する**

   次のうち、最初に当てはまるものを使う。

   - ユーザーが示した差分、パスの集合、コミット範囲、ステージ済みだけという範囲
   - 元の作業手順から示された明示的な範囲
   - ローカルの変更では、ステージ済み、未ステージ、関連する未追跡の変更

   考えられる二つの範囲でコミットが変わる場合は、ユーザーに尋ねる。\
   変更を取得できない場合は、下書きを実行しなかったことを報告する。\
   計画が扱う変更を示せれば完了とする。

2. **規則と意図を読む**

   まず、リポジトリの type、scope、メッセージ、要約の言語についての規則を読む。\
   変更について示された目的と、関連する Issue、設計、引き継ぎ、テスト、その他の証拠を集める。\
   差分が示すのは、何が変わったかである。\
   意図は、ユーザーとこれらの証拠から得る。

3. **変更を調べる**

   リポジトリを利用できる場合は、状態と差分の統計から始める。\
   そのうえで、提案する各コミットを理解できるだけ、各変更を読む。\
   目的やまとまりがはっきりしない、含めるパスやハンクは、それぞれ読む。\
   各変更を、`Staged`、`Unstaged`、`Untracked`、`Partially staged`、`Provided diff only` のいずれかに分類する。

4. **一覧を作る**

   範囲内の各パスやハンクを、ちょうど一度ずつ割り当てる。

   - `Included`: 提案するコミットの一つに含める
   - `Excluded`: 理由とともに除く
   - `Unresolved`: 未解決の問いとともに残す

   範囲内の各変更に一つの項目があれば完了とする。

5. **秘密情報の疑いに対応する**

   変更に、秘密情報や認証情報の疑いがあるものが含まれている場合は、それを計画から除く。\
   報告するのはパスと種類だけにし、値は出力に含めない。\
   必要な対処か、不確かな点を示す。\
   値が無害な仮の値であるとみなすのは、それを証拠が示す場合だけにする。

6. **変更をコミットにまとめる**

   各コミットを、一つのまとまった目的と、必要な依存関係と、人がレビューできる挙動からなるものにする。\
   一つのファイルの変更が異なる目的に属する場合は、ハンクで分ける。\
   名前の変更とそれに伴う削除は一緒にし、必要なコミットの順序を示す。\
   コミットの数は、変更が必要とする数にする。

7. **type を選ぶ**

   各 type は、リポジトリの規則、確認済みの意図、観測できる効果、互換性への影響から選ぶ。\
   意図が足りないことで type が変わり得る場合は、ユーザーに尋ねるか、type を `Unresolved` とする。\
   type、互換性を壊す変更、本文、フッターの選び方が明らかでない場合は、`references/commit-types.md` を読む。

8. **メッセージを書く**

   完全なメッセージをそれぞれ書く。

   - リポジトリの要約の言語を使う。\
     決まっていなければ、ユーザーの言語を使う。\
     どちらも分からない場合は、ユーザーに尋ねるか、言語を `Unresolved` とする。
   - scope は、リポジトリの規則が支える場合か、その規則のもとで明らかに役立つ場合だけ付ける。
   - 背景、参照、リリースの自動化が必要とする場合は、本文やフッターを付ける。
   - 互換性を壊す変更には、`!` か `BREAKING CHANGE:` のフッターを付ける。

9. **ステージの計画を立てる**

   既存のステージ済みの内容と、除いた変更がそのまま残るように、ステージを計画する。\
   一部だけステージ済みのファイルは、作業ツリーのファイル全体ではなく、ハンクの単位でステージする。\
   コマンドは、[コマンドの規則](#コマンドの規則) に従う場合だけ示す。\
   そうでない場合は、計画を言葉で示し、コマンドを示さない理由を述べる。

10. **計画を確かめる**

    次の項目を確かめる。

    - 範囲内の各変更が、一度ずつ現れている。
    - 各コミットに、主な目的が一つある。
    - 各メッセージが、確認済みの意図とリポジトリの規則に合っている。
    - 除いたものが、除いたままになっている。
    - リポジトリの状態が変わっていない。

## コマンドの規則

- コマンドを示すのは、リポジトリの状態を調べていて、コマンドが計画を正確に表せる場合だけにする。\
  `Provided diff only` の入力では、コマンドを付けずに計画を示す。
- 内容がすでにステージ済みの場合は、ステージ済みのままにし、それに対する `git add` は示さない。
- ファイル単位の `git add` は、ファイル全体がそのコミットに属する場合だけ使う。\
  除いた変更や未ステージの変更が、そのコミットに入らないことを確かめる。
- ハンク単位のステージには、`git add -p -- <path>` か、それと同等の指示を使う。\
  ハンクはユーザーが選ぶので、対話的な操作であることを示す。
- パスの前には `--` を置き、特定したシェルに合わせてパスを引用符で囲む。\
  パスやメッセージをコマンドの中で安全に書けない場合は、コマンドを付けずに計画を示す。
- 複数行のメッセージ、本文、フッターは、別のメッセージのブロックに書く。\
  `git commit -m` は、安全に表せるメッセージにだけ使う。

## 報告

次の項目を含め、空の節は省く。

- 変更の範囲、リポジトリの規則、意図の証拠
- 各コミットについて、主な目的、完全なメッセージ、含めるパスやハンクとその現在の状態、順序、ステージの計画
- コマンドの規則に従う場合だけ、コマンド
- 除いた変更と、未解決の変更
- 秘密情報の疑いへの対応、ほかの止まった理由、確認していない項目
- リポジトリを変更していないことと、次の工程

下書きが進められない場合は、足りない変更の範囲、意図、リポジトリの規則、ステージの判断を示す。\
影響を受ける範囲を `Unresolved` とし、計画が未完成であると報告する。
