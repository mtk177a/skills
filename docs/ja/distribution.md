# Plugin の配布手順

`mtk177a-skills` は、公開している `skills/` を 1 つの Agent Plugin として配布する。\
複数のクライアントで扱える共通形式を採用する。\
Plugin と単体・APM での導入には同じ Skill の原本を使うため、保守者は配布用のコピーを別に管理せず、`skills/` を更新できる。

導入する場合は [導入方法を選ぶ](#導入方法を選ぶ)、配布用アーカイブを準備する場合は [アーカイブを生成・検証する](#アーカイブを生成検証する) を参照する。\
[互換性の文書](compatibility.md#plugin-の実行条件) には、各 Skill が必要とする機能と入力を記載している。

## 導入方法を選ぶ

同じ実行環境で Skill が重複しないよう、導入方法を一つに揃える。

| 利用先 | 導入方法 |
| --- | --- |
| ChatGPT と Codex | ZIP を ChatGPT の個人用 Plugin としてアップロードし、利用する画面や環境ごとに使えるか確認する |
| Cursor | 同じ ZIP を Cursor のローカル Plugin ディレクトリに展開する |
| Claude Code | 既存の [APM による導入](../../README.ja.md#claude-code-apm) を使う。このパッケージでは Claude 固有の Plugin マニフェストを追加しない |

Plugin を有効にする前に、別の Plugin や単体・APM 導入との重複を特定し、クライアントが提供する操作で無効化または削除する。\
無関係な Skill や認証情報は削除せず、文書化されていない優先順位や名前空間で重複を解消できるとは仮定しない。\
復旧に備えて前のアーカイブを保管し、新しい会話で Plugin を確認する。

Plugin の導入によって同梱された指示を利用できるようになるが、シェル、リポジトリ、外部接続、サブエージェント、書き込み権限が与えられるわけではない。\
そのため、Skill を導入できても、依頼された作業に必要な機能や権限が不足する場合がある。

## Plugin を導入・更新する

### ChatGPT と Codex

アーカイブはユーザーが手動でアップロードする。\
生成スクリプトは、アップロードやアカウント設定の変更を行わない。

1. 初回は、ChatGPT の個人用 Plugin のアーカイブアップロードから ZIP を導入する。\
   更新時は別の Plugin を作らず、既存 Plugin のメニューで「新しいバージョンをアップロード」を選ぶ。
2. 表示されたバージョンと Skill 一覧を確認し、新しい会話を開始する。
3. 利用可能な UI で Plugin を選び、依頼文で使う Skill を指定する。\
   たとえば、「`mtk177a-skills` の `define-referents` を使い、参照資料を読んでから命名案を出してください」と依頼する。
4. 利用する画面や環境ごとに、Skill が一覧に現れるか、本文・参照資料を読めたか、その結果どのような回答が得られたかを分けて確認する。\
   読み込みについては、実際に観測できる場合に確認する。

Chat、Work、dots、Codex では、呼び出し方や使える機能が異なる場合がある。\
妥当な回答が得られたことだけでは Skill の読み込みを証明できないため、読み込みの観測結果と回答の内容を区別する。

### Cursor

[Cursor の公式資料](https://cursor.com/docs/plugins) では、共通形式の Agent Plugin への対応と、`~/.cursor/plugins/local/<plugin-name>/` でのローカル検証が案内されている。

1. ZIP を `~/.cursor/plugins/local/mtk177a-skills/` に展開し、その直下に `plugin.json` を置く。\
   更新時は必要なバックアップを確保し、展開先の古いディレクトリを丸ごと入れ替える。\
   ファイルを上書きするだけでは、新版で削除された Skill が残る可能性がある。
2. Cursor を再起動するか、**Developer: Reload Window** を実行する。
3. Skill が認識されることと、明示的に指定して使えることを確認する。

この Skill のみを含むパッケージでは、`.cursor-plugin/plugin.json` は不要である。\
マーケットプレイスへの申請は、この手順の対象外とする。

## 同梱内容と管理元

Plugin のマニフェストはルートの `plugin.json` だけで管理し、Agent Plugins 1.0.0 のスキーマを宣言する。\
OpenAI 固有の設定が必要になった場合は、このファイルの `extensions["com.openai"]` に記載する。\
`.codex-plugin/plugin.json` は別に管理しない。\
OpenAI はこの互換形式も扱えるが、ルートのマニフェストに OpenAI 拡張を記載すると、その設定が採用され、互換形式の設定とは結合されない。\
詳細は [OpenAI の配布仕様](https://developers.openai.com/plugins/build/plugins) を参照する。

生成スクリプトは、指定した Git コミットから次の基準でファイルを選ぶ。

- ルートの `plugin.json`、`LICENSE`、`THIRD_PARTY_NOTICES.md` を含める。
- 公開 `skills/` 内の Git 管理下のファイルを含める。\
  参照資料、実行に必要なファイル、メタデータ、2 つの上流ミラーとその来歴文書 `UPSTREAM.md` が対象となる。\
  ただし、`evals/` ディレクトリと、ファイル名が `-ja.md` または `.ja.md` で終わるファイルは除外する。
- リポジトリの指示、テスト、文書、および `.agents/` 内のリポジトリ保守専用 Skill は除外する。

同梱するファイルの内容は、バイト単位で原本を保持する。\
`skills/` に追加して Git で管理するファイルは配布候補になるため、コミット前にスクリプト、外部参照、認証情報、生成物の混入を確認する。

ZIP には、`plugin.json` と `skills/` を囲む親ディレクトリは設けない。\
公開 Skill はすべて含めるが、利用時にはそれぞれの [実行条件](compatibility.md#plugin-の実行条件) を満たす必要がある。

## アーカイブを生成・検証する

Python 3.10 以降と Git を使う。\
生成スクリプトは追加の Python ライブラリを必要とせず、通信、インストール、アップロードを行わない。

1. **配布元のコミットを準備する。**\
   Skill 本文と関連ファイルは `skills/` で管理し、配布用のコピーを別に保守しない。\
   更新時は、変更した Skill の責務に必要な検証を行い、`plugin.json` のバージョンを上げる。\
   バージョンと原本の変更をコミットしてから生成する。\
   配布済みのバージョンを異なる内容で差し替えない。

2. **原本を検査し、ZIP を生成する。**\
   配布元のコミットと同じリビジョンをチェックアウトして実行する。\
   `<commit>` はそのコミット、`<outside-repository-output-directory>` はリポジトリ外の出力先ディレクトリに置き換える。

   ```bash
   python3 -B scripts/check_repository.py
   python3 -B -m unittest discover -s tests
   git diff --check
   python3 -B scripts/build_plugin.py --ref <commit> --output-dir <outside-repository-output-directory>
   ```

   生成スクリプトは、指定された参照からコミットを一度だけ特定し、コミット済みのファイルを読み取る。\
   未コミット・未追跡のファイルは含めない。\
   出力先に同名ファイルがあれば、上書きせずエラーにする。

3. **push 済みのコミットから導入を検証する。**\
   候補ブランチを push し、[APM の検証](compatibility.md#検証) に従って、そのコミットをリポジトリ外の検証用ディレクトリに導入する。\
   検証には、全 Skill の一括導入、影響する Skill の選択導入・個別パスからの導入、ロックファイルを使った frozen install、audit を含める。\
   ソースのチェックアウト内では、dry-run 以外の APM インストールを実行しない。

4. **生成物と検証結果を保管する。**\
   ZIP、ハッシュ、元コミット、変更概要、検証結果を対応づけて保管する。\
   その後、ユーザーがアーカイブをアップロードし、前述の導入手順で更新を確認する。\
   GitHub Releases で公開する場合は、別途許可を得る。

### 生成されるファイル

| 出力 | 用途 |
| --- | --- |
| `<name>-<version>.zip` | 導入する Plugin アーカイブ |
| `<name>-<version>.sha256` | アーカイブの内容を識別するための SHA-256 ハッシュ |
| `<name>-<version>.build.json` | 元コミット、アーカイブのハッシュ、Skill 一覧、同梱ファイルごとのハッシュとファイルモードの記録 |

ZIP 内のファイル順と時刻を固定し、無圧縮で格納するため、圧縮ライブラリのバージョンに依存せず、同じ入力からバイト単位で一致する ZIP を再生成できる。

### 生成時に検査する内容

生成スクリプトは、次を検査する。

- マニフェストの識別情報のうち対応する項目、ルートの必須ファイル、各 Skill の `SKILL.md` の存在。
- ミラーのハッシュと、来歴文書に記録されたハッシュの一致。
- 相対 Markdown リンクと、コードスパンに明記された `references/`・`../` から始まる参照が、同梱対象を指していること。
- 同梱対象にシンボリックリンクやサブモジュールが含まれていないこと。
- ZIP 内の各ファイルの内容とファイルモードが、元の Git blob とそのモードに一致すること。

これらは特定の梱包不備を検出する検査であり、JSON Schema の全項目の検証、Markdown の完全な解析、動作評価ではない。\
Skill を変更した場合は、一般的な例や通常の文章で示される参照、ツールの利用可否、条件付きの指示など、自動検査では確認できない内容を別途見直す。

## 不具合のある版から復旧する

必要な旧版の内容を原本に戻し、同じ生成・導入・検証手順を経て、新しいバージョンとして配布する。
