# Skill 作成ガイド

このガイドは、保守者と、保守者の代わりに作業するエージェントに向けたものである。\
このリポジトリで保守する Skill の設計、執筆、確認の方法と、Skill を変更したときにほかに更新するものを説明する。\
Skill を作る前や、既存の Skill の動作を変える前に読む。

2 つの上流 Gist のミラーは例外である。\
これらは [上流 Gist のミラー](#上流-gist-のミラー) のコピー規則に従い、このガイドの規則を理由に `SKILL.md` を変更することはない。

## Skill を設計する

### 責務

各 Skill には、一つの責務と、使う場面をはっきり持たせる。\
その責務の中で、次の判断を優先する。

- **結果から設計する**: 判断が必要な作業手順は、あらかじめ決めた成果物からではなく、期待する結果と証拠から設計する。
- **指示の自由度を作業に合わせる**: 複数の進め方が妥当な場合は、目的と制約を示す。\
  順序や網羅性が正しさに影響する場合は、短い番号付きの手順と確認方法を示す。
- **診断はすべて報告する**: 修正を段階的に実装したり展開したりする場合でも、すべての指摘を報告する。
- **作業の量は証拠に決めさせる**: さらに証拠を集めても判断が変わらなくなるまで、調べて報告する。

新しい Skill が既存の Skill と重複していないかを確かめるときは、重複を判断するのに必要な既存の Skill だけを読み、判断できたら止める。

### 名前

`clarify-request` や `design-changes` のように、動作と対象をケバブケースでつないだ名前にし、責務と使う場面が名前から分かるようにする。\
短さより分かりやすさを優先し、実際より広い責務を連想させる名前は避ける。\
`build` のような一語の名前は、責務が狭く、誤解のおそれがない場合だけ使う。

### description

エージェントは、Skill を使うかどうかを `description` を読んで判断する。\
一般的な説明ではなく、その判断のために書く。\
次を含める。

- Skill を使う状況
- Skill が支援する作業の種類
- 特定のクライアントに依存する場合は、その依存の内容

`description` には、エージェントが Skill を選ぶのに必要なことだけを書く。\
Skill を選んだ後に必要なこと（役割、処理の組み立て方、実行の詳細など）は本文に書く。

`description` は、「Drafts commit messages for ...」のように三人称で書く。\
クライアントは description をシステムプロンプトに加えるので、そこで視点が変わると、Skill が選ばれにくくなることがある。

`description` は簡潔に保つ。\
Skill を使う場面を書き、使わない場面は列挙しない。\
除外する作業を列挙すると、その作業がエージェントの文脈に入るからである。\
二つの Skill が同じ依頼で選ばれる場合は、それぞれの Skill の使う場面をより具体的にする。

次は避ける。

- 使う場面が分からない説明
- 「便利な Skill」のような主観的な表現
- 特定のクライアントを前提にしていることを書かずに、そのクライアントを前提にした説明
- 内部実装の詳細

### 本文

Skill の見出しを統一する必要はない。\
ただし、事前の文脈を持たないエージェントが、足りない方針を作り出さずに作業手順を選び、実行し、確認できるだけの情報は必要である。\
本文に次の内容があるかを確認する。

- 目的と、一つの責務
- 行動する前に必要な証拠、入力、前提条件
- 作業手順、または判断の基準
- 出力に含める情報。\
  後の工程がそれに依存する場合は、厳密な出力形式
- 重要な場合は、権限、失敗時の扱い、安全や許可の範囲
- 作業の結果と、関係する安全上の条件の確かめ方
- 同梱資料と、それぞれを読む条件や実行する条件

これらの内容を表せる最小の構成にする。\
よくある形は次の 2 つである。

| 形 | 典型的な内容 |
| --- | --- |
| 判断型 | 短い目的、完了条件のある手順、手順が使う判断基準や参照用の一覧、報告 |
| 操作型 | 短い目的、入力または前提条件、完了条件のある順序付きの手順、出力形式、確認方法 |

これらの形は本文をレビューするために使い、必須の見出しとしては扱わない。\
たとえば、判断で進め方を選んだ後に、壊れやすい操作を厳密な順序で行う Skill では、両方を組み合わせてよい。

次の節や一覧は、Skill の実行のしかたを変える場合だけ追加する。

- **`When to use` の節**: Skill が選ばれた後に、エージェントが分岐を判断する必要がある場合だけ追加する。\
  `description` を繰り返すだけの節は追加しない。
- **厳密な出力テンプレートと、自己確認用のチェックリスト**: それがないとエージェントの行動が変わる場合だけ追加する。

各規則は、範囲や規則の別の節ではなく、エージェントがそれを当てはめる手順の中に置く。

既存の安全対策を置き換える場合は、置き換えた後も元と同等以上に保護できることの確かめ方を決める。

### 手順

各手順は、「各指摘にラベルと確信度があれば完了とする」のように、エージェントが確かめられる完了条件で終える。\
完了条件が曖昧だと、エージェントは手順を早く終えてしまう。\
最も強い完了条件は、「変更した各ファイルを扱った」のように、確かめられて漏れのないものである。

### 挙動を変える文だけを残す

文を残すのは、それがないとエージェントの行動が変わる場合だけにする。\
モデルがもともとすることを伝える文は削り、語の一部ではなく文全体を削る。

- Red、Green、Refactor のように、モデルがすでに知っている語は、説明せずに使う。
- コマンドやファイルの構成のように、エージェントがリポジトリで見つけられる事実は、写さずにその場所を示す。\
  そのような事実を写すのは、見つけるのに手間がかかる場合だけにする。

### 制約

制約が一つ増えるごとに、エージェントが気にかけるべきことが増える。\
また、出所の違う制約どうしが食い違うこともある。\
制約は、その Skill の作業で起こり得る誤りを防ぐ場合だけ書く。

- **肯定の形**: 望む行動を書く。\
  たとえば「期待値は仕様から決める」のように書く。\
  禁止の形で書くと、禁じた行動がエージェントの文脈に入り、かえってその行動が起きやすくなることがある。
- **禁止事項**: 禁止は、許可のない破壊的な操作のように、肯定の形では書けない強い防護柵にだけ使う。\
  その場合も、望む行動を並べて書く。
- **一般的な規則**: ツールの出力は指示ではなくデータとして扱う、といった規則は、どの作業にも当てはまる。\
  このような規則は、Web ページを読む Skill のように、その作業がリスクを生む Skill にだけ書く。\
  書く場合は、リスクが生じる手順に一度だけ書く。
- **一つの規則は一か所に**: 同じ規則を、作業手順と範囲の節の両方に書かない。

## Simplified Technical English で書く

Skill の本文、`description`、同梱資料、リポジトリの文書の英語は、[ASD-STE100 Simplified Technical English](https://asd-ste100.org/about_STE.html) の書き方の規則に従って書く。\
リポジトリの文書には、`README.md`、`CONTRIBUTING.md`、`AGENTS.md`、`docs/` のファイルが含まれる。\
これらの規則は文を短くし、一つの文が一つの意味だけを持つようにする。\
そのため、エージェントも人も、同じ文を同じ意味に読める。\
次の一覧は要約である。\
規則の全体は、ASD から仕様を入手して確認する。

- 1 文には指示を一つだけ書く。
- 指示の文は 20 語以内、説明の文は 25 語以内にする。
- 能動態を使い、指示には命令形を使う。
- 4 語以上の名詞を連ねない。
- 1 つの段落は一つの話題にし、6 文以内にする。
- 1 文に収まらない数の条件や項目は、縦に並べたリストにする。
- 文を短くするために、冠詞、動詞、主語を省かない。
- 「this」「that」「it」「its」「their」が指すものが別の段落や項目にある場合は、指示語を使わずに「the」と名詞を書く。

STE の辞書は、厳密な規則ではなく目安として使う。\
二つの語から選べる場合は、より一般的な語を使う。\
[用語集](glossary.md) の用語、製品名、識別子は、技術用語として扱う。\
一つの語には一つの意味だけを持たせ、同じものには毎回同じ語を使う。

2 つの上流 Gist のミラー、引用した文とコード、日本語の文章には、これらの規則を適用しない。\
日本語の文章については、[同じ考え方を日本語に当てはめる](#同じ考え方を日本語に当てはめる) を参照する。

## 同じ考え方を日本語に当てはめる

日本語が基準の Skill と日本語参考訳には、STE の規則の意図を当てはめる。\
語数の上限と STE の辞書は英語に固有なので、代わりに次の規則を使う。

- 1 文には指示を一つだけ書く。
- 読点で 3 つ以上の節をつないだ文は、分ける。
- 主体が変わる場合は、新しい主体を示す。\
  文脈から主体が明らかな場合は、省く。\
  日本語では、主語を繰り返すと不自然になるからである。
- 指示は「〜する」のような言い切りで書く。\
  受け身や婉曲な依頼ではなく、能動の形にする。
- 漢語の名詞を 4 つ以上つなげない。\
  「の」や動詞で分ける。
- 1 つの段落は一つの話題にし、6 文以内にする。
- 1 文に収まらない数の条件や項目は、縦に並べたリストにする。
- 助詞と動詞を残し、体言止めを連ねない。
- 「この」「その」などの指示語が指すものが、別の段落や項目にある場合は、指示語を使わずに名詞を書く。
- [用語集](glossary.md) の語を使い、同じものには毎回同じ語を使う。

これらの規則は、指示としての明確さを扱う。\
翻訳調の構文や英語の混在のような、日本語としての自然さは、`write-natural-japanese` の Skill に従う。

## 手順とリストの書式を整える

- **2 文以上の手順**: 手順が 2 文以上あるか、リストを含む場合は、その手順の先頭に短い太字の手順名を置く。\
  手順名の後に空行を置き、その下に手順の本文を書く。
- **短い手順**: リストのすべての手順が 1 文の場合は、番号の直後にその文を書く。\
  リストのどれか一つの手順に太字の手順名が必要な場合は、そのリストのすべての手順に太字の手順名を付ける。
- **項目の間の空行**: リストのどれか一つの項目がリスト、表、複数の段落を含む場合は、そのリストのすべての項目の間に空行を置く。\
  それ以外の場合は、項目の間に空行を置かない。
- **手順に属する内容**: 手順に属する表やリストはインデントし、その手順の中に収める。

これらの規則は、Skill の本文に適用する。\
日本語参考訳にも適用する。

## Skill 同士を独立させる

各 Skill は、単独で機能しなければならない。\
`SKILL.md` と `SKILL-ja.md` には、ほかの公開 Skill の名前を書かない。\
対象外の作業は作業の種類で、引き継ぎは次の工程が必要とする入力で書く。\
Skill 同士の関係は、[次に使う Skill を選ぶ](../users/workflows.md) にだけ記録する。\
`scripts/check_repository.py` は、ほかの公開 Skill の名前を検出するとエラーにする。\
承認済みの併用関係と上流のミラーは対象外とする。

### 併用関係

併用関係では、一方の Skill が、規則を正しく適用するために意図して他方の Skill を必要とする。\
これは限られた例外である。\
意図しない Skill 間の結びつきは設計上の問題なので、利便性、主題が近いこと、任意の依存関係を理由に作らない。

承認した関係ごとに、次を記録する。

- 関わる Skill と、どちらがどちらを必要とするか
- 併用する Skill が必要な理由
- 2 つの Skill をどのように一緒にインストールするか、または配置するか
- 併用する Skill が使えない場合の動作（作業を止めるかどうかを含む）
- この関係を導入した、または維持している出典と、このリポジトリでの改変

いずれかの Skill、関係、インストールの方法、併用する Skill がない場合の動作が変わったときは、この記録を見直し、影響を受ける動作を確かめる。

### 承認済み: 日本語参考訳の保守

| 必須の併用関係 | 出典 |
| --- | --- |
| `maintain-japanese-references` → `write-natural-japanese` | 独自作成。[#42](https://github.com/mtk177a/skills/pull/42) で保守用 Skill を追加。[#77](https://github.com/mtk177a/skills/issues/77) に必須の併用関係と、日本語で要件を定める例外を記録 |

- **理由**: 英語版の意味を保ちながら、文脈に合う日本語にするため。
- **配置**: どちらの Skill もこのリポジトリで管理している。
- **使う前**: `skills/write-natural-japanese/SKILL.md` と、必須の参照資料を読む。\
  リポジトリのファイルが読めない場合は、個人環境の同名 Skill で代用せず、作業を止めて報告する。

上流の `cognitive-rhythm-writing` も、ほかの Skill を必要とする。\
[上流 Gist のミラー](#上流-gist-のミラー) を参照する。

## 複数のクライアントに対応する

### 共通の Skill とクライアント固有の Skill

まず、特定のクライアントに依存せずに Skill を書けるかを判断する。

- 共通の Skill は、複数のクライアントで、同じ目的に同じ手順で使える。
- クライアント固有の Skill は、手順、ツール、入出力の形式が一つのクライアントに結びついている。

このリポジトリでは、Skill をクライアントごとのディレクトリに分けない。\
クライアントへの依存は、Skill の名前か `description` で示す。

クライアント固有のメタデータは、Skill がそのクライアントの呼び出しの制御、画面表示、依存関係の宣言、許可の動作を必要とする場合だけ追加する。\
それ以外の場合は、`name`、`description`、指示、資料を、共通形式のまま保つ。

### 一つのクライアント向けの Skill をほかのクライアントに対応させる

Codex などの一つのクライアント向けに書かれた Skill をほかのクライアントに対応させるときは、そのクライアントに固有の表現を残すべきかを判断する。\
残すのは、その固有性が Skill の価値の中心である場合だけにする。\
それ以外の場合は、クライアント固有の仕組みを入れ替えられるよう、目的と判断基準を中心に書き直す。

次を確認する。

- 特定のツール名に頼りすぎていないか
- 依頼の形式と出力の形式が、ほかのクライアントでも意味を成すか
- 手順が、一つのクライアントの機能を前提にしていないか
- 残っているクライアントごとの違いが、`description` か本文に書かれているか
- その要件が、Skill の指示で足りるのか、クライアントが強制するポリシー、許可設定、フックが必要なのか

クライアントが指示ファイルをどう検出し、読み込み、優先するか、Skill をどう呼び出すかを、形式の互換性から推測しない。\
これらの動作が設計に影響する場合は、対象の各クライアントの最新の公式資料を確認する。\
資料が条件付きであったり不完全であったりする場合は、対象のバージョンや環境で動作を確かめる。\
その結果はその時点の判断に使い、このガイドにはクライアントの動作の一覧を持たない。

### 共通の指示ファイルとクライアント固有の指示ファイル

リポジトリ共通の指示は `AGENTS.md` に置く。\
クライアント固有の指示ファイルは、そこへの橋渡しだけを担う。

- **Copilot の橋渡し**: `.github/copilot-instructions.md` は、Copilot に `AGENTS.md` を読むよう指示する。\
  読めない場合、Copilot はファイルの変更、コマンドの実行、外部の状態の変更をせずに止まる。
- **`AGENTS.md` を自動で読み込まないクライアント**: 安全と承認の範囲を守るのに必要な最小限の規則だけを、橋渡しのファイルにも書く。\
  これはそのクライアントに規則を届けるための代替手段であり、規則の 2 つ目の基準ではない。
- **更新**: `AGENTS.md` の関連する規則が変わったときは、代替の規則も確認して更新する。\
  その他の共通の規則は、橋渡しのファイルに写さない。

最新のクライアントの資料: [Codex の `AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Claude Code のプロジェクト指示](https://code.claude.com/docs/en/memory)、[GitHub Copilot のカスタム指示への対応状況](https://docs.github.com/en/copilot/reference/custom-instructions-support)。

## 必要な資料だけを同梱する

### スクリプト

`scripts/` を追加するときは、スクリプトの実行に必要なものと副作用を確認する。

- 特定のシェル、OS、アーキテクチャへの依存を最小にする。\
  macOS M1 と Windows WSL の両方で動かないスクリプトは、必要性を明示的に説明できる場合を除いて追加しない。
- 追加の依存関係があれば、それを記録する。
- リポジトリの外にある絶対パスに依存しない。
- 破壊的な操作を行うスクリプトでは、実行前に確認を求めるよう Skill の本文に書く。
- 生成物やキャッシュをリポジトリに含めない。

### 参照資料

`references/` ディレクトリには、形式、仕様、判断基準など、Skill が判断に使う資料を置く。

- 事前の文脈を持たないエージェントが Skill を適用するのに必要なものだけを含める。
- 外部の文書をそのままコピーせず、元の資料にリンクする。
- 一時的なメモや、顧客に固有の情報を保存しない。
- 含める資料のライセンスを確認し、両立しないライセンスの内容は同梱しない。

### アセット

`assets/` ディレクトリには、画像、再利用できるテンプレート、小さな構造化データなど、Skill が使う補助資料を置く。

- 出典が明確で、ライセンスが両立する資料だけを含める。
- 生成物、キャッシュ、一時ファイルを含めない。
- 大きなバイナリファイルは、本当に必要な場合を除いてリポジトリに含めない。

## 秘密情報と非公開情報を含めない

Skill の本文、スクリプト、参照資料、アセットには、次を絶対に含めない。

- API キー、トークン、パスワード
- 顧客名、個人情報
- 社内の URL、社内の手順、その他の非公開の運用情報
- ローカル環境にだけ存在する秘密のファイルへの参照

Skill は、ほかの環境やエージェントから読まれることを前提に書く。\
環境に固有の情報には、変数名やプレースホルダーを使う。

## 外部の Skill を取り込む

### 外部の Skill をこのリポジトリに取り込む条件

2 つの Gist のミラーを除き、このリポジトリは外部の Skill をそのままコピーしない。

次のいずれかに当てはまる場合だけ、外部の Skill をこのリポジトリに取り込む。

- 自分で継続して変更し、保守する必要がある
- そのまま使うより、一から設計し直した方がよい
- 自分の作業の進め方に合わせて構成を変えたい

その場合も、そのまま取り込まず、フロントマターと `description` をこのリポジトリの規約に合わせる。

第三者の Skill を採用または改変する前に、出典、ライセンス、すべてのファイル、外部への参照、スクリプト、ツールとネットワークの使用、それらを組み合わせたときにできることをレビューする。\
Markdown の指示は、無害な文章ではなく、エージェントを動かし得るものとして扱う。\
チェックリストは [セキュリティレビュー](security.md) に従う。

### 上流 Gist のミラー

`japanese-tech-writing` と `cognitive-rhythm-writing` は、k16shikano 氏が公開している Gist のコピーである。\
これらの `SKILL.md` は、それぞれの `UPSTREAM.md` に記録した版とバイト単位で一致する。\
どちらのファイルにも、このリポジトリ独自の規則、フロントマターの項目、編集上の修正、日本語参考訳を追加しない。

リポジトリの検査スクリプトは、各コピーを `UPSTREAM.md` に記録した SHA-256 と照合する。\
新しい Gist の版があるかどうかは検査しないので、それを知るには上流の Gist と自分で比較する必要がある。

ミラーを更新する手順は次のとおりである。

1. 記録した版と現在の Gist を比較する。
2. [セキュリティレビュー](security.md) に従って、変更全体を確認する。
3. 採用した版を改変せずにコピーする。
4. 版、ハッシュ、第三者の著作物の表示を更新する。

新しい上流のファイルをそのまま採用できない場合は、差分を記録し、このリポジトリ独自の版は作らない。

上流の `cognitive-rhythm-writing` は、使う前に `../japanese-tech-writing/SKILL.md` を読む。\
インストールする人は、[APM でインストールする](../users/installation.md#apm-でインストールする) に書いたとおり、2 つを一緒にインストールする必要がある。\
併用する Skill がない場合の手順を、上流のファイルに追加しない。

## 関連する文書を更新する

Skill を追加したり、Skill の動作を変えたりしたときは、その Skill を外から説明している文書を確認する。

- **目的別の一覧**: `README.md` と `README.ja.md` にある、その Skill の行を追加または更新する。\
  どちらかの一覧に Skill がないと、検査スクリプトが報告する。
- **[次に使う Skill を選ぶ](../users/workflows.md)**: Skill の引き継ぎが変わったときに更新する。\
  報告する状態の名前が変わった場合も含む。\
  このガイドは、その状態の名前を使って次に使う Skill を示している。
- **[実行条件](../users/compatibility.md)**: Web へのアクセス、サブエージェント、ほかの Skill、全文を読む同梱の参照資料など、すべての Skill に必要なこと以上の条件が増えたり、なくなったりしたときに更新する。
- **日本語参考訳**: `SKILL.md` の意味が変わったときは、[言語と日本語参考訳](localization.md) に従って `SKILL-ja.md` を更新する。

## プルリクエストを作る前に新しい Skill を確認する

- [ ] ディレクトリ名がケバブケースで、フロントマターの `name` と一致している。
- [ ] `SKILL.md` のフロントマターに `name`、`description`、`license` がある（2 つの Gist のミラーは上流のフロントマターを保つ）。
- [ ] 本文を読まなくても、`description` から使う場面が分かる。
- [ ] 見出しのテンプレートを機械的に写さずに、本文が [本文](#本文) に挙げた内容を満たしている。
- [ ] 本文が英語で書かれているか、日本語の執筆・推敲用の例外が記録されている。
- [ ] 英語が [Simplified Technical English で書く](#simplified-technical-english-で書く) に従い、日本語の文章が [同じ考え方を日本語に当てはめる](#同じ考え方を日本語に当てはめる) に従っている。
- [ ] [手順](#手順) のとおり、各手順が完了条件で終わっている。
- [ ] それぞれの制約が [制約](#制約) の条件を満たしている。
- [ ] `SKILL.md` が記録済みの日本語の基準でない限り、`SKILL-ja.md` がある。
- [ ] 承認済みの併用関係を除き、ほかの公開 Skill の名前を書いていない。
- [ ] 秘密情報、個人情報、社内の URL を含んでいない。
- [ ] 外部の資料を含める場合は、第三者の出典と実行機能のリスクをレビューしている。
- [ ] `scripts/`、`references/`、`assets/` には Skill に必要なものだけがあり、空のディレクトリは削除している。
- [ ] [関連する文書を更新する](#関連する文書を更新する) に挙げた文書を更新している。
- [ ] リポジトリの検査スクリプトと、残しているコードのテストが成功し、Skill の作業結果と安全上の範囲を必要に応じて確認している。
