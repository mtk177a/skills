# Skill 作成ガイド

この手引きは、保守者と、保守者の代わりに作業するエージェントに向けたものである。\
このリポジトリで保守する Skill の設計、執筆、確認の方法を説明する。

2 つの上流 Gist のミラーは例外である。\
これらは [上流 Gist のミラー](#上流-gist-のミラー) のコピー規則に従い、この手引きの規則を理由に `SKILL.md` を変更することはない。

Skill 本文の言語と参考訳の更新は、[言語と日本語参考訳](localization.md) に従う。

## Skill を設計する

### 責務

各 Skill には、一つの責務と、使う場面をはっきり持たせる。\
設計では次を優先する。

- 判断が必要な作業手順は、あらかじめ決めた成果物からではなく、期待する結果と証拠から設計する。
- 指示の自由度は、作業の壊れやすさと文脈への依存度に合わせる。\
  複数の進め方が妥当な場合は、目的と制約を示す。\
  順序や網羅性が正しさに影響する場合は、短い番号付きの手順と確認方法を示す。
- 完全な診断と、段階的な実装や展開を分ける。
- 調査の範囲や報告する指摘の数に、根拠のない上限を設けない。

新しい Skill を既存の Skill と比べるときは、責務の重複を解消し、判断がまとまるのに必要な例だけを読む。\
その目的を果たしたら止め、理由なくカタログ全体を読まない。

Skill と一緒に配布する必要がある設計上の説明は、その Skill の `references/` ディレクトリに置く。

### 名前

`clarify-request` や `design-changes` のように、動作と対象をケバブケースでつないだ名前にし、責務と使う場面が名前から分かるようにする。\
短さより分かりやすさを優先し、実際より広い責務を連想させる名前は避ける。\
`build` のような一語の名前は、責務が狭く、誤解のおそれがない場合だけ使う。

### description

`description` は、エージェントが Skill を使うかどうかを判断するために読むものであり、一般的な説明ではない。\
次を含める。

- Skill を使う状況
- Skill が支援する作業の種類
- 特定のエージェントに依存する場合は、その依存の内容

実行の仕組みより、使う場面について書く。\
自動的な選択に必要な情報はすべて `description` に置き、Skill を読み込んだ後に必要な情報（役割、処理の組み立て方、実行の詳細など）は本文に置く。

次は避ける。

- 使う場面が分からない曖昧な説明
- 「便利な Skill」のような主観的な表現
- Codex を前提にしていることを書かずに、Codex を前提にした説明
- フロントマターに詰め込んだ内部実装の詳細

### 本文

Skill の見出しを統一する必要はない。\
ただし、事前の文脈を持たないエージェントが、足りない方針を作り出さずに作業手順を選び、実行し、確認できるだけの情報は必要である。\
本文が次の役割を満たしているか確認する。

- 目的と、一貫した一つの責務
- `description` に含める、使う場面を判断するための十分な文脈と、重要な対象外
- 行動する前に必要な証拠、入力、前提条件
- 作業手順または判断の進め方
- 必要な出力の情報。\
  後の工程がそれに依存する場合は、厳密な出力形式
- 重要な場合は、権限、失敗時の扱い、安全や許可の範囲
- 作業の結果と、関係する安全上の条件の確認
- 同梱する資料と、それを読む条件や実行する条件

これらの役割を表せる最小の構成にする。\
よくある形は次の 2 つである。

| 形 | 典型的な内容 |
| --- | --- |
| 判断型 | 目的、証拠、作業手順、必要に応じた判断基準、報告内容、範囲 |
| 操作型 | 目的、入力または前提条件、順序のある手順、出力形式、確認方法、範囲 |

これらはレビューのための分類であり、必須の見出しではない。\
判断で進め方を選んだ後に、壊れやすい操作を厳密な順序で行う Skill では、両方を組み合わせてよい。

`description` を繰り返すだけの `When to use` の節は、本文に追加しない。\
Skill が選ばれた後に、エージェントが分岐を判断するために必要な場合だけ残す。\
同じように、厳密な出力テンプレート、`Always` / `Ask first` / `Never` の一覧、自己確認用のチェックリストは、Skill の実行のしかたを変える場合だけ使う。

既存の安全対策を置き換える場合は、置き換えた後も同等以上に保護できることの確かめ方を決める。

Skill の指示や資料を変更したときは、[実行条件とクライアントごとの違い](../users/compatibility.md) の該当する記述と、一緒に配布する資料も見直す。

## Skill 同士を独立させる

各 Skill は、単独で機能しなければならない。\
`SKILL.md` と `SKILL-ja.md` には、ほかの公開 Skill の名前を書かない。\
対象外の作業は作業の種類で、引き継ぎは次の工程が必要とする入力で書く。\
Skill 同士の関係は、[次に使う Skill を選ぶ](../users/workflows.md) にだけ記録する。\
`scripts/check_repository.py` がこの規則を検査する。\
承認済みの併用関係と上流のミラーは対象外とする。

### 併用関係

併用関係は、一方の Skill が規則を正しく適用するために、意図して他方の Skill を必要とする、限られた例外である。\
利便性、主題が近いこと、任意の依存関係を理由に作らない。\
意図しない Skill 間の結びつきは、引き続き設計上の問題として扱う。

承認した関係ごとに、次を記録する。

- 関係の向きと、関わる Skill
- 併用する Skill が必要な理由
- 対応する導入方法
- 併用する Skill が使えない場合の動作（作業を止めるかどうかを含む）
- この関係を導入した、または維持している出典と、このリポジトリでの改変

いずれかの Skill、関係、導入方法、併用する Skill がない場合の動作が変わったときは、この記録を見直し、影響を受ける動作を確かめる。

### 承認済み: 日本語参考訳の保守

| 必須の併用関係 | 出典 |
| --- | --- |
| `maintain-japanese-references` → `write-natural-japanese` | 独自作成。[#42](https://github.com/mtk177a/skills/pull/42) で保守用 Skill を追加。[#77](https://github.com/mtk177a/skills/issues/77) に必須の併用関係と、日本語で要件を定める例外を記録 |

- **理由**: 英語版の意味を保ちながら、文脈に合う日本語にするため。
- **配置**: どちらの Skill もこのリポジトリで管理している。
- **使う前**: `skills/write-natural-japanese/SKILL.md` と、必須の参照資料を読む。\
  リポジトリのファイルが読めない場合は、個人環境の同名 Skill で代用せず、作業を止めて報告する。

上流の `cognitive-rhythm-writing` も、ほかの Skill を必要とする。\
[上流 Gist のミラー](#上流-gist-のミラー) を参照する。

## 複数のエージェントに対応する

### 共通の Skill とエージェント固有の Skill

まず、特定のエージェントに依存せずに Skill を書けるかを確認する。

- 共通の Skill は、複数のエージェントで、同じ目的に同じ手順で使える。
- エージェント固有の Skill は、手順、使えるツール、入出力の形式が一つのエージェントに結びついている。

このリポジトリでは、分類用のディレクトリを使わない。\
違いは、Skill の名前か `description` で示す。

クライアント固有のメタデータは、Skill が呼び出しの制御、画面表示、依存関係の宣言、権限の動作を必要とする場合だけ追加する。\
それ以外の場合は、`name`、`description`、指示、資料を、共通形式のまま保つ。

### Codex 専用の Skill をほかのエージェントに対応させる

Codex 専用の Skill を Claude Code や GitHub Copilot 向けに改変するときは、Codex 固有の表現を残すべきかを判断する。\
残すのは、その固有性が Skill の価値の中心である場合だけにする。\
それ以外の場合は、仕組みを入れ替えられるよう、目的と判断基準を中心に書き直す。

クライアントが指示ファイルをどう検出し、読み込み、優先するか、Skill をどう呼び出すかを、形式の互換性だけから推測しない。\
これらの動作が設計に影響する場合は、対象の各クライアントの最新の公式資料を確認する。\
資料が条件付きであったり不完全であったりする場合は、対象のバージョンや環境で動作を確かめる。\
その結果は、このリポジトリにクライアントの動作の一覧を保守するのではなく、その時点の判断に使う。

改変するときは、次を確認する。

- 特定のツール名に頼りすぎていないか
- 依頼の形式と出力の形式が、ほかのエージェントでも意味を成すか
- 手順が Codex 固有の機能を前提にしていないか
- エージェントごとの違いが、`description` か本文に書かれているか
- 共通の指示の基準が一つで、クライアント固有の橋渡しファイルが、記録した最小限の安全と承認の規則だけを重複させているか
- 残している安全と承認の代替規則が、基準となる規則とずれていないか
- その要件が、挙動についての指示で足りるのか、クライアントが強制するポリシー、権限、フックが必要なのか

### 共通の指示ファイルとクライアント固有の指示ファイル

リポジトリ共通の指示は `AGENTS.md` に置く。

- **Copilot の橋渡し**: Copilot に `AGENTS.md` を読むよう指示する。\
  読めない場合、Copilot はファイルの変更、コマンドの実行、外部の状態の変更をせずに止まる。
- **`AGENTS.md` を自動で読み込まないクライアント**: 安全と承認の範囲を守るのに必要な最小限の規則だけを、橋渡しのファイルに重複して書く。\
  これは指示を届けるための代替手段であり、規則の 2 つ目の基準ではない。
- **更新**: `AGENTS.md` の関連する規則が変わったときは、代替の規則も確認して更新する。\
  その他の共通の規則は重複させない。

最新のクライアントの資料: [Codex の `AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Claude Code のプロジェクト指示](https://code.claude.com/docs/en/memory)、[GitHub Copilot のカスタム指示への対応状況](https://docs.github.com/en/copilot/reference/custom-instructions-support)。

## 必要な資料だけを同梱する

### スクリプト

`scripts/` を追加するときは、実行に必要なものと副作用を確認する。

- 特定のシェル、OS、アーキテクチャへの依存を最小にする。
- 追加の依存関係があれば、それを記録する。
- リポジトリの外にある絶対パスに依存しない。
- 破壊的な操作を行うスクリプトでは、実行前に確認を求めるよう Skill の本文に書く。
- 生成物やキャッシュをリポジトリに含めない。

macOS M1 と Windows WSL の両方で動かなくなるスクリプトは、必要性を明示的に説明できる場合を除いて避ける。

### 参照資料

`references/` ディレクトリには、形式、仕様、判断基準など、Skill が判断するときに必要な資料を置く。

- 事前の文脈を持たないエージェントが Skill を適用するのに必要なものだけを含める。
- 外部の文書をそのままコピーせず、元の資料にリンクする。
- 一時的なメモや、顧客に固有の情報を保存しない。
- 含める資料のライセンスを確認し、両立しないライセンスの内容は同梱しない。

### アセット

`assets/` ディレクトリには、画像、再利用できるテンプレート、小さな構造化データなど、配布する補助資料を置く。

- 出典が明確で、ライセンスが両立する資料だけを含める。
- 生成物、キャッシュ、一時ファイルを含めない。
- 大きなバイナリファイルは、本当に必要な場合を除いてリポジトリに含めない。

## 秘密情報と非公開情報を含めない

Skill の本文、スクリプト、参照資料、アセットには、次を絶対に含めない。

- API キー、トークン、パスワード
- 顧客名、個人情報
- 社内の URL、社内の手順、その他の非公開の運用情報
- ローカル環境にだけ存在する秘密のファイルへの参照

Skill は、ほかの環境やエージェントから読まれることを前提に書く。\
環境に固有の情報には、変数名やプレースホルダーを使う。

## 外部の Skill を取り込む

### 外部の Skill をフォークまたはコピーする条件

2 つの Gist のミラーを除き、外部の Skill をそのままこのリポジトリにコピーしない。\
外部の Skill の導入は、dotfiles で `apm.yml` と `apm.lock.yaml` によって管理する。

次のいずれかに当てはまる場合だけ、Skill をこのリポジトリに取り込む。

- 自分で継続して変更し、保守する必要がある
- そのまま使うより、一から設計し直した方がよい
- 自分の作業の進め方に合わせて構成を変えたい

その場合も、そのまま取り込まず、フロントマターと `description` をこのリポジトリの規約に合わせる。

第三者の Skill を採用または改変する前に、出典、ライセンス、すべてのファイル、外部への参照、スクリプト、ツールとネットワークの使用、実行機能の組み合わせをレビューする。\
Markdown の指示は、それ自体が安全な文章ではなく、エージェントを動かし得るものとして扱う。\
リポジトリのチェックリストは [セキュリティレビュー](security.md) に従う。

### 上流 Gist のミラー

`japanese-tech-writing` と `cognitive-rhythm-writing` は、k16shikano 氏が公開している Gist のコピーである。\
これらの `SKILL.md` は、それぞれの `UPSTREAM.md` に記録した版とバイト単位で一致する。\
どちらのファイルにも、このリポジトリ独自の規則、フロントマターの項目、編集上の修正、日本語参考訳を追加しない。

リポジトリの検査スクリプトは、各コピーを `UPSTREAM.md` に記録した SHA-256 と照合する。\
新しい Gist の版があるかどうかは検査しないので、それには上流の Gist との明示的な比較が必要になる。

ミラーを更新する手順は次のとおりである。

1. 記録した版と現在の Gist を比較する。
2. [セキュリティレビュー](security.md) に従って、変更全体を確認する。
3. 採用した版を改変せずにコピーする。
4. 版、ハッシュ、第三者の著作物の表示を更新する。

新しい上流のファイルをそのまま採用できない場合は、差分を記録し、このリポジトリ独自の版は作らない。

上流の `cognitive-rhythm-writing` は、使う前に `../japanese-tech-writing/SKILL.md` を読むことを求めている。\
[選んだ Skill の導入](../users/installation.md#apm-でインストールする) で、両方を一緒に導入する。\
併用する Skill がない場合の手順を、上流のファイルに追加しない。

## プルリクエストを作る前に新しい Skill を確認する

- [ ] ディレクトリ名がケバブケースで、フロントマターの `name` と一致している。
- [ ] `SKILL.md` があり、フロントマターに `name`、`description`、`license` がある（2 つの Gist のミラーは上流のフロントマターを保つ）。
- [ ] 本文を読まなくても、`description` から使う場面が分かる。
- [ ] 見出しのテンプレートを機械的に写さずに、本文が [本文](#本文) に挙げた役割を満たしている。
- [ ] 本文が英語で書かれているか、日本語の執筆・推敲用の例外が記録されている。
- [ ] `SKILL.md` が記録済みの日本語の基準でない限り、日本語参考訳の `SKILL-ja.md` がある。
- [ ] 承認済みの併用関係を除き、ほかの公開 Skill の名前を書いていない。
- [ ] 秘密情報、個人情報、社内の URL を含んでいない。
- [ ] 外部の資料を含める場合は、第三者の出典と実行機能のリスクをレビューしている。
- [ ] `scripts/`、`references/`、`assets/` には Skill に必要なものだけがあり、空のディレクトリは削除している。
- [ ] リポジトリの検査スクリプトと、残しているコードのテストが成功し、Skill の作業結果と安全上の範囲を必要に応じて確認している。
