# 用語集

このガイドは、保守者と、保守者の代わりに作業するエージェントに向けたものである。\
このリポジトリ固有の概念にどの用語を使うかと、一つの語で指してはいけない対象の組み合わせを記録する。\
これらの概念について文書や Skill の本文を書くときや、日本語に訳すときに参照する。

これは、訳語を一つに固定する対応表ではない。\
同じものを指すときは同じ用語を使い、用語は英語の語だけからではなく、その文が指しているものから選ぶ。\
ここに載せた語も、ほかの文脈では通常の意味で使ってよい。

## このリポジトリの概念

### Plugin の ZIP

- **英語**: plugin ZIP
- **日本語**: Plugin の ZIP
- **指すもの**: `scripts/build_plugin.py` が作る ZIP ファイル。\
  `plugin.json` と `skills/` を含む。

「アーカイブ」や「パッケージ」ではなく「Plugin の ZIP」と書く。\
ファイルと、その中に入っている Plugin を、読み手が区別できるようにするためである。

### Plugin

- **英語**: plugin
- **日本語**: Plugin
- **指すもの**: クライアントで有効にする Agent Plugin。\
  どのファイルで届いたかは問わない。

### 公開 Skill 全体

- **英語**: all public Skills
- **日本語**: 公開 Skill 全体
- **指すもの**: `skills/` にあるすべての Skill。\
  APM で一度にインストールできる。

「バンドル」は、APM の `SKILL_BUNDLE` 形式を指す場合だけ使う。

### 同梱資料

- **英語**: bundled resources
- **日本語**: 同梱資料
- **指すもの**: Skill のディレクトリにある `SKILL.md` 以外のファイル。\
  `references/`、`scripts/`、`assets/` など。

### インストール

- **英語**: install
- **日本語**: インストール
- **指すもの**: Skill をクライアントで使える状態にすること。\
  APM でインストールする場合も、Plugin の ZIP をアップロードする場合や展開する場合も含む。

`apm install` のようなコマンド名は、そのまま書く。\
「展開」は、ZIP を展開するという具体的な操作の名前として使う。\
「導入」は、新しい用語や機能を導入するといった本来の意味にだけ使う。\
Skill のインストールには、「インストール」を使う。

### 公開と配布

- **英語**: publish
- **日本語**: 公開
- **指すもの**: 保守者以外の人も Skill を使える状態にすること。\
  現在は、このリポジトリを GitHub で公開することで Skill を公開している。\
  Plugin の ZIP を公開するには承認が必要である。

「配布」（distribute）は、ライセンスの再配布の条件のように、第三者の資料をほかの人へ渡す場合だけに使う。\
Plugin の ZIP は手元で作るだけで誰にも渡していないので、「配布」と呼ぶと実際に起きていることと合わなくなる。

### 作る

- **英語**: build
- **日本語**: 作る
- **指すもの**: 生成スクリプトで Plugin の ZIP を作ること。

スクリプトそのものの動作を説明するときは「生成」を使う。

### 保守者

- **英語**: maintainer
- **日本語**: 保守者
- **指すもの**: このリポジトリを保守する人と、その人の代わりに作業するエージェント。

### 利用者

- **英語**: people who use the Skills
- **日本語**: 利用者
- **指すもの**: Skill をインストールして使う人。\
  保守者自身も含む。

リポジトリの文書では、この人を「ユーザー」（user）ではなく「利用者」と書く。\
これらの文書はエージェントと人の両方が読むので、「ユーザー」は読み手によって指す相手が変わってしまうからである。

### Skill の本文の「ユーザー」

- **英語**: user
- **日本語**: ユーザー
- **指すもの**: 現在のセッションでエージェントに作業を指示している人。

Skill の本文の読み手は常にエージェントなので、「ユーザー」はこの意味にしかならない。

### クライアントと ChatGPT の画面

- **英語**: client
- **日本語**: クライアント
- **指すもの**: エージェントが Skill を実行するソフトウェア。\
  Codex、Claude Code、Cursor、ChatGPT など。

Chat、Work、dots は、ChatGPT の中の別々の画面である。\
総称を作らず、「ChatGPT の Chat、Work、dots」のように名前で書く。

### 利用側のリポジトリ

- **英語**: consumer repository
- **日本語**: 利用側のリポジトリ
- **指すもの**: APM で Skill をインストールし、自分の `apm.yml` とロックファイルを管理するリポジトリやディレクトリ。

### 英語版

- **英語**: English source
- **日本語**: 英語版
- **指すもの**: 要件を定める英語のファイル。\
  日本語参考訳はこのファイルから訳す。

このファイルを「原本」や「正本」と呼ばない。\
これらの語は法的な原本や記録上の正本を連想させるが、実際の関係は翻訳とその元のファイルだからである。

### 上流

- **英語**: upstream
- **日本語**: 上流
- **指すもの**: 上流 Gist のミラーのコピー元にした、外部の Gist。

### ガイド

- **英語**: guide
- **日本語**: ガイド
- **指すもの**: `docs/` にある、読者を明示して書いた文書。

## 別々のものを指し得る語

### 証拠と理由

日本語では「根拠」がどちらの意味にもなるため、混ざりやすい。

- 主張を支えたり否定したりする材料（観測、ログ、テスト結果、文書など）: evidence、証拠。
- 判断や結論をそう決めた理由: reason や basis、理由や根拠。

「証拠で裏付けられている」と「根拠がある」は、どちらも自然な場合がある。\
材料が理由に読めたり、理由が観測した材料に読めたりしないように、表現を選ぶ。

### 権限とアクセス権

- 人や当事者が持つ、決めたり操作を認めたりする力: authority、権限。\
  例: 設計する権限、実行の権限。
- クライアントやシステムの設定で与えられる技術的なアクセス（ツールへのアクセス、サンドボックスの設定、書き込みなど）: permission、アクセス権または許可設定。\
  例: 書き込みのアクセス権。

どちらも「権限」と訳すと、足りないのが人の判断なのか、システムの設定なのかが分からなくなる。

### 許可と承認

- 権限を持つ人が、特定の操作や範囲を認めていること: authorized、許可された。
- 責任者が、提案や結果を明示的に受け入れること（GitHub の `Approve` を含む）: approved、承認された。

`authorized` は、「承認済み」ではなく「許可された」と訳す。\
「承認」は、実際には行われていないかもしれない正式な受け入れの手続きを連想させる。

### 確認と検証

- 実行した個々のテスト、コマンド、点検: check、確認。\
  `check_repository.py` のような特定のチェックの名前は、そのまま書く。
- 結果が期待を満たしているかを証拠で確かめること（修正が元の指摘を解消したかの判定など）: verify、validate、verification、検証。

この区別が必要ない通常の文では、「確認」でかまわない。

## 項目を追加・変更する

項目を追加するのは、次のどちらかに当てはまる場合だけにする。

- このリポジトリ固有の概念
- 現在、区別すべき二つのものを一つの語で指してしまっている語

一般的な語を追加するのは、意味が混ざっている場合だけにし、表記が揺れているだけでは追加しない。\
各項目には、指すものと、区別が必要な理由を書く。\
英語版と日本語参考訳は一緒に更新する。
