# 次に使う Skill を選ぶ

この手引きは、一つの作業で複数の Skill を使う人に向けたものである。\
通常どの Skill を次に使うかと、次へ進む条件を示す。\
最初に使う Skill は、[目的別の一覧](../../../README.ja.md#skill-一覧) から選ぶ。

ここに書いたつながりは案内である。\
すべての手順を実行する必要はなく、つながりがあることで何かの操作が許可されるわけでもない。\
入力、出力、作業の範囲は、各 Skill に書かれている。

## 変更と障害

一般的な変更では、次の 4 つの Skill を順に使う。

`clarify-request` → `design-changes` → `implement-changes` → `review-changes`

依頼の明確化や設計で決めるべきことが、すでに十分に明確で許可も得ている場合は、その工程を省略する。

この流れの前や途中で、特定の不足を補う Skill が 2 つある。

- 用語が曖昧な場合は `define-referents` を使い、合意した意味で元の作業に戻る。
- 重要な選択に実質的に異なる選択肢がある場合は `explore-decision-space` を使い、方針を選んでから `design-changes` を使う。

依頼全体が不明確な場合は `clarify-request` を使う。\
`define-referents`、`draft-issue`、`record-session-handoff` などは、依頼全体を自分で明確化せず、明確化が必要なことを報告する。

障害の場合は `investigate-failure` から始める。\
実装へ直接進むのは、診断に裏付けがあり、許可された目的、影響範囲、期待する結果、安全対策、検証方法がすべて決まっている場合に限る。\
それ以外の場合は、次に `design-changes` を使う。\
修正した後は、`validate-fix` で元の障害に照らして確かめる。

`investigate-failure` や `triage-review-feedback` が、現在の公開文書、注意喚起、提供元の挙動を証拠として必要とする場合は、`research-web-safely` で調べられる。\
その場合も、診断や判断は元の Skill が行う。

原因調査はインシデント対応を支援できるが、対応の指揮や承認済みの安定化手順を代わりに担うものではない。

## レビューと修正

レビューでは、通常次の Skill を順に使う。\
コメントの下書きは、必要な場合だけ行う。

`review-changes` → `triage-review-feedback` → `draft-review-comments`（任意） → `implement-changes` → `validate-fix`

各引き継ぎでは決まった情報を渡し、受け取る側の Skill は、前の Skill が担う判断を行わない。

- **レビュー → 指摘の判断**: 指摘の分類、影響、確度だけでは、対応するかどうかは決まらない。
- **指摘の判断 → 実装**: 実装するのは、許可された `Act now` の作業だけである。\
  懸念を認めても、指摘した人の解決案を採用する必要はない。
- **指摘の判断 → コメントの下書き**: 評価、状態、対応方針を渡す。\
  依頼者が直接指定してもよいが、下書きの工程ではこれらを判断しない。
- **指摘のないレビュー → コメントの下書き**: 結論、レビューした範囲、実施した確認、その限界を渡す。\
  指摘ごとの判断は不要である。
- **修正 → 再確認**: 特定済みの修正の確認には `validate-fix` を使う。\
  `review-changes` を再び使うのは、差分全体の再レビューを明示的に依頼された場合だけである。

`validate-fix` は、検証対象の外で見つけた、修正が原因の問題を `review-changes` へ引き継ぐ。\
差分全体を再レビューする場合は、修正が原因の問題、修正後に初めて確認できるようになった問題、以前から確認できた問題を区別し、次の修正に進む条件は Skill の指示に従う。

これらの引き継ぎでは、証拠と不確実な点を引き継ぐ。\
情報がないことは、リスクが低い根拠にならない。\
コメントの下書きを作っても、それを投稿することや GitHub のレビュー操作を選ぶことは許可されない。

変更を説明するだけで問題を探さない Skill が 2 つある。\
変更の要約には `summarize-changes`、コミットの分け方とメッセージには `draft-commit` を使う。

## リスクのある作業と行き詰まった作業

次の状況では、作業をいったん止めて、対応する Skill を使う。

| 状況 | Skill | 作業に戻る条件 |
| --- | --- | --- |
| 復旧、運用、セキュリティ、外部の状態に重大な影響がある操作をする | `assess-risky-change-readiness` | 対象の操作、安全対策、残るリスク、実行の権限が揃っている。 |
| 仮説を変えずに同じような試行を繰り返しても、役立つ証拠が増えない | `break-failure-loop` | 仮説を見分ける確認によって、証拠か仮説が変わる。 |
| 現在の設計では進められず、局所的な確認でも選択を決められない | `explore-decision-space` | 実質的に異なる方針を選び、変更を設計する。 |

`design-changes` や `implement-changes` で追加の重大リスク対策が必要と分かった場合は、実行前に `assess-risky-change-readiness` を使う。\
使うかどうかは、「移行」「本番」などの呼び名ではなく、実際の影響で判断する。\
`Ready for authorization` は承認済みという意味ではない。\
`Ready for execution handoff` は既存の権限を記録する状態であり、操作を実行するものではない。\
復旧には、巻き戻しではなく、復元、補償、影響の封じ込め、損失の受け入れが必要な場合もある。

仮説を見分ける確認で証拠か仮説が変わるまでは、行き詰まった分岐を止めたままにする。\
`break-failure-loop` の後は、診断に直接戻る場合も、作業を止めたままにする場合もある。\
簡単に元に戻せる作業や、十分な比較に基づいて選択済みの作業では、選択肢の探索を求めない。

## 実行環境と学習支援

作業に使うチャット、エージェント、モデル、ツールを使える環境、エージェントの構成を選ぶには、`choose-ai-execution-setup` を使う。\
作業内容への理解も保ちたい場合は、選んだ環境の中で `calibrate-learning-support` を続けて使う。

## エージェント向けの指示と Skill

ここで扱う Skill は、`AGENTS.md` や Skill のように、エージェントが継続して使う指示を対象にする。

エージェントの予期しない挙動の原因が分からない場合は、変更を設計する前に `audit-agent-guidance` を使う。\
原因がすでに証拠で裏付けられている場合は、この診断を省く。\
そのうえで、次のどちらかの Skill で修正を設計する。

- Skill の責務と範囲には `design-skill`
- 指示文書の役割分担と、クライアントによる読み込み方には `design-agent-instructions`

最後に、`design-changes` で実装と検証方法を決める。\
設計しただけでは、予期しない挙動が直ったことにはならない。
