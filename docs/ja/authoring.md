# Skill 作成ガイド

この文書は、このリポジトリで管理する Skill の作成ガイドである。\
元 Gist のコピー 2 件には後述の別の規則を適用し、この文書の作成規則を理由に `SKILL.md` を変更しない。\
個別の Skill と一緒に配布する必要がある設計上の説明は、その Skill の `references/` ディレクトリに置く。

- **新しく作る**: [責務](#責務を定める) → [名前](#skill-の命名) → [使用条件](#description-の書き方) → [本文](#本文に必要な情報) の順に確認する。
- **外部から取り込む**: [取り込み条件と Gist の扱い](#外部-skill-のフォークコピーについて) を確認する。
- **提出前に確認する**: [新規 Skill チェックリスト](#新規-skill-チェックリスト) を使う。

## 責務を定める

**一つの責務と、使う場面を明確にする。**

本文と参考訳の言語・更新方法は [言語方針](localization.md) に従う。

設計では次を優先する。

- 高度な判断を要する作業手順は、あらかじめ決めた成果物ではなく、期待する結果と証拠から設計する
- 指示の自由度を手順を誤った場合の影響と文脈依存性に合わせる。\
  複数の進め方が妥当なら目的と制約を示し、順序や完全性が正しさに影響するなら簡潔な番号付き手順と検証方法を示す
- 完全な診断と、段階的な実装または展開を分ける
- 調査範囲や指摘件数に、根拠のない上限を設けない

既存の Skill と比較する場合は、責務の重複を解消し、判断が収束するまでに必要な例を確認する。\
目的を満たしたら止め、根拠のない件数上限を設けたり、理由なくカタログ全体を読んだりしない。

## Skill の命名

`clarify-request` や `design-changes` のように、責務と利用場面が分かる `動作 + 対象` のケバブケースを基本とする。\
実際より広い責務を連想させる名前は避け、短さより明確さを優先する。\
`build` などの単語だけの名前は、責務が狭く、誤解されない場合に限る。

## description の書き方

`description` は一般的な説明ではなく、Skill を使うか判断するための情報である。\
次を含める:

- どのような状況でこの Skill を呼び出すか
- どのような作業を支援するか
- 特定のエージェントへの依存があれば、その依存内容
- 実行方法より利用場面に重点を置く
- 暗黙的な選択に必要な情報をすべて `description` に置き、読み込み後の役割、処理の組み立て方、実行方法は本文へ移す

避けること:

- 利用場面が不明瞭な曖昧な説明
- 「便利な Skill」のような主観的な表現
- 明示せず Codex を前提にした説明
- 内部実装の詳細をフロントマターに詰め込むこと

## 本文に必要な情報

Skill の見出しを統一する必要はない。\
一方で、事前知識のないエージェントが不足する方針を推測せずに作業手順を選び、実行し、検証できるだけの情報は必要となる。

次の役割を満たしているか確認する:

- 目的と一貫した単一の責務
- `description` に含める、使用条件を判断するための十分な文脈と重要な対象外
- 行動前に必要な証拠、入力、前提条件
- 作業手順または判断方法
- 必要な出力情報。\
  後続の利用者が必要とする場合は厳密な出力形式
- 重要な場合の権限、失敗時の扱い、安全性または許可の境界
- 作業結果と関係する安全上の条件の検証
- 同梱する資料と、それを読む条件または実行する条件

これらの責務を表せる最小の構成を使う。\
代表的な構成は次の 2 つである。

| 構成 | 典型的に含める内容 |
| --- | --- |
| 判断型 | 目的、証拠、作業手順、必要に応じた判断基準または観点、報告内容、境界 |
| 操作型 | 目的、入力または前提条件、順序付きの手順、出力形式、検証方法、境界 |

これらは確認時の分類であり、必須の見出しではない。\
文脈に応じた判断で方法を選び、その後に失敗しやすい操作を厳密な順序で行う Skill では、両方を組み合わせられる。

`description` の繰り返しとして本文へ `When to use` を追加しない。\
Skill が選択された後にもエージェントが分岐判断に使う条件がある場合だけ残す。\
同様に、厳密な出力テンプレート、`Always` / `Ask first` / `Never`、併用 Skill の節、自己確認用のチェックリストは、その区別が実行を実質的に変える場合だけ使う。

既存の安全対策を置き換える場合は、同等以上の保護を維持できる検証方法を定める。

## 併用 Skill

Skill は原則として自己完結させる。\
併用関係は、一方の Skill が規範を正しく適用するために、他方の Skill を意図的に必要とする場合に限って認める例外である。\
利便性、関連する主題、任意の依存関係を表すためには使わない。\
意図しない Skill 間の結合は、引き続き設計上の問題として扱う。

承認する関係には、次を記録する。

- 関係の方向と対象 Skill
- 併用 Skill が必要な理由
- 対応する導入方法
- 併用 Skill が利用できない場合の動作。\
  作業を停止するかどうかを含む
- 関係を導入または維持する出典とローカルでの改変内容

いずれかの Skill、関係、導入方法、または併用 Skill がない場合の動作を変更する場合は、この記録を見直し、影響を受ける挙動を確認する。

### 承認済み: 日本語参考訳の保守

| 必須の併用関係 | 出典 |
| --- | --- |
| `maintain-japanese-references` → `write-natural-japanese` | 独自作成。[#42](https://github.com/mtk177a/skills/pull/42) で保守用 Skill を追加。[#77](https://github.com/mtk177a/skills/issues/77) に必須の併用関係と日本語で要件を定める例外を記録 |

- **理由**: 英語版との意味の一致と、文脈に合う日本語の両方を確認するため。
- **配置**: 両 Skill をこのリポジトリで管理する。
- **使用前**: `skills/write-natural-japanese/SKILL.md` と必要な参照資料を読む。\
  読めない場合は個人環境の同名 Skill で代用せず、停止して対象ファイルを報告する。

## 共有 Skill とエージェント固有 Skill

まず、エージェント依存なしに Skill を表現できないかを検討する。

- 共有 Skill: 同じ目的・同じ手順で複数のエージェントが使用できる
- エージェント固有 Skill: 手順、ツール、入出力形式が特定のエージェントに強く結びついている

このリポジトリでは分類ディレクトリを使わない。\
違いは Skill 名や `description` で表す。\
エージェント固有性が重要な場合は、名前か説明にその文脈を含める。

## 複数のエージェントに対応する

Codex 固有の Skill を Claude Code や GitHub Copilot 向けに改変するとき、Codex 固有の表現を残すべきかを見直す。

Skill の共通仕様に対応するクライアントでも、指示ファイルの検出方法、読み込み方、優先順位、Skill の選択方法が同じとは限らない。\
これらの違いが設計に影響する場合は、対象クライアントの最新の公式文書を確認する。\
公式文書の説明がバージョンや実行環境によって異なる、または十分でない場合は、対象環境での挙動も確かめる。\
確認した結果はその設計判断に使い、変わり得るクライアントの挙動をこの文書に一覧として維持しない。

### 共有指示とクライアント固有の指示

**共有指示は `AGENTS.md` で管理する。**

- **Copilot 用の橋渡しファイル**: `AGENTS.md` を読むよう指示し、参照できなければファイル変更・コマンド実行・外部変更をせずに停止させる。
- **自動で読み込まれない環境への対応**: 橋渡しファイルには、この境界を保つための最小限の安全性・承認ルールだけを重複して記載する。\
  共有指示を別に定義する場所にはしない。
- **更新時**: `AGENTS.md` の関連ルールと橋渡しファイルを同時に確認・更新する。\
  それ以外の共有ルールは重複させない。

### 他のエージェントへ対応させるときの確認

- 特定のツール名への過度な依存
- 依頼形式と出力形式が他のエージェントでも意味をなすか
- Codex 固有の機能を前提にしているステップ
- エージェント固有の差異が `description` や本文で十分に説明されているか
- 共通指示を `AGENTS.md` で管理し、クライアント固有の橋渡しファイルが、文書化された必要最小限の安全性・承認ルールだけを重複しているか
- 維持している安全性・承認用の代替手段が `AGENTS.md` のルールと整合しているか
- 要件をエージェントへの動作指示で表すべきか、クライアントが強制する方針、権限、フックが必要なのか

その固有性が Skill の主な価値である場合のみ、Codex 固有の表現を残す。\
そうでなければ、目的と判断基準を中心に書き直し、実行機構を差し替え可能にする。

クライアントの公式文書: [Codex の `AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Claude Code のプロジェクト指示](https://code.claude.com/docs/en/memory)、[GitHub Copilot のカスタム指示](https://docs.github.com/en/copilot/reference/custom-instructions-support)。

## 外部 Skill のフォーク・コピーについて

下記の Gist 2 件を除き、外部 Skill はそのままコピーしない。\
外部 Skill のインストールは、dotfiles の `apm.yml` / `apm.lock.yaml` で管理する。

次の条件を満たす場合のみ、このリポジトリに取り込む。

- 自分で継続的に変更・維持する必要がある
- そのまま使うより最初から再設計した方が良い
- 自分のワークフロー向けに明確に再構成したい

取り込む場合でも、フロントマターと `description` をこのリポジトリの規約に合わせて見直す。\
そのままインポートしない。

第三者の Skill を採用または改変する前に、出典、ライセンス、すべてのファイル、外部参照、スクリプト、ツールとネットワークの利用、組み合わせたときに得られる機能を確認する。\
Markdown の指示を本質的に安全な文章ではなく、実行に影響する入力として扱う。\
リポジトリのチェックリストは [セキュリティレビュー](security.md) に従う。

### 元 Gist のコピー 2 件

`japanese-tech-writing` と `cognitive-rhythm-writing` は、k16shikano の公開 Gist をコピーした Skill である。\
各 `SKILL.md` は、`UPSTREAM.md` に記録した版とバイト単位で一致させる。\
独自の規則、フロントマターの項目、本文の訂正、日本語参考訳は加えない。\
リポジトリ検査では、各ファイルと `UPSTREAM.md` に記録した SHA-256 の一致を確認する。\
Gist に新しい版があるかどうかは、別途確認する必要がある。

更新時は、記録した版と現行 Gist を比較し、変更全体を [セキュリティレビュー](security.md) に従って確認する。\
受け入れた版を無改変でコピーし、版、ハッシュ、第三者資料の通知を更新する。\
そのまま受け入れられない場合は差分を記録し、独自の改変版を作らない。

元の `cognitive-rhythm-writing` は、適用前に `../japanese-tech-writing/SKILL.md` を読むよう指示している。\
[選択導入](distribution.md#apm-で導入する) で両方を導入する。\
併用先がない場合の手順を、元 Gist の本文へ独自に追記しない。

## 秘密情報・個人情報を除く

Skill 本文、ヘルパースクリプト、参照資料、補助ファイルには次を含めない。

- API キー、トークン、パスワード
- 顧客名、個人情報
- 内部 URL、内部手順、非公開の運用情報
- ローカル環境にしか存在しない秘密ファイルへの参照

Skill は他の環境やエージェントから参照される可能性があると想定して書く。\
環境固有の情報には変数名やプレースホルダーを使う。

## 必要な補助ファイルを同梱する

### スクリプト

`scripts/` を追加する場合は、実行環境と副作用を確認する。

- シェル、OS、アーキテクチャへの依存を最小化する
- 追加の依存があれば文書化する
- リポジトリ外の絶対パスに依存しない
- スクリプトが破壊的な操作を行う場合、Skill 本文で安全確認を促す
- 生成物やキャッシュをリポジトリに混在させない

明確な理由なく、macOS M1 または Windows WSL との互換性を損なうスクリプトは避ける。

### 参照資料

`references/` ディレクトリには、Skill が判断時に必要とする資料 (フォーマット、仕様、判断基準) を置く。

- 事前知識のないエージェントが Skill を適用するために必要なものだけを含める
- 外部文書はそのままコピーせず、公開されている参照元へリンクする
- 一時メモや顧客固有情報を置かない
- 含める資料のライセンスを確認し、互換性のないライセンスの資料を同梱しない

### 画像・テンプレートなど

`assets/` ディレクトリには、配布可能な補助ファイル (画像、再利用可能なテンプレート、小さな構造化データ) を置く。

- 出典が明確でライセンスが互換なものだけを含める
- 生成物、キャッシュ、一時ファイルを `assets/` に混在させない
- 本当に必要でない限り、大きなバイナリファイルはリポジトリに入れない

## 新規 Skill チェックリスト

新規 Skill の PR を作る前に、次を確認する。

- [ ] ディレクトリ名がケバブケースでフロントマターの `name` と一致している
- [ ] `name`、`description`、`license` のフロントマターが揃った `SKILL.md` が存在する（文書化した Gist のコピー 2 件は元のフロントマターを維持する）
- [ ] `description` が本文を読まなくても利用場面を明確に伝えている
- [ ] 見出しテンプレートを機械的に写さず、本文に意味上必要な情報が揃っている
- [ ] 本文が英語で書かれているか、日本語の執筆・推敲用 Skill の例外が文書化されている
- [ ] 日本語の `SKILL.md` で要件を定めると文書化されている場合を除き、`SKILL-ja.md` の日本語参考訳が存在する
- [ ] 秘密情報、個人情報、内部 URL が含まれていない
- [ ] 外部素材を含む場合、第三者の出典と、組み合わせたときに生じる機能上のリスクを確認している
- [ ] `scripts/`、`references/`、`assets/` に必要なものだけが含まれている (空のディレクトリは削除済み)
- [ ] リポジトリ検査と残すコードのテストが成功し、Skill の作業結果と安全上の境界を必要に応じて確認している
